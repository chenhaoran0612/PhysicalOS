# 机器人应用：应用瀑布流和工作流页面（issue #60）

更新：2026-11-27。对应 GitHub issue #60「机器人应用管理」：

> 机器人应用本质是给机器人配置 一个工作流，让他调用1个后者多个技能。
>
> 最外面应该是一个瀑布流，展示所有的应用，也是绑定给对应品牌型号的机器人。

> 状态：代码和测试完成；**没有在任何真机上运行过**，也还没有合并。验证范围见[最后一节](#在哪里验证过哪里没有)。

用户在 issue 会话里定的三件事（2026-11-27）：

1. **「技能资产」和「注册技能」收进「技能」按钮**：最外层只有应用瀑布流；右上角「技能」点开是技能列表，可以登记技能、看详情。
2. **点开一张应用卡片是应用的工作流页面**：按顺序画出每一步调用哪个技能、参数和最长时间；修改、检查、交付清单、绑定任务都从这一页进。
3. **创建应用时选品牌型号**，不再选某一台机器人；系统用这个品牌型号里的一台机器人核对能力。

## 现在的页面

| | 原来 | 现在 |
|---|---|---|
| 「机器人应用」最外层 | 上半部分是应用卡片（等高的三列），下半部分是「技能资产」表格 | 只有应用瀑布流 |
| 一张卡片是什么 | 应用的一个版本（改出新版本后是两张卡片） | 一个应用，显示它最新的版本，写明一共几个版本 |
| 卡片上有什么 | 名称、品牌型号、几个技能步骤、前三个技能、「交付清单」「检查」 | 品牌型号、版本、名称、工作流的每一步（技能名称，最多 6 步，多的写“还有 N 步”）、可用的机器人、进度、绑定的任务 |
| 点卡片 | 没有反应（要点按钮） | 打开这个应用自己的页面 |
| 技能 | 在同一页的下半部分 | 在「技能」页面（右上角按钮，写着技能个数） |
| 创建应用 | 选“目标机器人” | 选“品牌型号” |

### 瀑布流（`#skills`）

- 账号里的每个应用一张卡片，新的在前。卡片的高度跟着工作流的步数走，所以是瀑布流：宽页面三列，窄了两列、一列（CSS 多列，卡片不会被拆开）。
- 品牌型号的筛选（issue #48）照旧在卡片上面。
- 整张卡片可以点，键盘上是卡片标题那个按钮（回车打开）。卡片底部「绑定到任务」（issue #50）照旧。
- 从任务过来创建应用时（issue #50 的“正在为任务「…」准备应用”），提示改成“创建时选的品牌型号就是应用的品牌型号”，卡片和应用页面上都有「绑定到这个任务」。
- 还没有应用时：没有技能，先让人把机器人上已安装的技能加进来；有技能，直接创建应用；所选品牌型号下没有应用，写明应用属于一个品牌型号。

### 一个应用的页面（`#app`）

- 「← 全部应用」；品牌型号、版本；名称；「修改工作流」「检查」「交付清单」。
- **工作流**：从“开始”到“结束”的一条线，每一步一个节点：技能名称和版本、执行入口、完成条件、停止条件、最长时间、需要的设备能力、调用时的参数（原样显示）。技能已经不在的步骤标红并写明。
- 右边四块：**机器人**（这个品牌型号有几台、几台已连接、名字，已连接的在前）、**进度**（配置检查 → 现场测试 → 发布，按当前版本的记录算）、**任务**（绑定到了哪些任务，可以绑定和解除）、**版本记录**（可以查看旧版本；旧版本的页面写明“这不是最新版本”）。
- 「修改工作流」就是原来的“修改为新版本”：保存后是同一个应用的新版本，页面跟着显示新版本。「检查」和「交付清单」打开的还是原来的交付清单。
- 侧边栏仍然亮着「机器人应用」，页头的路径写“机器人应用 / 应用名称”。刷新页面留在这个应用上（记在浏览器的会话存储里）；应用不在了就回到瀑布流。

### 技能页面（`#app-skills`）

原来的「技能资产」表格，多一列“使用情况”（几个应用在用，按各应用最新版本算）。「使用机器人上已安装的技能」和「登记技能」在这一页的右上角。不在侧边栏里，从「机器人应用」的「技能」按钮进。

### 创建应用：选品牌型号

- 表单里“目标机器人”换成“品牌型号”：账号里机器人的每个品牌型号一项（写明几台机器人），没有填品牌型号的机器人各自一项（“名字（未填写品牌型号）”，这样的应用只能用在这一台上，issue #48 的规则）。
- 选了品牌型号，下面能选的技能只剩这个品牌型号的（issue #48 的规则，没有改）。
- 发给服务端的仍然是一台机器人的 id（服务端的规则没有改：应用的品牌型号取自这台机器人）。**这一台怎么选**：这个品牌型号里已连接的真机优先，其次真机，其次已连接的仿真机器人；同样条件下取最早添加的。
- 这个品牌型号只有仿真机器人时，在字段下面写明“应用只能做仿真测试，接入真机后才能发布到设备”。
- 正在按某个品牌型号筛选、或者是从某个任务过来的，表单一开始就选中那个品牌型号。
- “修改工作流”的表单同样改成品牌型号；应用原来记的那台机器人不变。

## 怎么实现的

- 新增 `web/app_gallery.js`、`web/app_gallery.css`，在 `web/task_apps.js` 之后加载。应用的事实（每个应用的最新版本、可用的机器人、进度、绑定的任务）都用 `web/task_apps.js` 里现成的函数；筛选条用 `web/robot_model.js` 的。
- 它接管 `views.skills`，新增 `views.app`、`views['app-skills']` 两个页面；包了一层 `action`（`appg-open`、`appg-back`、`appg-skills`、`appg-version`）、`render`（侧边栏和路径；`#app` 没有应用时回到瀑布流）、`form`（两个表单的机器人字段换成品牌型号）。
- 表单字段的名字没有变（仍是 `robot_id`），所以 `web/app.js` 的提交、`web/robot_model.js` 的“只能选同品牌型号的技能”都不用改。字段是按原来的写法找到再替换的；`web/delivery.js`、`web/revisions.js` 里那两处写法变了的话，`tests/test_app_gallery.py` 会失败。
- 改到共用文件的地方只有两处插入：`brainos/server.py`（静态文件）、`web/index.html`（一行）。服务端的规则和接口没有改动。
- `web/robot_model.js` 的 `rmAppsPage`、`rmApplicationCard`（issue #48 画这个页面的函数，issue #50 在卡片上加了一行）现在没有页面使用，没有删：留给以后决定。

## 对已有浏览器验收脚本的影响

见分支交付说明。原则：卡片仍然是 `article.card`，容器仍然带 `cards`；创建应用的表单字段仍然叫 `robot_id`，保存后仍然打开交付清单。变了的是：

- 「技能资产」表格、`skill-add`、`detail-skills` 不在 `#skills` 上了，在 `#app-skills`。
- 应用表单里 `robot_id` 的选项是品牌型号，值是代表这个品牌型号的那台机器人的 id；原来按任意一台机器人的 id 选的脚本要改成按品牌型号选。
- 卡片上没有「交付清单」「检查」按钮了（在应用的页面里）。
- 整张卡片是一个点击区域：脚本要点卡片上的按钮（「绑定到任务」）照常点；要“点卡片”就点标题按钮 `.ag-open`。

这次改了三个已有脚本，其余的没有受影响：

- `browser_smoke`：登记技能改到 `#app-skills`，再回 `#skills` 创建应用。
- `robot_model_browser`：“技能按品牌型号列出”改为到技能页面检查每个技能写着自己的品牌型号；应用的筛选照旧。
- `ux02_browser`：创建应用时关于仿真的提示改成新的句子（“只有仿真机器人：应用只能做仿真测试”）。

## 这一版没有做的

- 工作流仍然是顺序执行、失败即停（服务端第一版的规则），没有分支、循环、并行；页面上的“工作流”画的就是这条顺序线。
- 工作流的修改还是在对话框表单里做（「修改工作流」），不是在页面上直接拖动节点。
- 检查、现场测试、发布发给哪一台机器人，仍然是应用记的那台，或者在交付清单里另选（issue #48）；没有改成“自动选一台已连接的”。
- 删除应用（原来也没有）。
- 瀑布流用 CSS 多列：卡片先从上到下排满一列，再排下一列，所以“最新的”在左上，第二新的在它下面，不是右边。
