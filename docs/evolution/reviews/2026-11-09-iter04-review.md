## 总评

做得扎实、经实证成立的部分：

- **静态级与报告结构**：清单校验、必备能力、`simulated` 显式、`model_runtimes` 一致、固定本体都能抓出问题；`levels.*.ok` 的链式规则与 `blocked` 语义正确。报告 `manifest_digest` 与云端 `catalog.manifest_digest` 逐字节一致（实测 `56529ab0…`）。
- **会被抓出的诚实故障**：
  - 停止后真实滑行 1.5 s（如实上报）→ 中止并保持锁存；
  - 看门狗不归零（如实上报）→ 中止并保持锁存；
  - 导航报"到达"但未移动、机械臂报成功但关节未动 → failed；
  - `cancel()` 抛异常 → 运行时退回到停止，机械臂没有越过最小步长。
- **进程被杀**：motion 测试中 `kill -9` 运行时，重启后急停默认锁存（"上次运行时未正常关闭"），该测试记录标为 `unknown`、不重跑。
- **ADR-011 守住了**：发布与启动只认 `evaluations` 中 `scope:"onsite"` 的记录，这类记录只能由 `/v1/evaluate` 的 `device_run` 证据产生。一致性报告存在 `conformance_reports` 里，store 按集合隔离，无法拿报告 ID 当作 `report_id` 用于部署。云端拒绝 `device_run`、拒绝 `field_acceptance≠false`，桌面端解析也拒绝两者，变异 C1/C2/D1/D2 都被测试杀死。
- **桌面端**：
  - 脚手架输入不可注入：厂商、型号固定为"待确认"，模块名取自净化后的机器人 ID，`evidence_id` 只能引用 store 中已有的 ID；
  - 无证据的映射一律降级为"需确认"；
  - 一致性测试在独立子进程中运行，最小环境、`setsid`、资源上限、超时可杀。

但核心问题的答案是：**会**。

- **测试过程中会造成危险运动，2 个 P0：**
  - **一致性测试会清除操作员按下的急停，然后继续做 motion 运动**（Q4-01）；
  - **dry 级在一个常见的映射下会让机械臂移动 0.9 rad**。dry 级本应不运动、也不需要授权（Q4-02）。
- **另有 5 个 motion 安全或判定 P1：**
  - 中途异常后不停车不锁存，机械臂走完 8 倍步长（Q4-03）；
  - 无定位时"0.1 m 最小目标"实际开了 4.87 m（Q4-04）；
  - 真机也按适配器自报的倍速把导航目标放大到 10 m（Q4-05）；
  - 底盘速度 ×5 或方向反了仍通过 motion（Q4-06）；
  - 取消后延迟恢复、复位后重放旧速度仍通过 motion，测试结束后本体还在开（Q4-07）。
- **另有 2 个工程 P1：**
  - cloud 测试红（Q4-08）；
  - 脚手架可被注入可执行代码（Q4-09）。

"会撒谎的适配器"中，读数与动作一起伪造的情况（滑行但读数静止、看门狗失效但读数伪装、只在被测时守规矩）属于这类套件可测范围的**固有限制**，任何基于适配器自身反馈的测试都抓不到。报告和文档应把这一点写成明确的边界。抓不到的诚实故障是缺陷，见结果表。

本轮共 **2 个 P0、7 个 P1、8 个 P2、5 个 P3**。

**结论：0.11.0 现在不能发布。** 条件如下：

1. 修复 Q4-01 至 Q4-09 并复验。
2. cloud 测试恢复全绿。
3. 发布范围仍限仿真本体与受控云端环境，并在发布说明中写明两点：
   - 一致性 motion 级**在真机上运行前**必须已修复 Q4-01 至 Q4-07；
   - 一致性报告由适配器所在进程自报，可被适配器代码篡改（Q4-13）。

若时间不够，可以先发布不含 `motion` 级、不含 `--url` server 模式的版本，但 Q4-01 的 dry 部分、Q4-02、Q4-08、Q4-09 仍须修复：只跑 dry 也会清除操作员急停，也会让机械臂运动。

## 发现列表

严重度：P0 会导致物理危险、资金损失或越权；P1 是功能错误或可被利用；P2 是健壮性问题或契约偏差；P3 是建议。

### P0

#### Q4-01 · P0 · runtime · 一致性测试会复位操作员按下的急停并继续运动（已复现）
- **位置**：`runtime/neuxmind_runtime/conformance.py:614-626`（`_stop`）、`628-638`（`_ensure_unlatched`）、`640-648`（`_release_latch`）、`1041-1056`（`_dry_stop`）、`1328-1340`（`_after_stop`）、`332-350`（`RuntimeTarget.stale_probe`）。
- **根因**：
  - 套件判断"锁存是我造成的"，依据只是 `latch_reason == self._own_reason`。
  - `_stop()` 不检查当前是否已被别人锁存，直接以自己的原因再停一次。`SafetySupervisor.emergency_stop` 每次都覆盖 `latch_reason`（`safety.py:562`）。
  - 于是只要套件在操作员按停之后自己再调一次 `_stop`，操作员的原因就被覆盖成套件的原因，后面的 `_ensure_unlatched`/`_release_latch` 会把它当成自己的锁存复位。`_dry_stop` 无条件停两次；motion 的每个中断用例都在 `_after_stop` 里停一次。
  - `stale_probe` 更直接：先停再 `reset(True)`，不看原因。
- **复现**（`operator_stop.py`）：用 `AdapterTarget(SimQuadruped)` 模拟操作员按停，两种时机：
  - **dry**：在 `safety.stop.idempotent_latched` 之前插入 `runtime.emergency_stop("operator: person in path")`。结果 `dry_ok=true`、`aborted=null`、`final_latched=false`，操作员停止之后有 **3 次 `safety.reset`**。
  - **motion**：在 `base.velocity.stop_latency` 的套件停止之前插入同样的操作员停止。结果 `motion_ok=true`、未中止、最终未锁存，之后**又执行了** `navigate_to.min_goal / cancel / stop_latency` 与 `legged.posture.stand_noop` 共 4 个运动用例。

  契约写的是"测试中途有人按了停止 → 中止并保持锁存"，与上述行为相反。在 `POST /v2/conformance`（运行中的运行时）上，同样的竞态还会把其他客户端或技能的急停清掉。现有用例 `test_external_stop_aborts_and_stays_latched` 只覆盖"操作员停止后套件下一步就是 `_ensure_unlatched`"这一种时机，所以没有发现这个问题。
- **修复建议**：
  1. 不要用原因字符串判断锁存归属。改用 `SafetySupervisor` 的停止计数或代数：套件每次自己停止后记下计数 n；任何时刻发现计数大于套件自己的停止次数，或锁存不是由套件这一次造成的，就 `_Abort(keep_latched=True)`。
  2. `_stop()` 调用前若已锁存且不是套件自己造成的，立即中止，不得再停。
  3. `stale_probe` 同样先核对计数，复位前再核对一次。
  4. 补用例：在 dry 与 motion 的每个阶段插入外部停止，断言 `aborted`、`final_latched=true`、之后无 `safety.reset`。

#### Q4-02 · P0 · runtime · dry 级会让机械臂运动：`joint.state` 的前 dof 个值被当成机械臂当前角（已复现）
- **位置**：`conformance.py:1231-1246`（`_dry_arm_zero`：`before = joints["position"][:dof]`）、`1036-1038`（`_probe`）、`1268-1281`（`_dry_chunk_zero`）、`849-855`（static 只要求 `joint.state.dof >= arm dof`）。ROS 2 转换 `adapters/ros2.py:139-147` 原样保留 `/joint_states` 的顺序。
- **复现**（`dry_audit.py`）：审计 dry 级发往适配器的全部 `invoke/start_action`。
  - `SimQuadruped`、`SimArm` 都只收到零速度与"目标=真实当前角"，零缺陷。
  - 本体 `ArmJointStateExtra`：`joint.state` 把一个夹爪关节列在最前（dof 7），机械臂 dof 6，真实 q=[0.3,-0.4,0.5,-0.2,0.1,0.0]。dry 级（无 `--authorize`）向机械臂发出 `[0.04,0.3,-0.4,0.5,-0.2,0.1]`，**最大位移 0.9 rad**，机械臂真的走到了该位置。static 通过，dry 报告 `zero_displacement` failed（"零位移目标后关节移动了 0.9000 rad"），但运动已经发生。
  - ROS 2 的 `joint_states` 常含轮子、夹爪关节，顺序由驱动决定。这台测试本体不是刻意构造的极端情形。
- **修复建议**：
  1. 能力标准给 `arm.joint_position` 加 `joint_names`（或 `joint.state` 加索引映射），套件按名称取值。
  2. 在标准修订前，`joint.state.dof != arm.joint_position.dof` 时把所有用到"当前角"的 dry/motion 用例记为 `blocked`。
  3. 发出零位移目标前连读两次 `joint.state` 并核对长度与名称。
  4. dry 级任何动作都应有"目标与当前读数差 ≤ 1e-6"的前置断言，作为 `_assert_zero` 的关节版。

### P1

#### Q4-03 · P1 · runtime · motion 用例中途出现异常时不停车、不锁存、继续后续运动（已复现）
- **位置**：`conformance.py:579-607`（`_record` 对 `CallError` 与任意 `Exception` 只记 failed，不停止、不中止）。
- **复现**（`midfault.py arm_read_raises`）：`SimArm` 在 0.4 rad 的中断目标开始 0.15 s 后读 `joint.state` 抛异常。
  - 用例记为 failed（`adapter_fault`），套件既没有停止也没有中止，机械臂**走完了 0.4 rad**（最小步长的 8 倍）。
  - 随后套件继续开始夹爪运动用例（均因 `busy` 失败），最终 `final_latched=false`。
  - 对照：`cancel_raises` 中运行时自己退回到了停止，安全。
- **修复建议**：motion 级的 `_record` 遇到 `_Fail` 之外的任何异常（包括 `CallError`），先 `_stop`，再 `_Abort(keep_latched=True)`。dry 级若有运行未结束也应如此。补"读数在动作中失效"的用例。

#### Q4-04 · P1 · runtime · 无 `localization.pose` 时"0.1 m 最小导航目标"按 odom 坐标发到 map 坐标系（已复现）
- **位置**：`conformance.py:1137-1142`（`_current_pose` 退回 `base.odometry`）、`1393-1417`（`_motion_nav_min`）、`1419-1447`（中断用例同样如此）。脚手架 ROS 2 模板发 Nav2 目标在 `map_frame`，里程计在 `/odom`。
- **复现**（`frame_offset.py`）：本体 `simulated:false`，map = odom + (4, 3) m。机器人刚开机时 odom 原点就在开机位置，这种偏移很常见。
  - `min_goal` 的"0.1 m"目标让本体**行驶 4.87 m**（用时 10.5 s），用例 failed 但没有中止；
  - 随后的 cancel/stop 用例照常执行，判为 passed。
  - 真机上 Nav2 会以巡航速度朝远处目标行驶，最长到 `action_timeout_s=30 s`。

  README 只把这一点写成"假定 odom≈map"，没有说明其危险。
- **修复建议**：未声明 `localization.pose` 时，导航 motion 用例一律 `blocked`（"无地图坐标系位姿，无法计算安全的最小目标"）；或者在 `base.navigate_to` 参数里声明目标坐标系并核对。motion 级的"未静止/偏差过大"应中止并锁存，不能只记 failed 后继续。

#### Q4-05 · P1 · runtime · 倍速 k 取自适配器时钟或 `/v1/status`，真机也会把导航中断目标放大到 10 m（已复现）
- **位置**：`conformance.py:890`（`self.k = max(1.0, self.target.time_scale())`）、`355-357`、`512-514`（HTTP 取 `/v1/status.adapter.time_scale`，这是适配器 `status()` 返回的厂商字典）、`1426`（`distance = min(0.5 * self.k, 10.0)`）。
- **复现**（`liars.py fake_time_scale_real_body`）：`simulated:false` 的本体时钟 `time_scale=20`。报告 `time_scale: 20.0`、`simulated: false`，导航中断用例发出 **+10.1 m 与 −9.9 m** 的目标，`motion_ok=true`。真机适配器的 `status()` 里只要有一个叫 `time_scale` 的厂商字段（或时钟配置错），就会发生。
- **修复建议**：只有 `simulated:true` 时才使用 k>1；`simulated:false` 时 k 固定为 1，并在 `time_scale≠1` 时把 motion 级整体 `blocked`。导航中断距离设绝对上限（如 0.5 m），倍速只用于缩短等待。

#### Q4-06 · P1 · runtime · 底盘速度单位或方向错误仍通过 motion（已复现）
- **位置**：`conformance.py:1355-1387`（watchdog/stop 只检查"动了"与"停了"，不比较实际速度、位移与指令）。
- **复现**（`liars.py`）：
  - `velocity_x5`：实际速度为指令的 5 倍（0.1 → 0.6 m/s 实测，常见的 cm/dm 单位错），`motion_ok=true`；
  - `velocity_reversed`：vx 方向相反，`motion_ok=true`。

  这正是新适配器最常见的缺陷，也是现场最危险的一类。
- **修复建议**：watchdog 用例记录 `distance_m`、峰值速度与位移方向，要求速度在指令的 ±50 % 内、位移方向与 vx 同号（在机体系计算），否则 failed 并锁存；`base.velocity` 的 motion 结论依赖这一项。导航 `min_goal` 同样核对位移方向。

#### Q4-07 · P1 · runtime · 取消、停止、复位后只验证"瞬时静止"，延迟恢复和复位重放旧指令都能通过（已复现）
- **位置**：`conformance.py:1328-1340`、`1419-1447`、`1500-1540`（静止判定只在 ≤2 s 窗口内取首次满足）、`628-638`（复位后不验证仍静止）、`890-903`（套件结束时不验证静止）。
- **复现**（`liars.py`）：
  - `nav_cancel_resume`：取消后 1.3 s 目标悄悄恢复，`motion_ok=true`；
  - `arm_cancel_resume`：同上，`motion_ok=true`；
  - `reset_resumes_velocity`：`reset()` 重放最后一个非零速度（有的厂商驱动会在解锁后恢复上一条指令），`motion_ok=true`。**套件结束后本体仍以 0.1 m/s 行驶**（结束后 1 s 内实测再走 0.118 m），运行时看门狗未武装，因为这条指令不经过运行时。
- **修复建议**：
  1. 每次取消、停止后要求在 `still_hold_s`（如 2 s，按 k 换算）内持续静止。
  2. 每次 `_ensure_unlatched`/`_release_latch` 之后验证 1 s 内静止。
  3. 套件结束前做一次最终静止检查，未静止则停止、锁存并判 failed。

**测试痕迹**（#8 的补充）：适配器可以轻易识别"正在被测"，识别方式有：

- 调用栈；
- 临时状态目录前缀 `nx-conformance-`；
- 停止原因 `conformance:<id>:…`，在 server 模式下可从事件读到；
- 请求 ID 前缀 `conformance-`；
- 事件 `conformance.started`。

完全消除痕迹不现实，但至少不应把这些信息暴露给适配器可观察的接口。根本的办法仍是现场人工验收：报告里 `field_acceptance:false` 的声明是对的，应在免责声明中点出"适配器可识别测试并在测试中表现不同"。

**dry 级调用审计**（`dry_audit.py`，记录所有到达适配器的调用）：

- `SimQuadruped` 的 10 次调用、`SimArm` 的 8 次调用，只有零速度、`stop`、`reset`，以及"目标 = 真实当前关节角"；
- 夹爪、导航、姿态在 dry 级都没有到达适配器（非法目标被安全监督器拒绝）；
- 唯一的缺陷是 #21（Q4-02）。

**测试过程安全的其他结论**：

- `kill -9` 后重启默认锁存（`kill_mid.sh`）；
- 适配器 `cancel()` 抛异常时是安全的；
- 中途有人按停止时**不安全**（Q4-01）；
- 中途异常时**不安全**（Q4-03）；
- 并发客户端可以运动（Q4-15）。
