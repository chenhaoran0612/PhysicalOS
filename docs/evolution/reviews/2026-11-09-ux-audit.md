# 用户路径审查（ux02，第 05 轮）

> 本轮主题（创始人）：「很多场景完全没有站在用户的需求来设计，需要一个个解决」。
> 方法：v0.11.0 全新启动（`python -m brainos.server --port <空闲端口> --state-dir <临时目录>`，云平台地址指向无服务端口），
> 以**第一次使用、刚添加了一台仿真四足**的用户身份，用 Playwright 逐页走完左侧导航全部 15 页（任务要求的 12 页 + 自有服务、平台模型与算力、用量与账单），
> 1440×900 截图；再逐个点击每页的主要按钮、提交表单，并走通「仿真四足 → 技能 → 应用 → 检查 → 现场测试 → 发布」整条路径。
> 截图与原始记录在桌面 Agent 的临时目录（`final/before/`、`final/after/`），不入库。

## 总体结论

1. **仿真机器人是新用户唯一能动手的东西，但大部分页面不认识它。**「仿真试运行」页说“还没有可用的仿真服务”；「验证与测试」「部署与运行」不提前说明仿真不能做现场证据，用户走到发布才看到一句技术性拒绝，像故障。
2. **死胡同多。** 工程助手所有按钮都跳到一个没有解释的“选择工程模型”；「机器人应用」要求手填“执行端技能标识”“需要的设备能力”，看不到机器人上已经装好的技能；多个空状态只有一句话、没有下一步。
3. **技术错误原样抛给用户。** 例如仿真应用做现场测试得到「设备端未通过应用执行前检查」（不说哪一项），发布得到「…（本体能力清单声明 simulated=true（仿真本体））」。
4. **术语**：Harness、契约、执行入口、Streamable HTTP、Bearer Token、Responses 协议、版本化引用等，在面向新用户的位置直接出现。
5. **技能运行参数是一个 JSON 文本框**，新用户不知道能填什么、填错只看到“不是合法 JSON”。

## 逐页记录（新用户视角）

| 页面 | 这页是干什么的 | 新用户现在能做有用的事吗 | 困惑点 / 看起来像故障的地方 |
|---|---|---|---|
| 任务工作台 | 任务进度总览，推荐下一步 | 部分。推荐的“现在做这一步：让助手准备”需要助手模型 | 对只有仿真机器人的用户，推荐去找工程助手（必然被模型挡住），而不是先运行技能；“仿真按需，现场测试有据”是行话 |
| 我的机器人 | 接入机器人（仿真 / SSH / 已有接入程序） | **能**。ux01 后这是最顺的一页 | 1440×900 下侧栏底部“云平台账户”要滚动才看得到（小问题） |
| 工程助手 | 让 AI 助手调查设备、写接入程序与测试 | **不能**。所有入口都跳到“选择工程模型” | 不说为什么需要模型、模型是干什么的；“使用平台付费模型”点进去是“等待运营端上架”（死胡同）；“Responses 工具调用协议”“Harness”看不懂；“还没有工作”的空状态没有按钮 |
| 机器人应用 | 把技能编排成应用 | **不能**。机器人上已装的“巡逻”在这里看不到 | 创建应用 → “先准备机器人和工作技能” → 只能“让助手准备”（被模型挡住）或“登记已有技能”（要填执行端技能标识、设备能力 ID）；应用步骤参数仍是 JSON |
| 仿真试运行 | 在虚拟环境里试运行 | 看起来**不能**：页面只讲外部仿真服务、场景登记，显示“还没有可用的仿真服务” | 用户刚加的仿真机器人完全不出现，像是“仿真机器人不算仿真”；“仿真引擎/场景版本地址”是专业用法 |
| 验证与测试 | 应用检查 + 现场测试 | 有应用后可以做检查 | **不提前说**仿真机器人只能做仿真测试；“静态 Harness”；仿真应用做现场测试时（技能没装到机器人上）只报「设备端未通过应用执行前检查」，看起来像故障；空任务列表没有下一步 |
| 部署与运行 | 发布到设备、启动/停止 | 对仿真机器人**按设计不能**（ADR-011） | 页面不说；用户走完一路，最后被「仿真本体的测试结果不能作为现场证据…（simulated=true）」拒绝，像故障；“暂无设备操作”没有下一步 |
| 模型库 | 选平台模型或接入自有模型 | 目录为空时不能 | “当前分类暂无可用模型”没有按钮；接入模型表单的“推理服务 / 输入契约 / 输出契约”是行话 |
| 训练与改进 | 训练/微调模型 | 新用户通常不需要 | “尚无任务记录：配置执行服务后提交任务…”没有下一步 |
| 训练与测试数据 | 登记数据版本 | 新用户通常不需要；有按钮 | 数据地址要求 s3:// 等，属进阶 |
| 助手工具 | 给助手加工作方法（Skills）和 MCP 工具 | 新用户不需要 | 不说“基本使用不需要配置”；两个空状态没有按钮；Streamable HTTP / Bearer Token / OAuth |
| 自有服务 | 接入自己的模型/训练/仿真服务 | 进阶 | “版本化协议”；有按钮 |
| 平台模型与算力 | 平台资源目录 | 未开通时不能 | “当前分类暂无可用平台服务”没有按钮 |
| 用量与账单 | 额度与用量 | 可以申请额度（只保存申请） | “暂无用量”“暂无额度申请”没有下一步 |
| 云平台账户 | 登录云平台、钱包、模型 | 没有云平台时不能；页面已解释（ux01） | 无明显问题 |

全局：所有点击类错误走 toast、表单错误走 `.form-error`，都直接显示后端原文（含英文网络错误、HTTP 状态码、`simulated=true` 之类）。

## 按设计、但看起来像故障的

- **仿真机器人不能做现场证据、不能发布**（ADR-011）。本轮改为在用户尝试之前说明，并给出能做的事和真机部署需要什么。
- **停止 = 锁存急停**，必须现场确认后“解除急停”才能再运行（ux01 已在实时状态里说明，本轮未改）。
- **“发布成功不表示机器人已经工作”**、**结果未知的操作不自动重试**：文案已有，保留。

## 本轮处理（按对用户的影响排序）

| # | 页面 | 问题 | 处理 |
|---|---|---|---|
| 1 | 验证与测试 / 部署与运行 / 交付清单 | 仿真不能部署像故障 | **已修**：两页顶部在用户尝试前说明「用仿真机器人可以 / 不能 / 要真正部署需要」，按钮：在仿真机器人上运行技能、去仿真试运行、接入真机；交付清单标出“现场测试 / 发布版本：需要真机”，主按钮改为“在仿真机器人上运行技能”，仿真测试改名“做一次仿真测试（不计为现场证据）”；创建应用、应用选择列表提前标出仿真目标；服务器拒绝规则不变 |
| 2 | 仿真试运行 | 不认识用户的仿真机器人 | **已修**：新增“你的仿真机器人”（运行技能 / 实时状态 / 安装技能），说明下方仿真任务属进阶 |
| 3 | 全局 | 技术错误原样显示 | **已修**：白话解释在前，原文放在可折叠的“技术细节”里（toast 与表单都适用）；已是中文白话的错误保持原样 |
| 4 | 验证与测试 | 「设备端未通过应用执行前检查」不说原因 | **已修**：后端带上未通过的检查项（如“步骤 1（patrol）技能已安装：…”），前端解释为“技能还没装到这台机器人上 / 参数不符合”等 |
| 5 | 运行技能 | 参数是 JSON 文本框 | **已修**：按 skill.json 生成表单（类型、默认值、范围、单位、必填；坐标列表可逐行增删），“高级：直接编辑 JSON”可切换且双向同步；填错时说清是哪个参数 |
| 6 | 工程助手 | 无模型时直接卡住 | **已修**：说明助手模型是干什么的，三种获取方式各写“需要什么 / 费用”；未上架的选项显示为不可用而非死胡同；“暂时不想配置”指向仿真机器人 |
| 7 | 机器人应用 | 看不到已装技能，只能手填登记 | **已修**：“使用机器人上已安装的技能”一键加入项目，随后可直接创建应用 |
| 8 | 多页 | 空状态没有下一步 | **已修**：所有页面空状态都有一个具体按钮（浏览器验收逐页检查） |
| 9 | 任务工作台 | 仿真用户被推荐去找工程助手 | **ux03 已修**：只有仿真机器人时推荐“运行技能 / 去仿真试运行”，之后依次“创建机器人应用 → 检查应用 → 在仿真里验证（接入真机）”；不再推荐被模型挡住的“让助手准备” |
| 10 | 机器人应用 | 应用步骤参数仍是 JSON；手动登记技能的表单仍是行话 | **ux03 已修**：项目技能可保存参数声明（加入已装技能时自动带上；手动登记可在“高级”里填 skill.json 的 parameters）；创建应用与“修改为新版本”的步骤用与运行对话框相同的表单（含高级 JSON）；未声明参数的技能保留 JSON 框；登记表单改为白话 |
| 11 | 模型库 / 自有服务 / 助手工具 / 仿真场景 | 进阶表单术语（契约、Streamable HTTP、场景版本地址） | **ux03 已修**：基本字段在前、白话；契约、访问令牌、协议说明、场景文件位置与版本收进“高级”；“高级”里的必填项为空时自动展开 |
| 12 | 全局 | 1440×900 下侧栏底部需滚动 | **ux03 已修**：窗口高度 ≤1000px 时侧栏紧凑排布；1440×900 下“云平台账户”底边在 749px，无隐藏滚动 |

## 安全语义（未改变）

- 运动类操作仍需勾选现场授权（技能运行、现场测试、解除急停）；未授权时浏览器拦截、服务器拒绝。
- 停止仍锁存急停，锁存期间“运行技能”不可用，解除需现场确认。
- 直接运行技能仍只对仿真机器人开放；仿真报告仍不能用于发布（服务器 `require_real_evidence` 未改）。

## 验证

- `tests/ux02_browser.cjs`（使用 `tests/ux01_browser_fixture.py`）：逐页检查空状态都有按钮；仿真说明先于尝试出现；参数表单（类型、默认值、错误值不发送、坐标增删、高级 JSON 双向同步、坏 JSON 白话提示）；授权、停止锁存、解除急停；已装技能加入项目 → 创建应用 → 交付清单 → 仿真测试 → 服务器仍拒绝发布；错误 toast 白话在前、技术细节默认收起。
- `tests/test_ux02.py`：参数声明的提取规则；执行前检查失败时带出失败项；仿真本体仍不能发布。
- 回归：ux01、sim_reset、desktop02、delivery 浏览器验收通过；cloud03、adaptation 浏览器验收在“工程会话产物”一步失败，**在未改动的 v0.11.0 上同样失败**（与本轮无关，见遗留）。

## ux03 补充（同日）

- 参数表单显示中文名：优先 skill.json 参数的 `title` / `description` / `unit`，否则用内置对照（waypoints→航点、loops→圈数、tolerance→到达容差、cycles→次数、amplitude→幅度 …），原始键名作为次要文字；单位显示在输入框旁；出错提示写“圈数（loops）：需要整数”。
- **cloud03、adaptation 的根因是测试环境**：本机没有固定版本的 Codex 0.146.1 运行时（`runtime/bin/codex` 或 `NEUXMIND_TEST_AGENT_BINARY`）。adaptation 夹具因此直接得到“工程引擎未安装”，映射表永远不会出现；cloud03 夹具退回到只重放录制请求、从不执行工具调用的替身，工作区永远没有产物。产品无缺陷：同一套验收在真实 Codex 0.146.1（npm `@openai/codex@0.146.1-linux-x64`）下通过。修复：新增确定性的 app-server 替身 `tests/codex_standin.py`（像 Codex 一样执行 `exec_command`、把动态工具交给产品、上报用量与云端错误），无二进制时两个夹具自动使用它。
- 旧浏览器验收（engineering、discovery、browser_smoke）的失败都是**测试过时**：第 02 轮起会话里的“查看本体档案”是 `inventory-report`、证据是 `inventory-evidence`；应用改由交付清单推进（检查 → 现场测试 → 发布 → 启动）。已按现行界面更新。extensions 验证的是 Codex 自身的 Skill/MCP 加载，替身无法证明，无二进制时明确跳过（有二进制时通过）。旧验收的夹具与脚本都可传入独立的配置路径，不再依赖共享的 /tmp 固定文件。
- 验证：`tests/ux03_browser.cjs`、`tests/test_ux03.py`；全部 14 项浏览器验收 + browser_smoke 在各自独立夹具上通过（替身与真实 Codex 两种运行时）。
