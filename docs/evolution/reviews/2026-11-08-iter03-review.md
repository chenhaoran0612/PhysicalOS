## 总评

本轮整体质量延续第 02 轮，"失败即关闭"的思路贯穿新代码。用攻击脚本实证确认成立的部分：

- **停止从不被安装阻塞**：恶意包服务器做了慢速（每 0.8 s 1 字节）、只发响应头不发正文、重定向环、跨协议重定向、Content-Length 撒谎（偏小、负数、两个不同值）、磁盘满。`/v1/stop` 延迟始终在 7 ms 以内，运行立即进入 `stopped`。所有异常都没有发布未校验的包，`.partial/` 也没有残留。
- **不写出 models 目录**：`model_id`/`name` 用 `../../../etc/passwd` 时只作为元数据记录；按这个目录 ID 删除，删掉的是正确的 sha 目录。URL 路径穿越会被规范成安全文件名。
- **沙箱内只读**（root，3.13 与 3.10）：技能以 uid 65534 运行，对模型根目录和模型目录做 `chmod`、替换模型文件都得到 `PermissionError`，模型摘要不变。`/v1/status` 的 `level/privilege_drop/runtime_user/python_usable` 与技能实际 uid 一致；nxtest 下如实报告 `best-effort` 并给出 2 条原因。
- **cloud 白名单**：命名空间嵌套、合计 129、`function_call_output` 中的图片/文件/嵌套列表/对象/多余键、`encrypted_content` 超过 400k、`include` 重复或写成字符串，全部被拒。`encrypted_content` 的字节确实计入输入上界。客户端在延迟转发的终止事件之前断开时，网关仍按实际 usage 结算：`inflight` 归零，扣费等于会话计量，预留归零。SQLite 与 PG 结果一致。
- **桌面端本地账本**：真实 Codex 下跑了单会话、两个并发云会话、关闭失败三条路径，本地 `commerce.reserve/settle/release` 都没有被调用。两个并发会话的云端钱包扣费 28 点，等于两份会话计量之和，预留归零。

本轮发现 **0 个 P0、1 个 P1、7 个 P2、9 个 P3**。

- **P1（Q3-01）**：遥测库损坏、被换成目录、被其他进程锁住、或预留值异常时，**整个运行时无法启动**，安全监督与停止接口随之不可用。断电损坏 SD 卡上的 SQLite 文件、有人用 `sqlite3` 命令查看遥测，都会触发。第 03 轮之前遥测是纯内存，不可能出现这种失败。
- **P2 主要有两类**：
  - 遥测：写线程失败时整批事件丢弃且不推进 seq 预留，崩溃重启后 seq 被重复使用，违反 §5.2"跨重启连续"和 README 的"绝不再发一次"（Q3-02）；
  - 桌面端：云会话令牌（以及任何模型密钥）被 Codex 写进 `runtime-home/shell_snapshots/*.sh`（0644），会话关闭后仍留在盘上。现有测试"令牌永不落盘"只覆盖了替身，真实 Codex 下不成立（Q3-03）。

**结论：修复 Q3-01 并复验后，可以按 0.10.0 发布，范围仍限仿真本体与受控云端环境（ADR-018 的第三方技能闸门不变）。** Q3-02 与 Q3-03 建议同轮修复，因为它们直接推翻了本轮文档和测试中的明确承诺。若不修，发布说明中必须删去或改写这两条承诺。其余 P2 可进入第 04 轮，但有两个时间约束：

- Q3-05 须在以非 root 方式部署带守护进程的真实适配器之前修复；
- Q3-04 须在桌面端正式分发给用户之前修复（每个会话约 86 MB 磁盘 + 一次 GitHub 下载）。

## 发现列表

严重度：P0 会导致物理危险、资金损失或越权；P1 是功能错误或可被利用；P2 是健壮性问题或契约偏差；P3 是建议。

### P1

#### Q3-01 · P1 · runtime · 遥测库任何异常都会让运行时启动失败（已复现）
- **位置**：`runtime/neuxmind_runtime/core.py:61-62`（`EdgeRuntime.__init__` 无条件调用 `events.persist`）；`runtime/neuxmind_runtime/events.py:66-80`（`connect`、`PRAGMA journal_mode=WAL`、`CREATE TABLE`、读预留值，均无异常处理）。
- **复现**（`attack_telemetry.py corrupt` 与一段内联脚本），state 目录中的 `telemetry.sqlite3` 分别设为以下情况，`EdgeRuntime(...)` 的结果：

| 遥测库状态 | 启动结果 |
|---|---|
| 垃圾字节 | `DatabaseError: file is not a database` |
| 同名目录 | `OperationalError: unable to open database file` |
| `meta.reserved_seq = 2^63-2` | `OverflowError: Python int too large to convert to SQLite INTEGER` |
| 另一个连接持有 `BEGIN EXCLUSIVE`（例如有人在用 `sqlite3` CLI 查看遥测） | 5.0 s 后 `OperationalError: database is locked` |

- **影响**：运行时进程起不来，适配器、安全监督器、`/v1/stop`、急停锁存持久化全部不可用，只能人工登录设备删除文件。遥测是诊断数据，本不该决定机器人能否启动。真机上断电损坏 SQLite 文件是常见故障。另一个后果是不能在设备上安全地"只读查看"遥测库。
- **修复建议**：
  1. `persist()` 失败时降级为纯内存遥测：在 `/v1/status.telemetry` 中报告 `persistent:false` 和原因，并发 `telemetry.persist_failed` 事件。
  2. 打不开或校验不通过的库改名为 `telemetry.sqlite3.corrupt-<ts>` 后重建。
  3. 预留值做范围校验（超过 2^62 视为损坏）。
  4. 连接的 `timeout` 设小（如 0.5 s），启动时被锁就降级，不等待。
  5. 补测试：上述四种状态下运行时都能启动，且 `/v1/stop` 可用。

### P2

#### Q3-02 · P2 · runtime · 写入失败时整批事件丢弃且不推进预留，崩溃后 seq 被复用（已复现）
- **位置**：`runtime/neuxmind_runtime/events.py:111-137`（`flush` 先把 pending 全部 `popleft`；`sqlite3.Error` 时 `write_errors += 1; return 0`，批次既不放回也不推进 `_reserve`）。`RESERVE_AHEAD = 10_000`（L29）。
- **复现**（`attack_telemetry.py stall`）：
  1. 子进程运行时 `persist()` 后，另开一个连接持有 `BEGIN EXCLUSIVE`，在锁存续期间发出 15000 条事件；
  2. 客户端经 `since()` 看到的最大 seq 为 15010，`write_errors=1`；
  3. 子进程 `os._exit(9)` 模拟崩溃；
  4. 下次启动 `first_seq = 10011`，**区间 10011–15010 被重复使用**。库中只有 11 行，那 15000 条事件永久丢失，`/v2/runs/{id}/events` 也回放不到。
- **违反的承诺**：§5.2"跨重启连续"；`runtime/README.md:323`"绝不会把客户端已经见过的 seq 再发一次"；`events.py` 模块文档；SDK `robot.py:284` 的"never repeats"。跨层后果是 `nx telemetry tail` 用的游标会**静默跳过**新进程中 seq ≤ 旧游标的全部事件，其中包括安全事件。
- **修复建议**：
  1. 写入失败时把批次放回 pending 头部（`extendleft(reversed(batch))`），有界丢弃并计数；
  2. 新进程的起点不只看磁盘预留，还要考虑"预留可能没跟上"：例如预留推进失败时，`emit` 侧在 `seq > _reserved` 后发 `telemetry.reservation_lag` 事件；或启动时一律跳过 `RESERVE_AHEAD` 而不是取 `max`；
  3. 补测试：写线程失败期间发出超过 `RESERVE_AHEAD` 条事件，再崩溃，下次的 `first_seq` 大于客户端见过的最大 seq。现有测试无法发现此问题，变异 R5（删除 flush 后的 `_reserve`）存活即是证明。

#### Q3-03 · P2 · desktop · 云会话令牌（及任何模型密钥、MCP 令牌）被真实 Codex 写入 `shell_snapshots`，关闭后仍在盘上（已复现）
- **位置**：`brainos/agent_runtime.py:84`（`env.update(CODEX_HOME=..., NEUXMIND_MODEL_KEY=profile['api_key'])`，MCP 令牌同样以 `NEUXMIND_MCP_n` 进入环境）；`brainos/engineering.py:550`（`CODEX_HOME = <store>/engineering/<sid>/runtime-home`，持久保留）。
- **复现**（`test_review03_desktop.py`、`test_review03_snapshot.py`，真实 Codex 0.146.1 + 真实 cloud 应用）：
  - 一次工程任务完成并 `cloud_settled` 后，扫描桌面数据目录，命中 `engineering/agent-session-…/runtime-home/shell_snapshots/<uuid>.<n>.sh`；
  - 文件 0644、目录 0755，内容为 `declare -x NEUXMIND_MODEL_KEY="<令牌>"`；
  - 会话关闭后仍在。快照、会话记录、错误信息中没有令牌（这几处是好的）；
  - 智能体的 shell 命令看不到该变量（`env | grep -c NEUXMIND_MODEL_KEY` = 0，`inherit = "none"` 生效）。
- **影响**：
  - 存储根是 0700（`brainos/store.py:13`），其他本机用户读不到。
  - 但它推翻了 §5.3 的验收承诺与 `tests/test_cloud_engineering.py` 文档串中的"the access token is never stored"。该测试只在替身 `ReplayAppServer` 下检查，替身不会写快照。

  3. 把 `test_access_token_is_never_stored` 移到 `RealRuntimeThroughCloudTest`，扫描范围包含 `runtime-home`。

#### Q3-05 · P2 · runtime · 非 root 收割者杀掉运行时自己以新会话启动的辅助进程，并"偷走"其退出状态（已复现）
- **位置**：`runtime/neuxmind_runtime/sandbox.py:575-605`（`_reap_round`：同 uid 且会话 ≠ 运行时会话即目标；对 direct 子进程 `_reap_zombies`）。
- **复现**（`reaper_collateral.py`，良性）：
  - 运行时所在进程先用 `subprocess.Popen(["sleep","300"], start_new_session=True)` 模拟适配器守护进程，再启动一个同会话的 `sleep`，然后跑一个立即返回的技能，几秒后：

| 环境 | 新会话辅助进程 | 同会话辅助进程 |
|---|---|---|
| nxtest 3.13 / 3.10（无 cgroup） | **被杀**，`Popen.poll()` 返回 **0** | 存活 |
| root 3.13（有 cgroup） | 存活 | 存活 |

  - 运行时自身始终存活，SIGSTOP 没有落到运行时上。
- **影响**：
  - 进化记录已写明"会被清理"，这一点不是新问题。新的问题是 **退出状态被收割者 `waitpid` 拿走**：适配器看到守护进程"正常退出（0）"，不会报错或重启它，现场表现为 ROS 桥、相机进程等无声消失。
  - 只要发生过一次技能运行，30 s 窗口内的周期扫描都会触发。
  - 非 root 是 §5.0 的正式支持模式。
- **修复建议**：
  1. 只收割"祖先链上曾经是已跟踪技能进程"的后代：在技能子进程启动时记录其会话 ID（技能总在新会话中启动），收割时要求目标的会话 ∈ 已知技能会话集合，而不是"≠ 运行时会话"。setsid 逃逸者会建新会话，这类再配合 `/proc/<pid>/stat` 的 `starttime` 和祖先链判定；
  2. 或把适配器的辅助进程登记为白名单 pid；
  3. 至少不要对非目标 pid 调 `waitpid`。补测试时用真实子进程，不要只用 mock 的 `/proc` 表。

#### Q3-06 · P2 · runtime · 安装没有并发上限，也不对在途同 sha 去重，可占满与状态目录共享的磁盘（已复现）
- **位置**：`runtime/neuxmind_runtime/models.py:423-430`（`start_install` 无上限）、`449-453`（已安装才幂等，在途不去重）。
- **复现**（`attack_models2.py conc`）：8 个同 sha 的安装并发 → 8 次下载，`.partial` 峰值 3.1 MB，是包大小的 6 倍；最终只装 1 份（幂等正确）。按默认上限 2 GiB 计，N 个并发即 N×2 GiB。
- **影响**：
  - 调用方需要授权，但云端 SDK 重试或用户多次点击都能触发；
  - 磁盘满会连带遥测写入失败（触发 Q3-02）以及 Store/急停锁存持久化失败。本轮磁盘满实验（tmpfs 400 KB）中安装本身正确失败并清理。
- **修复建议**：同 sha 的在途安装合并到同一个 handle；全局并发上限（如 2）；开始下载前检查可用空间 ≥ `Content-Length`（或上限）+ 余量。

#### Q3-07 · P2 · cloud ↔ desktop · 1 MB 请求体上限与 Codex 全量历史不兼容，桌面端无对应提示（已复现）
- **位置**：`cloud/neuxmind_cloud/config.py:39`（`max_body_bytes = 1_000_000`）；`brainos/engineering.py:25-39`（`CLOUD_FAILURES` 没有 `payload_too_large`）。
- **复现**（`test_review03_cloud.py`，SQLite 与 PG）：录制的 Codex 请求加上 45 个 24 KB 的工具输出（共 1.14 MB）→ 413 `payload_too_large`。Codex 在 `store=false` 下每次都发送完整历史，`tool_output_token_limit=6000`，长工程会话会在上下文压缩之前越过 1 MB。
- **影响**：长任务在中途失败，用户只看到原始错误。另外上界按"字节即 token"计算，1 MB 请求单次就预留约 100 万 token，桌面端的预算上限也是 100 万。§5.3 的"预算下限 80000"只保证第一轮可用。
- **修复建议**：网关会话路由单独设置更高的体积上限（例如 8 MB，仍受预留约束）；桌面端映射 413，提示"会话历史过长，请开新会话"；在 `ENGINEERING_ENGINE.md` 中写明长会话的预算与体积关系。

#### Q3-08 · P2 · runtime · 遥测库被锁时 `/v1/status` 阻塞约 5 s（已复现）
- **位置**：`events.py:128-133`（写线程在 `_db_lock` 内执行 `executemany/commit`，SQLite busy 等待默认 5 s）；`events.py:198-210`（`describe → retention → _db_rows` 获取同一把锁）；`core.py:236`。
- **复现**（`attack_telemetry.py status_block`）：外部连接持有排他锁时，`/v1/status` 耗时 4.81 s，`/v1/stop` 耗时 0.099 s（停止路径不受影响），`emit` 耗时 < 0.1 ms。
- **影响**：桌面端健康轮询与 SDK `latest_seq()` 卡顿，同时占用普通连接名额。停止路径不受影响，因此不升级。
- **修复建议**：连接 `timeout` 设小；`describe()` 不读库（`oldest_seq` 由写线程缓存）；读路径用独立的只读连接，不和写线程共用锁。

### P3

#### Q3-09 · P3 · runtime · https 到内网/链路本地/元数据地址不拒绝；SHA 错误信息是摘要预言机（已复现）
- **位置**：`models.py:360-363`（https 只检查有主机名）；`models.py:155-161`（同协议重定向逐跳只做 `check_url`）；`models.py:460`（错误信息含"实际 {digest}"）。
- **复现**（`attack_models.py https_internal error_oracle`，自签 CA 经 `ca_file` 信任）：
  - 直连 `https://169.254.169.254/...` 与 `https://10.255.255.1/` 被接受并实际发起连接（本环境经代理失败）；
  - 公网 https 重定向到 `https://127.0.0.2:<port>/secret`，内部服务收到 1 次请求，错误信息返回该资源的 SHA-256；
  - `file://` 配置目录内一个 0600 文件：先用错误 sha 取得真实摘要，再用正确 sha 安装，文件以 **0444** 发布到 `models/<sha>/`；
  - 技能声明 `model.install` 后可以在沙箱内自己调用（root 与 nxtest 下实测 `ctx.call("model.install")` 均可执行），因此能读到它原本读不到的文件。
- **评估**：
  - 在当前信任模型下增益很小：包地址只有运营员能上架（`catalog.py:155-159`），技能本身也没有网络隔离（ADR-017）。
  - 但第 05 轮补上技能网络隔离后，`model.install` 会变成技能的网络出口和"读 root 文件"通道。https 到内网是否应拒绝：**应当默认拒绝**，与桌面端 Q2-10 的地址策略一致（私网/共享/链路本地默认拒、元数据地址始终拒，配置开关放行私有镜像，并在连接时校验解析结果以防 DNS 重绑定）。
- **修复建议**：采用上述地址策略；错误信息不返回实际摘要（只写入运行时日志）；发布的模型文件不比源文件更宽松（或要求 `file_roots` 中的文件本身可公开读）；技能能否调用 `model.install` 应由显式策略决定（建议默认禁止）。

#### Q3-10 · P3 · runtime · 下载没有总时限；只发头部的服务器使安装线程在停止后继续存活（已复现）
- **位置**：`models.py:78`（只有逐操作的 `timeout_s`）；`models.py:505`（套接字只在 `opener.open` 返回后才挂到 `cancel()`）。
- **复现**：
  - 每 0.8 s 发 1 字节（`timeout_s=1`）：12 s 后仍是 `running`，只受 `model.install` 的 1800 s 运行超时约束；
  - 只发头部不结束：停止后运行立即 `stopped`（正确），但 `nx-model-install` 线程仍存活，要到 http.client 读满 100 个头部才退出（约 80 s）。
- **修复建议**：增加下载总时限与最低速率；在连接建立后立即登记套接字（自定义 `HTTPSConnection.connect`），使 `cancel()` 能中断握手和读头阶段。

#### Q3-11 · P3 · runtime · `model.install` 的 1800 s 超时按机器人时钟计，仿真倍速下被压缩（已复现）
- **位置**：`runner.py:61`、`runner.py:299`（`run.deadline = clock.now() + timeout`）。
- **复现**：`SimQuadruped(time_scale=3600)` 下，一个正常的 512 KB 慢速下载在墙钟 0.55 s 时报"运行超时"。测试常用倍速 20 时，上限只有 90 s。
- **修复建议**：非运动能力（`safety=system`）用墙钟截止时间。

#### Q3-12 · P3 · runtime · 输入校验的小缺口
- `SHA_RE = ^[0-9a-f]{64}$`（`models.py:59`）用的是 `match`，`$` 允许结尾带换行：`sha + "\n"` 会通过 precheck，然后注定校验失败，错误信息里带出换行。应改为 `fullmatch`。
- `name`/`model_id` 只拒绝 `ord<32`（`models.py:413`）：DEL（0x7f）、C1 控制字符和双向覆盖符 U+202E 都能存储（实测 `"x‮gnp.exe\x7f"` 被原样列出），在桌面端/CLI 列表中可用于伪装显示。
- 两个不同的 `Content-Length` 头被接受（按第一个处理）。因为有 SHA 校验所以无害，记录备查。

#### Q3-13 · P3 · runtime · 非 `ModelInstallError` 的失败（磁盘满等）没有 `model.install_failed` 事件（已复现）
- **位置**：`models.py:464-466` 只在 `ModelInstallError` 时发失败事件。
- **复现**：tmpfs 磁盘满时，运行错误为 `OSError: [Errno 28]`，该运行的事件只有 `run.started / model.install_started / run.finished`。§5.1 要求"可回放失败原因"。
- **修复建议**：`_install` 中 `except Exception` 也发失败事件；把 `OSError` 映射为可读的中文原因。

#### Q3-14 · P3 · runtime · 非 root 下技能可替换已安装模型，运行时仍列出旧 sha（已复现，属已声明的尽力而为）
- nxtest（3.13/3.10）下技能可以 `chmod` 模型根目录和模型目录并替换模型文件，替换后摘要不再匹配，`/v2/models` 照旧列出原 sha。进化记录已声明"同用户可 chmod 模型"。
- 建议：在 `ctx.models`/推理加载时按大小与 mtime（或抽样摘要）复核，不一致则标记为 `invalid` 并在 `/v1/status` 中报告。

#### Q3-15 · P3 · cloud · 客户端不带 `prompt_cache_key` 时网关不注入组织键（已复现）
- **位置**：`gateway.py:345-346` 只在 `outbound` 已有该键时改写。
- **复现**：去掉该字段的 Codex 请求，上游收到的请求体中没有 `prompt_cache_key`。供应商的自动前缀缓存仍按单一上游账户共享。
- **评估**：README 表格写的是"租户无法把请求引到别的租户的缓存路由上"，这对"带键"的请求成立；对"不带键"的请求，跨租户的前缀缓存（时延侧信道）依然存在。
- **建议**：始终写入 `scoped_cache_key(org_id, key or "default")`，并把 README 改为准确描述。

#### Q3-16 · P3 · desktop · 工作流把 `cloud_close_failed`/`cloud_close_pending` 当作正常完成
- **位置**：`brainos/workflows.py:197`。
- **问题**：关闭失败时云端计量未知，阶段照样进入验收；与 `reconciliation_required` 的处理不对称。另外变异 B4（去掉对 `cloud_reconciliation_required` 的处理）存活，说明这一分支没有测试。
- **建议**：这两种状态在阶段结果中给出"费用待确认"提示，并补测试。

#### Q3-17 · P3 · runtime · 两个运行时共用一个 state 目录时遥测互相交织，没有互斥锁
- 见 G 节的复现：后启动的运行时 `since(0)` 读到前一个运行时的事件；两者都还活着时，前者的预留推进可能覆盖（`INSERT OR REPLACE`）后者的行。生产中这不该发生，但重启重叠（旧进程未退）时可能出现。
- **建议**：state 目录加 `flock` 独占锁，第二个实例拒绝启动。

## G：两个已知偶发的判定

1. **`runtime test_async_evaluate…test_unfinished_becomes_unknown_and_is_not_replayed` 取遥测 `[0]`：测试缺陷，不是产品缺陷（已复现根因）。**
   - 测试在同一 state 目录上先后创建两个运行时，然后用 `restarted.events.since(0)` 取第一个 `runtime.started`（`test_async_evaluate.py:216`）。
   - 遥测持久化后，`since(0)` 按契约会返回前一次启动的事件。旧运行时的 `runtime.started` 是否已被写线程（0.1 s 周期）落盘，取决于时间。
   - `g_async.py`：重启前等 0 s，结果是 `[10001]`（通过）；等 0.3 s，结果是 `[1, 10001]`，`[0]` 来自上一次启动（失败）。高负载下前半段更慢，所以偶发。
   - 修复：过滤 `e["seq"] >= restarted.events.first_seq`，或断言"存在一个"该事件而不是取 `[0]`。
2. **`tests/test_workflows` 高负载 25 s 超时：已复现，根因未确定。**
   - 单独运行（6.4 s、7.6 s）和带计时插桩的单测运行（0.5 s）都通过；
   - 在 2 核机器上并行跑 cloud+runtime+sdk 三套测试时，3 次中 1 次失败：运行停在 `stopping` 超过 25 s，整组用时 67 s；
   - 插桩后的 4 次重跑没有再失败，没能抓到停在哪个 RPC。
   - 可确认的产品侧因素：①`_run` 中的 `thread/start`、`turn/start` 与 `turn/interrupt` 都是同步 RPC（超时 25 s/5 s），停止只能在 RPC 之间被看到，停止延迟没有上界保证；②每个会话都在后台克隆约 25 MB 插件（Q3-04），会加重负载。
   - 判断：以测试时限过紧为主，但停止响应时间缺少产品侧上界（P3，建议 RPC 等待也检查停止事件）。第 04 轮应带插桩复现。
