### 2.1 Q6-01 守护在真实噪声/漂移下误报（P2）

`r7/noise.py`：本体**真实静止**，只有上报的反馈带真实量级的噪声或漂移，锁存 1 小时（机器人时钟）。同一脚本用 `r7/py012.sh` 对照 v0.12.0：

- 影响：只多发 `adapter.stop()`，不发运动、不解锁（安全侧）。但每次都发 `safety.motion_while_latched`，文案让操作员“若反复出现请使用硬件急停并检查驱动”；2 次/秒的事件 42 分钟就能冲掉 5000 条内存事件环里的原始停止记录。真正的蠕动告警会淹没在误报里——这正是 Q5-01/02 想解决的问题的反面。
- 现场无法标定：`GuardConfig` 只能经 `EdgeRuntime(latch_guard=…)` 设置，`serve` 没有参数，适配器只能声明 `stop_settle_s`；`ros2` 适配器（真实 `/odom`）什么也没声明；按代码，`/odom` 超过 `stale_after_s=1.0` 未更新时读取抛错，守护会按“不可读”每 0.5 s 再停并发事件（未在真 ROS 2 上实验）。
- 建议：(1) 适配器/清单可声明守护阈值（与 `stop_settle_s` 同一机制），`serve` 提供覆盖参数；(2) 刹停宽限内估计噪声底，阈值取 max(默认, k·σ)；(3) 累计漂移按“漂移速率”判断（例如 0.05 rad 内的纯偏航慢漂且速度≈0 不计），或至少把慢漂移与运动证据分开上报；(4) 同类事件合并（计数 + 每 N 秒一条），避免冲掉事件环。

| `{"type":"str","min":1,"max":3}` | 接受 | `"zzzzzz"` → 成功 | 原样 |
| `{"type":"pose","min":-1,"max":1}` | 接受 | `[50,0,0,0,0,0,1]` → 成功 | 原样 |
| `{"type":"float","minimum":0.1,"maximum":0.5}` | 接受 | `9.0` → 成功 | `9.0` |

- `check_parameter_declarations` 的文档写“拒绝无法执行的约束（fail closed）”，但只校验 `min`/`max` 是有限数，不看类型；`_check_one` 只对标量数值和 `vector`/`floats` 逐元素检查。航点这类“对象里的坐标”是最可能被作者写上范围的地方。
- `brainos/robot_caps.parameter_view` 把 `minimum`/`maximum` 映射成 `min`/`max`：表单显示“范围 0.1 – 0.5”并在发送前拒绝 9.0，作者和用户都以为生效；设备不认这两个键。这正是 Q5-05 的同一类问题（“只有表单在管”）。
- 设备端监督器的限速/工作区仍然兜底，所以不是运动安全缺口；但技能作者写在 skill.json 里的安全相关上限会被静默忽略。
- 建议：非数值类型（`object`/`str`/`pose`/`bool`/`enum`/`blob_ref`）上出现 `min`/`max`，安装时 400 `param_declaration_invalid`（或对 `object` 做逐数值检查并在契约写明）；`minimum`/`maximum` 要么运行时同样执行，要么桌面不再映射并在安装预览提示“设备不执行此约束”。

### 2.3 Q6-03 迟到的复位在“保持锁存”之后自行解除锁存（P2）

- 运行时（`r7/hung500.py`）：`adapter.reset()` 卡 2.5 s 后返回 → `{"latched": false}`；`reset_grace_s` 调成 1 s、本体静止时同样解除（守护只在“看到运动”时干预）。复位返回多晚都会生效，没有上限。
- 桌面（`r7/restart.py`）：重启后复位再次卡住 → 记录 `unknown / reset_in_progress`，文案“…一直没有完成；急停仍然锁存”；驱动放开后 1 s，`robot_live` 显示**未锁存**——期间没有任何人再次确认。
- 浏览器（ux04 截图 `10-reset-hangs.png`）：标题“解除急停的结果还不确定”，正文却是“所以这次复位被拒绝了。急停保持锁存，机器人不会运动”，按钮“再试一次解除急停”。对于仍在机器人上执行的那次复位，“被拒绝”“不会运动”都不对（运行时自己的提示是“复位正在执行（例如机器人正在起立）”）。
- 风险：操作员看到“保持锁存、不会运动”后离开或走近本体检查；几分钟后驱动返回，锁存解除，本体可能正好完成起立。解除锁存本身不发运动指令，后续运动仍需授权，所以定 P2 而非 P1。
- 建议：(1) 运行时给复位设过期：`adapter.reset()` 超过某个时限（例如 `reset_grace_s` 或新参数）才返回时保持锁存、发 `safety.reset_expired`，要求重新授权；(2) 桌面对 `unknown + reset_in_progress` 改说“复位仍在机器人上进行，完成后急停会解除；不想让它继续，请按‘停止’（会取消这次复位并保持锁存）”，并在对话框里直接给“停止”按钮——实验已确认（`r7/stopreset.py`）复位卡住时按停止，复位返回后为 409 `estop_latched`、`cause: stop_during_reset`，锁存保持；(3) `uxResetOutcome` 的 `rejected` 与 `unknown` 分开措辞。

### 2.4 Q6-04 “总位移有界”表述不实，缺少升级（P3）

§8 写“之后每再动 3 mm / 0.005 rad 再停一次（总位移有界）”。实测停后 2 s 恢复的驱动：600 s 1.00–1.08 m、再停 262–271 次，位移随时间线性增长（每轮约 4 mm）；完全不服从的驱动 9–11 m（守护只能再停，属固有上限）。建议改为“每次再停之间的位移有界”，并在“锁存期间 N 分钟内再停超过 M 次”时进入升级状态（`latched_motion.escalated`、桌面红色横幅“驱动不服从停止：立即使用硬件急停/断电”），与普通单次告警区分。

### 2.5 Q6-05 未声明 `stop_settle_s` 的受控坐下（P3，Q5-06 延续）

`r7/sit60.py`，同脚本对照 v0.12.0（`SitOnStop`：停止 = 0.8 rad 平滑坐下，“重规划”型驱动每次 `stop()` 从当前位置重新开始）：

| 坐下时长 / 驱动 | v0.12.0 再停（最后一次时刻） | 本轮再停（最后一次时刻） | 60 s 后剩余 |
|---|---|---|---|
| 2 s / 不重规划 | 2（1.7 s） | 3（2.2 s） | 0 |
| 2 s / 重规划 | 6（3.7 s） | **13（8.5 s）** | 0 |
| 3 s / 不重规划 | 4（2.7 s） | 5（3.2 s） | 0 |
| 3 s / 重规划 | 8（4.9 s） | **20（14.5 s）** | 0 |

最终都坐完，属安全侧；声明 `stop_settle_s` 后为 0（§1 表）。但现成的 `ros2` 适配器没有声明、`serve` 也不能设，真机首次接入会先看到十几条“锁存后仍在运动”。建议脚手架/ros2 适配器给出 `stop_settle_s` 配置项，并在一致性报告里提示“停止是否为受控动作”。

### 2.6 Q6-06 枚举/choices 比较宽松（P3）

`choices: [1, 2]` 的 `enum` 接受 `true` 和 `1.0`（Python `True == 1`）；`object` 的 `choices: [0, 1]` 接受 `false`。技能拿到的是 `True` 而不是 1。建议比较时同时比类型（排除 bool 与数值互等）。

### 2.7 Q6-07 `options` 对象在桌面显示为 Python 字面量（P3）

运行时支持 `options: [{"value": "slow", "label": "慢"}]`；`parameter_view` 对每项 `str(c)`，下拉框显示并提交 `"{'value': 'slow', 'label': '慢'}"`，设备以 `param_choice` 拒绝。建议显示 `label`、提交 `value`。

### 2.8 Q6-08 分类/字段的细节（P3）

- `param_type`（例如 `loops: "2"`）与 `param_declaration_invalid`（旧包默认值不合法）都走 `uxIsParamCode` → 显示“有一个参数超出了技能声明的允许范围…按提示把这个参数改到允许范围内”；后者用户改值也没用，应提示“技能包声明有误，请更新或重新安装技能”。
- `PASS_FIELDS` 有 `in_flight_s`，运行时用的是 `reset_in_progress_s`；`hint`、`cause` 都不传。守护导致的复位失败（`cause: latch_guard_reset_grace`）在浏览器只显示通用的“急停处于锁存状态…再点解除急停”，Q5-07 的说明只在“技术细节”里。
- 桌面自身 500 的文字“内部错误，操作未确认”被拼成“对方服务内部出错了。可以稍后重试…：内部错误，操作未确认”，对结果未知的操作不该建议重试。
- `object` 参数 5000 层嵌套 → 运行时 500 `internal_error`（“请求未执行（运行时内部错误：RecursionError）”），应为 400。

### 2.9 Q6-09 仿真运行时停止时 abort（P3）

`r7/restart.py` 中旧进程退出码 -6；`runtime.log` 每次停止/重启都有 `Fatal Python error: _enter_buffered_busy: could not acquire lock for <_io.BufferedReader name='<stdin>'> at interpreter shutdown, possibly due to daemon threads`。锁存已在此前落盘，重启后保留，进程组无遗留，功能不受影响；但日志里出现“Fatal”会误导排障，且可能产生 core 文件。本轮新增的“重启仿真机器人”让它更常见。建议退出前关闭/分离 stdin 读线程，或以 `os._exit` 结束。

### 2.10 其他核对（无问题）

- 守护不发运动指令、不解锁、不改原因、不计入 `stop_count`：所有场景 `motion_cmds = 0`、`stop_count = 1`。
- CPU：驱动 `stop()` 抛异常时 10 s 再停 18 次、CPU 0.054 s；静止锁存 10 s CPU 0.046 s。读取阻塞 10 次 `close()` 最长 1.01 s，遗留线程在读返回后全部退出；关闭后适配器调用 0 次。
- `stop_settle_s` 滥用：非数、bool、NaN 按 1 s；60 s 限到 5 s；只能由适配器代码设置，网络不可改。
- 操作员在说谎驱动运动中连续复位 10 次均成功（授权，预期行为），锁存期间运动指令 0。
- 复位卡住时 40 次重试全 409、线程不增长，期间 `/v2/stop` 5 ms 返回。
- 进程内 `close()` 之后卡住的复位才返回会抛 `sqlite3.ProgrammingError`（500）——只在测试里把运行时对象关闭而进程继续时出现；真实“重启运行时”进程已退出，不单列。

## 3. 桌面字段名与运行时 400 正文

运行时：`{error, code, param, min, max, choices, message, field, problem, constraint, value, step?}`。桌面 `refusal_fields` 透传 `param, field, min, max, choices, value`（`None` 丢弃），浏览器 `uxRefusedParam` 依次读 `param/parameter/field`，`range` 读 `min/max`，`choices` 读 `choices/options`——一致（§1.5 端到端实测）。未透传：`constraint`（长度类错误时字段旁只能说“机器人不接受这个值”）、`step`（应用步骤序号）、`problem`；复位类见 Q6-08。
