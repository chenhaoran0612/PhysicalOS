## 总评

第 02 轮的质量明显高于第 01 轮，多数新代码是带着"失败即关闭"的思路写的：

- **停止不变式在沙箱下依然成立**（代码推理 + 现有测试）。停止路径对子进程只做 `notify_stop()`：置标志，非阻塞地尝试获取 `_signal_lock`，然后 `kill(SIGTERM)`。它不等待子进程，也不碰管道。子进程的每个请求都在运行线程上用真正的 `SkillContext` 服务，运动类调用在下发到适配器前的最后一刻还会经过 `_pre_dispatch` 的守卫和 `ensure_epoch`。子进程不读回复时，运行线程最多在 `sendall` 里阻塞 5 s，被阻塞的是运行线程，不是停止路径或看门狗。进程退出后，`_require_alive` 守卫会让在途请求作废。
- **异步现场测试**有以下保证：结果只写一次（锁不被停止路径持有）；停止后第一次轮询就是 `completed/passed:false`；重启时 `running` → `unknown` 且不重放；"POST 即完成"按契约实现。
- **cloud 流式**有以下保证：预留和结算是两个短事务，流式期间不持有钱包锁；N-05 的判定在钱包锁内（`inflight_tokens > 0`，hold 恒 ≥ 1），SQLite 和 PG 两套全过；有界通道带反压；客户端断开后会继续排空上游，按实际 usage 精确结算。
- **桌面端**：技能包读取用父目录 fd + `O_NOFOLLOW` + `fstat`，读取有长度上限；安装前重读并比对摘要。云凭据目录 700、文件 600，原子写，令牌绑定签发地址，不进快照也不进前端。新前端文件的所有外部文本都经过 `h()` 转义（`h()` 转义 `& < > " '`，属性值位置也安全），`toast` 用 `textContent`。浏览器验收 0 异常。

本轮发现 **0 个 P0、1 个 P1、3 个 P2、6 个 P3**。

- 唯一的 P1：以 root 运行的运行时启动时会清理共享 `/tmp` 下"已死运行时"的沙箱目录，清理代码跟随符号链接。技能用户能在 `/tmp` 里放东西，所以技能能诱使 root 运行时在下次启动时递归修改 `/tmp` 之外的目录权限（Q2-01）。
- P2 集中在流式计量的边界（截止时间可被保活注释绕过；上游事件名和 CR 未规范化，导致 SDK 误认终止事件），以及沙箱在没有可写 pids cgroup 的部署上会失去"进程树全收回"的保证。

**结论：修复 Q2-01 并复验后，可以按 0.9.0 发布（仍限仿真本体与受控云端环境）。** P2 可以进入第 03 轮，但有两个时间约束：

### P1

#### Q2-01 · P1 · runtime · root 运行时启动清理 `/tmp` 时跟随符号链接，可被技能诱导递归修改任意目录权限（代码推理）
- **位置**：
  - `runtime/neuxmind_runtime/sandbox.py:320-322`（`parent = Path(config.workspace_root or tempfile.gettempdir())`；`_sweep_dead_workspaces(parent)`）；
  - `sandbox.py:363-372`（`parent.glob("nx-sandbox-*-*")`，`path.is_dir()` 跟随符号链接）；
  - `sandbox.py:353-360`（`_remove_tree`：`os.walk(path)` 后对每个目录 `os.chmod(dirpath, 0o700)`，再 `shutil.rmtree`）；
  - `runtime/neuxmind_runtime/cli.py:27`（CLI 从不设置 `workspace_root`，默认就是系统 `/tmp`）。
- **问题**：
  1. ADR-017 推荐生产环境以 root 启动运行时，技能降权为 `neuxmind-skill`/`nobody`。技能进程的私有 `TMPDIR` 在工作区内，但系统 `/tmp` 对它照样可写。
  2. 运行时每次启动时，会以 root 身份遍历 `/tmp/nx-sandbox-*-*`，名字里的 PID 不存在就当作遗留目录删除。
  3. 判断时用的是 `path.is_dir()`（跟随符号链接）。删除时先 `os.walk(path)`：`os.walk` 对顶层符号链接会进入其目标，对目标下的真实子目录继续递归，并对遍历到的每个目录执行 `chmod 0o700`。之后 `shutil.rmtree` 因为路径是符号链接而报错，但 `ignore_errors=True` 把这个错误吞掉了。
  4. 净效果：任何技能都能在运行期间留下一个名字合规、指向任意目录的符号链接。运行时下次启动（重启、升级、断电恢复）时，会以 root 把该目录树下的所有目录改成 0700，并清除其 setgid/sticky 位。指向 `/usr`、`/etc` 或运行时自己的状态目录时，本机上非 root 的服务全部失效，严重时整机不可用。这台机器同时承载安全监督和看门狗。
  5. 名字中的 PID 只要选一个不存在的数字即可满足"已死"判定。
- **复现思路**（未执行，留给第 03 轮做回归测试）：
  - 以 root 运行测试，并把 `workspace_root` 设为一个共享的、可被非 root 用户写入的临时目录；
  - 在其中放一个名为 `nx-sandbox-<不存在的PID>-x`、指向另一个临时测试目录的符号链接，测试目录下建几层 0755 子目录；
  - 构造 `Sandboxes(SandboxConfig(workspace_root=...))`，断言测试目录下各子目录的权限没有变化。当前代码下该断言应失败。
- **修复建议**：
  1. 沙箱根目录不要放在共享 `/tmp`。默认放进运行时自己的 0700 状态目录（如 `<state>/sandbox/`），技能用户通过 0711 只能穿越、不能创建。
  2. 清理时用 `os.lstat`：跳过符号链接、非目录、属主不是运行时 uid 的条目；只清理运行时自己创建的目录。
  3. `_remove_tree` 不要对顶层用 `os.walk`。改为先 `lstat` 确认顶层不是链接，再用基于 fd 的遍历（`os.fwalk(top, follow_symlinks=False)` 或 `O_NOFOLLOW|O_DIRECTORY` 逐级打开）做 `fchmod`。
  4. 补测试：顶层符号链接、属主不对的目录、名字合规但不是本运行时创建的目录，都不被修改。

### P2

#### Q2-02 · P2 · cloud · 流式最长时长只在"产出事件"时检查，上游只发保活注释即可越过 `stream_max_seconds`（已复现）
- **位置**：`cloud/neuxmind_cloud/streaming.py:315-318`（截止检查在 `for ev in parse_sse(...)` 的循环体里）、`streaming.py:95-96`（`parse_sse` 对注释行 `continue`，不产出事件）、`streaming.py:90-93`（没有 data 的空行也不产出）。
- **问题**：
  - `effective_stream_max_seconds` 的设计目的，是保证流在清理任务的"丢失判定"（`stale_call_seconds`）之前结束（cloud 进化记录）。
  - 但截止检查只在拿到完整事件后执行。上游（或中间代理）只要每隔不到 `upstream_timeout_seconds` 发一行 `: keepalive`，`parse_sse` 就一直在内部消费、不产出事件，截止检查永远不会运行，`read1()` 的套接字超时也永远不会触发。于是流可以无限期打开，越过 `stale_call_seconds`：清理任务把调用判为丢失，生产线程却还在转发。
  - 计费仍有 hold 兜底，所以不是资金问题。但这会让会话一直 `session_busy`、占住一个生产线程和上游连接，并且让 `call_marked_lost` 与结算发生竞争。SSE 保活注释在真实网关和代理上很常见。
- **复现**（`scratchpad/review02/cloud_deadline.py`：替身上游先连续 3 s 每 0.1 s 发一行 `: keepalive`，再发一个带 usage 的事件；`max_seconds=0.5`）：
  ```
  elapsed 3.0s (max_seconds=0.5)  termination=deadline
  ```
  截止只在 3.0 s 后第一个真实事件到达时才被发现。如果保活一直持续，流就一直不结束。
- **修复建议**：把截止检查下沉到行级。在 `parse_sse` 或 `UpstreamStream.lines()` 里，每读到一行就检查一次绝对截止时间，或者给上游连接设置随剩余时间递减的读超时。另外再加一个"无输出事件空闲上限"。补测试：只有注释或空行的上游必须在 `max_seconds` 内以 `stream_duration_exceeded` 结束。

#### Q2-03 · P2 · cloud ↔ SDK · 上游事件原样透传了保留事件名和裸 CR，"恰好一个终止事件"在客户端侧不成立（代码推理）
- **位置**：
  - `cloud/neuxmind_cloud/streaming.py:76-79`（`SSEEvent.encode` 保留上游 `event` 名；`data` 只按 `\n` 拆行）；
  - `streaming.py:322`（`chunk = ev.encode()` 直接转发）；
  - `cloud/neuxmind_cloud/upstream.py:142-146`（上游只按 `\n` 切行）、`streaming.py:89`（只剥掉行尾 `\r\n`）；
  - `sdk/neuxmind/gateway.py:346-352`（SDK 把**第一个** `neuxmind.metering` 或 `error` 事件当作终止事件，之后的事件全部忽略）。
- **问题**：
  1. 契约 §4.3 规定网关在最后"恰好发出一个终止事件"，客户端读到连接关闭为止。但网关会把上游的同名事件一并转发：
     - OpenAI Responses API 的流在出错时本身就会发 `event: error`，这是正常行为，不是攻击。网关转发它之后，SDK 把它当作网关的终止错误：这个事件没有 `neuxmind` 计量对象，SDK 会调用 `session._invalidate()`。紧随其后的、网关真正的终止事件（带计量）被丢弃，SDK 也就拿不到本次调用的用量。
     - 异常或被攻破的上游、代理，可以发一个伪造的 `event: neuxmind.metering`，让 SDK 显示伪造的用量和状态。服务端计费不受影响，这里的错误只出现在客户端展示和 SDK 的会话状态上。
  2. data 中的裸 `\r` 会被原样转发。WHATWG 兼容客户端（浏览器 EventSource 等）把单独的 CR 视为换行，因此可以在客户端注入 `event:` 字段。真实模型输出是 JSON，不会含裸 CR，这一条需要异常上游才能触发。NeuxMind SDK 只按 `\n` 切行，不受这一条影响。
  3. 反方向的同类问题：只用 CR 换行的合法 SSE 上游，会被网关当作一整行，最终落到 `usage_missing`（互操作问题）。
- **修复建议**：
  - 网关侧：对上游事件做规范化。保留名（`neuxmind.*`、`error`）改名转发，例如 `upstream.error`，或者整体加前缀；切行时按 WHATWG 规则同时识别 `\r\n`、`\n`、`\r`；`encode` 时对 data 中的 `\r` 同样拆行。
  - SDK 侧：以连接关闭前的**最后一个**终止事件为准，或者只认带 `neuxmind` 计量对象的终止事件。
  - 补测试：上游发 `event: error` 时，SDK 仍能拿到网关的计量。
  - 在契约 §4.3 中写明上游事件名的映射规则。

#### Q2-04 · P2 · runtime · "进程树全收回"依赖可写的 pids cgroup，常见部署上会静默失效（代码推理）
- **位置**：`runtime/neuxmind_runtime/sandbox.py:206-231`（`PidsCgroup.base()` 找不到可写层级时返回 `None`）、`sandbox.py:530-537`（`_killpg` 只杀进程组，有 cgroup 时才额外 `kill_all`）、`sandbox_child.py:383`（PDEATHSIG 只对直接子进程有效，fork 后的后代不继承）；ADR-017 把"rlimit + cgroup pids"列为决策的一部分。
- **问题**：
  - 本机（root、cgroup v1 的 pids 层级可写）上 `base()` 可用，开发者的 `setsid` 逃逸测试就是在 cgroup 生效的条件下通过的。
  - 典型的 Jetson/Ubuntu systemd 部署是 cgroup v2。服务单元没有 `Delegate=yes` 时，运行时对自己所在的 cgroup 没有写权限，`base()` 返回 `None`。这时脱离进程组的后代进程不会被 `killpg` 收回，运行结束或停止后仍会以技能用户身份存活。它们的 CPU 时间受 `RLIMIT_CPU` 限制，但睡眠不耗 CPU。
  - 存活的后代即使继承了协议套接字，请求也会被 `_require_alive`/撤销检查拒绝，所以**不会**让旧代数的运动调用下发，也不会延迟 stop。剩下的风险是：网络未隔离时，这些进程仍可直接驱动经网络/DDS 控制的本体（ADR-017 已列为剩余信任边界）。并且"停止后技能代码已全部终止"这个运维假设不再成立，而 `/v1/status` 只用一个 `pids_cgroup:false` 字段表达这一点。
  - 后代持续占用协议套接字时，运行线程会一直留在服务循环里（直到 `STOP_GRACE_S` 后被 finalize 撤销），属于资源泄漏。
- **修复建议**：
  - 非仿真本体在 `process` 模式下没有 cgroup 时，拒绝启动；或者显式要求 `--allow-no-cgroup`，并在 `runtime.started` 中告警。
  - 发布随包的 systemd 单元（`Delegate=yes`，或者用 `systemd-run --scope` 给每个技能一个 scope）。
  - 在 README 部署章节写清楚这一条件；补一个"无 cgroup 时状态与告警"的测试。

#### Q2-07 · P3 · 桌面端 · 技能文件夹路径的中间符号链接会被跟随，硬链接未检测（代码推理）
- **位置**：`brainos/skill_packages.py:93-104`（只对所选路径本身 `lstat`，`_open_dir(path)` 的 `O_NOFOLLOW` 也只作用于最后一级）、`skill_packages.py:59-70`（不检查 `st_nlink`）。
- **问题**：进化记录写的是"任何符号链接（含所选文件夹本身）一律拒绝"，实际上路径的中间各级仍会被跟随。硬链接进来的文件（例如用户家目录里的其他文件）会被读取并发往机器人。这一条不构成越权，因为读取的都是用户本来就能读的文件，而且预检页会列出所有文件。
- **修复建议**：文档改为"所选文件夹本身及其内部的符号链接一律拒绝"；可选地拒绝 `st_nlink > 1` 的文件，或在预检页提示。

#### Q2-08 · P3 · runtime · 多步应用能用日志挤掉遥测中的安全事件（代码推理）
- **位置**：`runtime/neuxmind_runtime/sandbox.py:102,760-765`（每个技能进程最多 500 条日志/进度事件）、`events.py:15`（`EventBus` 只保留最近 5000 条）。
- **问题**：日志上限按进程计算，而应用的每个步骤都会启动一个新进程，所以 10 个步骤就能写入约 5000 条日志，把 `/v2/telemetry` 窗口里的 `safety.*` 事件挤出去。
- **修复建议**：日志上限按运行（`RunState`）累计；或者把安全事件单独保存在一个不会被挤掉的环形缓冲里。

#### Q2-09 · P3 · 跨层 · `spec/neuxmind_spec.egg-info/` 被提交进了 git（已复现：`git ls-files`）
- **位置**：提交 `223ec96` 及之后；根目录 `.gitignore` 没有 `*.egg-info`（`runtime/.gitignore` 有）。
- **修复建议**：从仓库删除，并在根 `.gitignore` 中加入 `*.egg-info/`、`build/`。

#### Q2-10 · P3 · 桌面端 · 回环 http 例外按主机名 `localhost` 放行（代码推理）
- **位置**：`brainos/cloud_account.py:44-49,62`。
- **问题**：开发时云平台地址设为 `http://localhost:<端口>`。开发服务停止后，同一端口上的任何本机进程都会以明文收到会话令牌。
- **修复建议**：http 只允许字面量回环 IP；或者在界面上明确提示"仅限本机开发"，并在每次切换地址时重新登录。

## 文档不一致

1. **ADR-017** 把"rlimit + cgroup pids"写成决策内容，但代码里 cgroup 是"尽力而为"，没有它也会静默运行（Q2-04）。应写明部署前提，或者在代码里强制。
