# 第 01 轮独立审查报告（runtime/ 与 cloud/）

- 审查对象：提交 `3ccd890` 时的 `runtime/`、`cloud/`，以及它们和 `spec/`、`brainos/service.py` 之间的交互。`sdk/` 不在本次范围。
- 方法：逐文件读代码；每个疑点都写临时脚本，在仿真本体、自制替身适配器或 FastAPI TestClient 上实际跑一遍；对 24 处关键产品代码做了"改坏再跑测试"的抽查（改完都已恢复）。
- 基线测试（审查开始和结束时各跑一次，结果相同）：`runtime/tests` 71 个通过；`cloud/tests` 73 个通过；`tests` 72 个通过（20 个跳过，原因是缺少打包的运行时或 agent 二进制）；`spec/tests` 7 个通过。
- 产品代码零改动：审查结束时 `git status` 里只有 SDK Agent 的 `sdk/`（未跟踪），`git diff` 为空。
- 临时脚本都在仓库外（审查 Agent 的 scratchpad `review/` 目录），没有留在仓库里：`rt_limits.py`、`rt_stale_after_reset.py`、`rt_slowloris.py`、`rt_stop_locks.py`、`rt_watchdog_store.py`、`rt_misc.py`、`cloud_checks.py`、`cloud_concurrency.py`、`mutate.py`。

## 总评

两个模块的骨架是认真做的，多数不变式都有代码和测试支撑：

- runtime 的 HTTP 停止路径确实不碰账本、数据库、运行锁和队列。实测把 store、ledger、runner、skills、velocity 和仿真适配器的锁全部在其他线程占住，`/v2/stop` 和 `/v1/stop` 仍在 5–7 ms 内返回并锁存。
- cloud 的账本在 SQLite 上没有超卖、没有双扣。实测 30 个线程并发预留，只成功 10 个；settle 和 release 并发竞争时只有一个生效；布尔、小数、负数、超大和字符串金额都被拒绝。
- webhook 的验签、过期检查、去重和金额核对都有效，变异测试也都能杀掉。

但这次发现了两类开发 Agent 自己没有报告的严重问题：

1. **cloud 有两个可直接利用的 P0。**
   - 平台运营员按"邮箱白名单"认定，而注册没有邮箱验证。谁先注册白名单里的邮箱，谁就成了运营员，可以给自己任意加额度。
   - 网关会话把客户端的任意参数（如 `n`、`max_completion_tokens`）原样转给上游。超出预算的输出照样返回给用户，结算却转人工核对、不扣费。实测预算 1000 token 的会话用掉了 45 070 token，扣费为 0。
2. **runtime 的安全监督器信任清单参数，"急停锁存"不能阻止已在途的旧调用。**
   - 清单里的限幅参数为负数或 NaN 时，限幅器会把指令放大成反向满速，或者把 NaN 直接下发。
   - 关节限位列表比自由度短时，多出的关节不检查。
   - 读不到 `joint.state` 时，动作块的单步速度限制被静默跳过。
   - 被停止并撤销的技能，如果有一次调用在途，现场 reset 之后它仍能把运动指令送到本体。
   - HTTP 网关没有连接超时和线程上限。未认证的空闲连接能一直占住线程，最终让 stop 请求无法被服务。

另外，测试有明显的盲区：24 个变异里 4 个没有被任何测试发现，其中一个是"锁存时拒绝运动"这条主检查。`test_v1_compat` 还把"仿真结果当现场证据走完部署和启动"写成了预期成功的流程。

结论：第 01 轮的协议和仿真层面可以继续推进，但**本轮代码不应接真机，也不应对公网开放云端**，至少要先修完本报告的 P0 和 P1。

## 发现列表

严重度：P0 会导致物理危险、资金损失或越权；P1 是功能错误或可被利用；P2 是健壮性问题；P3 是建议。

### P0

#### C-01 · P0 · 白名单邮箱可被抢注，抢注者即成平台运营员（已复现）
- **位置**：`cloud/neuxmind_cloud/auth.py:84`（`user.email in settings.operator_emails`）、`auth.py:100-120`（注册不验证邮箱）、`cloud/Dockerfile:3-4`（示例直接给出 `NEUXMIND_OPERATOR_EMAILS=ops@example.com`）。
- **问题**：
  - 运营员身份由"邮箱字符串在环境变量白名单里"决定，而 `/auth/register` 不验证邮箱所有权。
  - 新部署时只要白名单邮箱还没注册（README 和 Dockerfile 都是先配环境变量），任何人都能先注册这个邮箱，拿到 `/admin/*` 的全部权限：给自己任意加额度、确认线下订单、修改模型价格和上游、核对他人预留。
  - 大小写和首尾空白会被归一化，所以 `"  OPS@Example.com "` 也能命中白名单。
  - 测试夹具 `cloud/tests/support.py:operator()` 本身就是"注册白名单邮箱即成为运营员"，测试实际上把这个漏洞当成了正常流程。
- **复现**（`cloud_checks.py` 第 1 节，`env=prod`，`operator_emails=["ops@example.com"]`）：
  ```
  register "  OPS@Example.com "  -> user ops@example.com
  /me platform_operator: True
  POST /admin/wallets/{own org}/adjust {"delta": 1e9} -> 200 balance 1000000000
  ```
- **修复建议**：
  - 去掉"按邮箱自动授予运营员"。只认 `grant-operator` 管理命令写入的 `is_platform_operator`。
  - 或者在邮箱验证完成之后才认白名单，并且同时绑定首次授予时的 `user_id`。
  - 更新 Dockerfile 和 README 的说明，并补一个反向测试：白名单邮箱的新注册用户不能访问 `/admin`。

#### C-02 · P0 · 会话透传任意上游参数，超额输出照常返回、不扣费（已复现）
- **位置**：`cloud/neuxmind_cloud/gateway.py:291`（`{**body, out_key: out}`）、`gateway.py:313-321`（超出 `max_tokens` 后仍然 `return {**data, ...}`）、`upstream.py:134`（只覆盖了 `model`）、`gateway.py:350`（关闭时超额转核对），以及 ADR-007"超额不自动扣费"。
- **问题**：
  - 会话调用只覆盖 `model` 和 `max_tokens`/`max_output_tokens`，其余字段原样发给上游，包括 `n`、`max_completion_tokens`（新 OpenAI 模型以它为准）、`tools` 等。
  - 上游报告的用量超过会话预算时，这次调用的结果**已经返回给了用户**；会话关闭时只标记 `reconciliation_required`，不扣费。
  - 运营的 `resolve settle` 不允许超过预留额；`/adjust` 的扣减又不能超过用户的可用余额。所以超出部分平台在制度上就收不回来。
  - 每开一个小额会话，就能换取大约"上游单次请求上限"的算力，平台要向上游真实付费。
- **复现**（`cloud_checks.py` 第 2 节，用一个按 `n` 返回多份结果的替身上游）：
  ```
  session max_tokens=1000 reserved_credits=10
  call {"n": 50, "max_completion_tokens": 100000}
    -> 200, 返回 50 个 choices, neuxmind.used_tokens=45070 / max 1000
  forwarded keys: ['max_completion_tokens','max_tokens','messages','n']
  close -> reconciliation_required, credits_charged None
  wallet: balance 100 reserved 10   (实际消耗 45 倍预算，扣费 0)
  ```
- **修复建议**：
  1. 透传改为白名单（`messages`/`input`、`temperature`、`top_p`、`stop` 等）。`n` 强制为 1；`max_completion_tokens` 和 `max_tokens` 两个字段都由网关写入。
  2. 上游用量超过本次调用的 `hold` 时**不返回上游数据**（与 `/infer` 一致），会话立即转 `reconciliation_required` 并拒绝后续调用。
  3. 对超出预留的部分，在服务条款和账本里定义"可欠费结算"（允许钱包变负，或预先冻结一个保证金），否则 ADR-007 的"不自动扣费"就等于"免单"。
  4. 补测试：带 `n` 或 `max_completion_tokens` 的请求会被剥离；超预算时不返回数据。

### P1

#### R-01 · P1 · 停止并 reset 之后，被撤销运行的在途调用仍能驱动本体（已复现）
- **位置**：
  - `runtime/neuxmind_runtime/skills.py:388-409`：`ctx.call` 只在入口检查一次 `check_stop`/`revoked`。
  - `bus.py:139-151`：`start_action` 先读 `joint.state`，再进入 `supervisor.check`。
  - `runner.py:331-333`：宽限期后执行 finalize 和 revoke。
  - `core.py:143`：reset 只检查 `active_runs()`，而这个列表不含已 finalize 的运行。
- **问题**：
  - 撤销（revoke）只拦住"之后的新调用"，拦不住已经过了入口检查、正阻塞在适配器 IO 上的调用。
  - 例子：技能调用 `policy.action_chunk`，卡在 `adapter.read("joint.state")` 上（ROS 话题延迟、串口超时都会这样）。期间操作员按了停止；2 秒宽限期后这个运行被结束并撤销；操作员 reset。
  - 此时读取返回，supervisor 看到"未锁存且 `run.authorized=True`"，动作就下发到了本体。随后轮询循环发现 `revoked`，才再 cancel。
  - 这正好违背 ADR-009"防止停止后被排队中的旧指令重新带动机器人"的目的。如果适配器的 cancel 是异步或慢速的（例如 Nav2），机器人会真的动起来。
- **复现**（`rt_stale_after_reset.py`，用自制的阻塞读适配器）：
  ```
  1 stop -> latched, stopped_runs=[run-…]
  2 run status stopped, active []
  3 reset -> latched False
     ('ADAPTER.start_action policy.action_chunk', {...})   <- 被撤销运行的指令到达适配器
     ('handle.cancel', None)
  RESULT: stopped run reached adapter after reset = True
  ```
- **修复建议**：
  - 给 supervisor 加一个"急停代数"（latch epoch）：每次 stop 加 1。
  - 运行在 `_admit` 时记下当时的代数；`supervisor.check` 和 `after_dispatch` 都要求调用方传入的代数等于当前代数，否则拒绝或立即停车。
  - 同时在 `bus.invoke` 和 `bus.start_action` 内部、紧挨 `supervisor.check` 的位置再检查一次 `run.revoked`，而不是只在 `ctx.call` 入口检查。

#### R-02 · P1 · 清单参数的类型、符号和有限性都不校验，限幅器会反向放大（已复现）
- **位置**：`spec/neuxmind_spec/manifest.py:64-70`（params 只检查字段名）、`runtime/neuxmind_runtime/safety.py:59-60, 136-137`（`_clamp(value, -limit, limit)`）、`adapters/ros2.py:135-146`（配置用 `json.load` 读取，接受 `NaN`）。
- **问题**：
  - 适配器清单或 ROS2 配置里的 `max_vx` 一旦写成负数，`_clamp(v, 1, -1)` 会把**任何非零指令**都变成 +1.0 m/s：方向反转，而且是满速。
  - 写成 `NaN` 时，指令被限幅成 NaN 后照样下发到适配器。
  - 写成字符串时，抛出 `ValueError`，最终变成 502 `adapter_fault`，并被账本记为 unknown。
  - "安全监督器只能执行清单声明的限幅"本来就是设计前提，但前提的输入完全没有校验。厂商集成人员写错一个符号，就会被安全层放大成危险动作。
- **复现**（`rt_limits.py`）：
  ```
  max_vx=-1.0, cmd vx=-0.2  -> {'vx': 1.0, ...}
  max_vx=-1.0, cmd vx=0.05  -> {'vx': 1.0, ...}
  max_vx=NaN,  cmd vx=0.3   -> {'vx': nan, ...}
  ```
- **修复建议**：
  - 在 spec 的 `Capability.params` 上声明类型，并新增约束：数值必须是有限值；速度、力、`reach`、`rate_hz` 必须大于 0；`dof` 是正整数；`lower`/`upper` 的长度等于 `dof`，且逐项 `lower < upper`。
  - 由 `validate_manifest_v2` 统一执行这些约束，启动时清单不合格就拒绝启动。
  - `_clamp` 增加断言 `low <= high`，并且所有输出都再做一次 `isfinite` 检查。

#### R-03 · P1 · 关节限位列表比自由度短时，多出的关节完全不检查（已复现）
- **位置**：`safety.py:165-169`。只检查了 `len(position) == dof`，限位用 `zip(position, lower, upper)` 迭代，会被截到最短的列表。
- **复现**：`dof=6, lower=[-1], upper=[1]`，目标 `[0,0,0,0,0,100.0]` 被放行，`{'position': [..., 100.0]}` 原样下发。
- **修复**：同 R-02，在清单层强制 `len(lower)==len(upper)==dof`；限幅器内部也要再检查一次长度。

#### R-04 · P1 · 读不到 `joint.state` 时，动作块静默跳过单步速度限制（已复现）
- **位置**：`bus.py:139-143`（`except Exception: pass`），`safety.py:253-259`（`previous is None` 时不做单步限制）。
- **问题**：
  - README:62 写的是"以当前 joint.state 为起点限制单步变化"。
  - 实际上，本体没声明 `joint.state`、或者读取失败时，第一步只裁剪到限位，不限速度：例如 0.1 s 内允许跳变 3 rad，而 `max_velocity` 是 1 rad/s。
  - 另外，`joint.state` 位置数组比 `dim` 短、或者 `upper` 比 `lower` 短时，会抛 `IndexError`，进而变成 unknown。
- **复现**：`rt_limits.py` 中的 `chunk no ctx` 返回 `[[3, -3]]`，dt=0.1；`ctx shorter than dim` 抛 `IndexError`。
- **修复**：`joint_position` 动作空间要求本体必须声明并能成功读取 `joint.state`，否则拒绝执行（fail closed）；同时校验读到的数组长度等于 `dim`。

#### R-05 · P1 · 网关没有连接超时和线程上限，未认证的空闲连接能挤掉 stop（已复现线程占用；线程耗尽为代码推理）
- **位置**：`gateway.py:187`（`ThreadingHTTPServer` 每个连接一个线程）；Handler 没有设置 `timeout`。
- **问题**：
  - 不需要 token：连上之后只发半个请求头，就能永久占住一个线程。
  - 在 Jetson 一类线程上限低的设备上，攻击者或一个有 bug 的客户端可以耗尽线程。之后新连接（包括 `/v2/stop`）在 `process_request` 里起线程失败，连接被直接关闭。
  - INTERFACES 不变式 3"停止路径不经过任何会阻塞的……网络"在传输层不成立。
  - 另外，`core.emergency_stop` 里的 `threading.Thread(...).start()` 在线程耗尽时会抛异常，HTTP 层就收不到 200（本体其实已经停了），桌面端会把这次停止判为失败。
- **复现**（`rt_slowloris.py`）：400 个未认证的半截请求，线程数从 3 涨到 403；10 秒后仍是 403。
- **修复建议**：
  - Handler 设置 `timeout = 5`（读请求头和请求体的超时）。
  - 限制并发连接数（用信号量，超额就立即关闭）。
  - stop 路径不再新建线程：持久化改由常驻的 monitor 线程轮询一个"待持久化"标志来完成。
  - 现场部署文档写明：硬件急停才是主通道；软件 stop 端点应只在受信网段开放。

#### R-06 · P1 · ROS2 适配器：目标还没发送完成时，stop 取消不了 Nav2 目标（代码推理）
- **位置**：`adapters/ros2.py:177-180`、`284-286`。
- **问题**：
  - `Ros2NavHandle.cancel()` 在 `_goal_handle is None`（`send_goal_async` 尚未完成）时只设置一个标志，不发出取消。之后 `poll()` 因为这个标志直接返回 CANCELLED，再也不会去取 goal handle。
  - `stop()` 也只遍历这些 handle。结果是：stop 恰好落在"目标发送中"这个窗口时，Nav2 稍后接受目标，机器人照常导航，而运行时以为已经取消。
  - 此外 `_nav_handles` 从不清理已完成的 handle。
- **说明**：模块标注了"骨架、未验证"，但 stop 语义是这个骨架里唯一不能"以后再说"的部分。
- **修复**：用 `send_future.add_done_callback` 处理：如果已经请求过取消，在回调里立即 `cancel_goal_async()`；stop 时同时调用 Nav2 的"取消全部目标"服务。

#### R-07 · P1 · v1 兼容层：`/v1/stop` 现在会锁存，而桌面端没有 reset 入口（运行时侧已复现，桌面侧为代码推理）
- **位置**：`gateway.py:137-151`、`core.py:120-130`，`brainos/service.py:613-645`（`operate` 只有 start 和 stop），`core.py:260-261`（validate 增加了"急停未锁存"检查项）。
- **问题**：
  - INTERFACES §1.1 要求 v1"必须保持行为一致"。旧 `brainos/edge.py` 的 stop 不锁存。
  - 现在桌面端只要点一次"停止"，之后这台机器人的 `/v1/validate` 就一直是 `accepted:false`，`/v1/start` 返回 409。桌面端会把操作记为 `unknown`，提示"请核对机器人状态"，但用户在桌面端没有任何办法解除。
  - README:185 承认了这一点，INTERFACES 和 ADR-009 没有写进去。
- **复现**：`rt_misc.py` 显示 `/v1/stop` 之后 `v1_validate.accepted = False`。
- **修复建议**：第 02 轮的桌面集成要加上"解除锁存（需现场确认）"操作，或者给 v1 定义一个 reset 路径；在此之前，INTERFACES 要显式写明这个行为变化。

#### R-08 · P1（已知问题，严重度评估）· 仿真结果会被桌面端记为现场证据
- **现状**：
  - 运行时返回了 `simulated:true`、`evidence_kind:"simulation"` 和 `simulation://` 前缀，`brainos/service.py:567-577` 都没有检查。
  - 报告以 `scope:'onsite', passed:true` 入库，之后的 deploy 和 start 都把它当作合格证据。
- **定 P1、不定 P2 的原因**（三处加重因素都是本次新确认的）：
  1. `adapters/ros2.py:119` 把 `"simulated": False` 写死。用 Ros2Adapter 接 Gazebo、Isaac 等仿真时，结果会被标成 `device_run`。也就是说，即使桌面端修好了检查，仿真依然能被记成真机证据。
  2. `manifest_v1_view`（`spec/manifest.py:89-97`）丢弃了 `simulated`、`vendor`、`model` 三个字段，桌面端的 `manifest_digest` 因此区分不了仿真和真机。`configure_connection` 允许换掉同一个机器人记录的 endpoint：如果仿真体和真机的 v1 清单相同（例如 ROS2 配置共用同一个 `instance_id`），旧的仿真报告会继续作为真机部署的证据。
  3. `runtime/tests/test_v1_compat.py:146-158` 把"仿真报告 → 部署 → 启动成功"写成了断言。第 02 轮修桌面端时，这个测试会挡住修复，必须同步改成"拒绝"。
- **修复建议**：
  - 桌面端：`simulated`/`evidence_kind` 不是真机时，存为 `scope:'simulation'`，不能用于 deploy。
  - v1 清单视图加上 `simulated` 字段，并让它参与 digest。
  - ROS2 适配器根据配置 `use_sim_time` 或单独的 `simulated` 字段声明自己是否为仿真。

### P2

#### R-09 · P2 · 看门狗与 SQLite 写入共用 monitor 线程（已复现）
- **位置**：`core.py:70-76`。`watchdog_tick` 和 `runner.tick` 串行执行；`runner.tick` 会调用 `_finalize`，进而调用 `store.put`（要拿 store 锁并 fsync）。
- **复现**（`rt_watchdog_store.py`）：
  - 一个不配合停止的技能在宽限期到期时需要 finalize；同一时刻存储被占用 3 s（模拟 SD 卡 fsync 卡顿或并发大写入）。
  - 结果：设定 `timeout_s=0.2` 的速度指令，看门狗 **3.08 s** 后才置零。
- **修复**：看门狗单独占一个线程，不做任何 IO；`runner.tick` 的持久化改成交给后台写线程完成。

#### R-10 · P2 · 锁存持久化是异步的，而且与 reset 存在竞争（代码推理）
- **位置**：`core.py:129`（stop 时另起线程写 True）、`core.py:146`（reset 时同步写 False）。
- **问题**：
  1. 断电或崩溃发生在 stop 之后几毫秒内时，磁盘上可能还没有锁存记录，重启后就不处于锁存状态。
  2. stop 恰好落在 `supervisor.reset` 清标志和同步写 False 之间时，两次写入的先后不确定，可能出现内存里是锁存、磁盘上是未锁存的情况。
  3. 持久化的 `reason` 永远是 `"stop"`，请求体里的原因只出现在事件里。
- **修复**：给持久化写入加上单调递增的代数，只接受代数更大的写入；reset 先写 False 再清内存标志；启动时如果检测到异常关机，默认进入锁存。

#### R-11 · P2 · 通过 v2 直接调用 action（例如 `base.navigate_to`）没有超时（已复现）
- **位置**：`runner.py:213-222`。`submit_capability` 的 body 从不设置 `run.deadline`。
- **复现**：导航到 190 m 外的目标，`run.deadline = None`，只能靠人工 stop。
- **修复**：按能力定义默认超时（可在清单 params 里声明上限），或者要求请求里必须带 `timeout_s`。

#### R-12 · P2 · 技能参数和 v1 应用的输入校验有缺口，后果是错误码混乱和 request_id 被永久占用（已复现）
- **位置**：`skills.py:105`（先 `dict(given)` 再判断类型）、`ledger.py:68-71`、`skills.py:83-100`、`core.py:250-253`。
- **问题**：
  - `parameters: "ab"` 会抛 `ValueError`，账本把它当成"执行结果未知"，返回 502 `adapter_fault`；同一个 request_id 永久变成 `outcome_unknown`，可实际上什么都没执行。
  - `parameters: [["speed", 0.2]]` 被静默接受。
  - `float` 类型的参数接受 NaN。
  - v1 应用的 `step.parameters` 是列表时，`/v1/validate` 返回 500，而不是一个失败的检查项。
  - `step.requires` 写成字符串时会被逐个字符当成能力 ID，报错是"缺少能力 ., a, b, c…"。
- **修复**：在 `check_parameters` 一开头就用 `isinstance(given, dict)` 判断类型；`float`/`vector` 拒绝非有限值；在 v1 校验里把所有用户输入的类型错误都转成失败的检查项；账本只把"已经发生副作用之后"的异常记为 UNKNOWN。

#### C-03 · P2 · 登录限速只按邮箱：任何人都能锁定受害者，Postgres 下并发还能绕过（锁定已复现，并发绕过为代码推理）
- **位置**：`auth.py:126-138`。
- **问题**：
  - 失败计数只看邮箱，阈值以内没有 IP 维度。攻击者对受害者邮箱每分钟试错 8 次，受害者用正确密码也会一直收到 429（实测，阈值 3）。
  - 反过来，撞库攻击换着邮箱试，完全不受限。
  - Postgres 下"计数 → 判断 → 插入"不在锁里，同一批并发请求可以全部通过计数检查（SQLite 下被 `BEGIN IMMEDIATE` 串行化了，所以测试发现不了）。
- **修复**：限速键改为（邮箱, IP）和（IP），分别设阈值；对正确密码采用逐步延迟而不是硬拒绝；计数放在 `SELECT … FOR UPDATE`（或 advisory lock）内完成。

#### C-04 · P2 · 上游所有 HTTP 错误都被当成"没有产生计费工作"并释放预留（代码推理）
- **位置**：`upstream.py:83-85`；测试 `cloud/tests/test_gateway.py:252` 把 500 断言成 `upstream_error`（已释放）。
- **问题**：502、504、524 往往来自上游前面的负载均衡或网关超时，这时模型可能已经算完并且计费了；429 和 400 才确定不计费。全部归为 `UpstreamRejected`，意味着平台向上游付费，却不向用户收费。
- **修复**：只把 4xx（不含 408）归为 Rejected，5xx 一律按 Unknown 转核对。反方向上，DNS 解析失败（`socket.gaierror`）目前被归为 Unknown，实际上请求根本没发出，应改为 Rejected。

#### C-05 · P2 · 预留会泄漏：崩溃或会话过期后，额度永远被占着，运营也看不到（代码推理）
- **位置**：`gateway.py:114-186`（三段事务）、`gateway.py:263-303`（`inflight_tokens`）、`routes/admin.py:131`（默认只列出 `reconciliation_required`）。
- **问题**：
  - 进程在第 1 段和第 3 段之间退出时，预留会永久停在 `held`，用量记录停在 `pending`。
  - 会话过期但没人调用 close 时，预留也一直 `held`。
  - 会话调用中途崩溃会让 `inflight_tokens` 一直大于 0，这个会话从此无法关闭（`session_busy`）。
  - 运营后台默认只列 `reconciliation_required`，看不到这些"僵尸 held"预留；用户的可用额度则被一直占着。
- **修复**：增加定时清理任务：超过 TTL 的 held 预留转为 `reconciliation_required`；过期会话自动按已计量的用量关闭（有 inflight 时转核对）。

## 测试有效性抽查结果

方法：`mutate.py` 每次只改一处产品代码，跑对应目录的全部测试，然后用 `finally` 恢复原文件；最后用 `git diff` 确认零改动。共 24 个变异，20 个被测试杀掉，4 个存活。

| R7 去掉 finalize 时的 `run.revoked = True` | **存活** | `test_uncooperative_skill_is_revoked_after_grace` 只检查运行状态和备注文字，没验证撤销之后 `ctx.call` 被拒 |

其他测试质量问题：

- `runtime/tests/test_v1_compat.py:146-158` 把"仿真报告被当作现场证据，并成功部署、启动"写成了断言。它验证的是已知缺陷，而不是不变式 4。

## 文档与代码不一致

1. **INTERFACES §1.1**：要求"`/v1/stop` 必须保持行为一致"。实际上 v1 stop 现在会锁存，桌面端也没有解锁入口（R-07）。只有 runtime/README:185 提到了这一点，契约本身没改。
2. **INTERFACES 不变式 3**："停止路径不经过任何会阻塞的锁、队列、模型调用或网络"。应用层成立（已实测），传输层不成立（R-05）。
3. **ADR-010 / runtime README:71**："不响应停止的技能 2 秒后被收回能力调用权限"。只对新调用成立，对在途调用不成立（R-01）。
4. **runtime README:62**："以当前 `joint.state` 为起点"限制单步变化。读不到 `joint.state` 时会静默跳过（R-04）。
5. **safety.py 模块说明**："commands are limited ... using the parameters the body declares"。没有说明这些参数本身完全不经校验，负数或 NaN 会让限幅失效（R-02）。
6. **cloud README:134**："网关按剩余预算硬性限制输出上限"。`n` 和 `max_completion_tokens` 等透传参数会绕过它（C-02）。
7. **cloud README:186 / auth.py docstring**："平台运营员只有两个来源"。没有指出白名单邮箱可以被抢注（C-01）。README:223 写了"没有邮箱验证"，但没有把两者联系起来。
8. **auth.py docstring**："demoting or removing the creator immediately narrows the key"。降级的逻辑存在但没有测试；移除成员的接口根本不存在（C-10）。
9. **spec `manifest.is_motion`** 与 **runtime `safety.is_motion`** 对 `x.*` 的判定相反（R-13）。
10. **INTERFACES §1.2** 没有列出已经实现的 `GET /v2/runs`；`/v2/reset` 已写进 INTERFACES，但 runtime/README:148 仍标注为"契约外新增"。
