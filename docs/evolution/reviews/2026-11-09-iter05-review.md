## 2. A：运行时（b96677f）对抗实验

`r5/attack_a.py`。适配器均为 `SimQuadruped`/`SimArm` 子类；`ManualClock` 每 0.1 s 推进一次并手动 `latch_guard.tick()`（与线程版周期一致），时间相关项用真实线程。

### 2.1 守护能否发运动、解锁、改原因、计数

| 场景 | 结果 |
|---|---|
| 停止后 2 s 驱动自行恢复 0.03 m/s（每次停止都恢复），600 s | 再停 285 次，位移 0.73 m；`latched=true`、原因不变、`stop_count` 不变、停止后适配器收到的运动/其他指令 **0** |
| 驱动 `stop()` 永远抛异常 + 立即恢复 0.3 m/s，10 s 真实线程 | 再停 18 次（≈ 每 0.5 s 一次，符合 `restop_interval_s`），事件 18 条，`stop_count=1`，保持锁存 |
| 锁存期间说谎驱动持续运动，操作员连续复位 10 次（A8） | 10 次复位均成功（操作员授权，属预期），守护从未在复位窗口外制造解锁；适配器收到运动指令 0 |

守护本身满足契约：只调 `adapter.stop()`、限速、不碰锁存与原因。

### 2.2 CPU、线程、关闭

| 测量 | 结果 |
|---|---|

| `base.odometry` 读取永久阻塞时创建并 `close()` 10 个运行时 | 每次 `close()` ≤ 1.01 s；**遗留 10 个 `nx-latch-guard` 线程**，读返回后全部退出（Q5-08） |

没有空转，没有阻塞停止路径（守护持有的锁停止路径从不获取）。

### 2.3 Q5-01：低于阈值的蠕动（P2）

阈值是“单个 0.1 s 采样间隔”的：速度 > 0.02 m/s，或位移 > 3 mm 且 > 0.02 m/s × dt。驱动停后 2 s 恢复一个低于阈值的速度：

| 恢复速度 | 600 s 位移 | seen / restops |
|---|---|---|
| 0.015 m/s | **8.97 m** | 0 / 0 |
| 0.019 m/s | **11.36 m** | 0 / 0 |
| 0.03 m/s | 0.73 m | 285 / 285 |

机械臂同理：关节 0.04 rad/s（阈值 0.05）可以一直转。阈值本身是为了容忍站立抖动和 IMU 漂移，合理；缺的是“锁存以来累计位移/累计关节角”这一项（例如锁存后超过 settle 的累计平移 > 5 cm 或任一关节累计 > 0.05 rad 即再停并告警），它对抖动免疫、对蠕动敏感。

### 2.4 Q5-02：反馈被“蒙住”（P2）

驱动在停止后继续 0.3 m/s，但 `base.odometry` 上报如下（30 s）：

| 上报 | 真实位移 | seen | read_errors | 有无事件/再停 |
|---|---|---|---|---|
| `pose`/`velocity` 全 NaN | 8.4 m | 0 | 300 | 无 |
| `pose` 3 维、`velocity` 1 维（不合标准） | 8.4 m | 0 | 300 | 无 |
| `velocity: null` | 8.4 m | 0 | 300 | 无 |
| 冻结（恒为原点、速度 0） | 8.4 m | 0 | 0 | 无（固有限制：反馈造假无法从反馈发现） |
| 速度报 0 但位姿真实 | 0.34 m | 14 | 0 | 再停 14 次（位姿差分兜住了） |

另：`SimArm` 子类停止后关节 1 每次读取漂 0.02 rad，`joint.state` 不给 `velocity`，且每次把 `names`/`position` 循环移位一格：守护因 `names` 与上次不同而跳过位置差分，30 s 关节漂 **6.0 rad**、`seen=0`。

`read_errors` 会出现在 `/v1/status.latched_motion` 里，但没有事件、没有再停，桌面也不显示。建议：锁存期间连续读失败（例如 ≥ 1 s）按“看不见即可能在动”处理——再停一次（停止本身是安全侧）并发 `safety.latched_feedback_unavailable` 事件；关节按名字对齐比较，而不是名字顺序一变就跳过。冻结反馈属固有限制，应在 README“锁存守护”一节写明“守护依赖真实反馈，不能替代硬件急停”。

### 2.5 合法运动：复位中起立、停止时坐下

| 场景 | 结果 |
|---|---|
| `adapter.reset()` 内起立 3 s（位姿、偏航、速度都在变） | 复位成功；`seen_during_reset=31`，再停 0 |
| 起立 3 s、`reset_grace_s` 调成 1 s（模拟起立超过 30 s 默认值） | 守护再停 5 次 → 复位失败 `estop_latched`，提示 **“复位期间又收到停止；保持锁存”**，`safety.reset_raced` 1 条（安全侧；文案不实，Q5-07） |
| 停止 = 受控坐下（关节 0.8 rad，不报速度），坐下 0.8 s | 再停 0 |
| 坐下 2 s（再次 stop 不重规划 / 重规划） | 再停 2 / 6 次，`seen` 10 / 25 |
| 坐下 3 s（同上） | 再停 4 / 8 次，`seen` 20 / 37 |

（`r5/attack_sit.py`）`settle_s=1 s` 对仿真合适，对实际足式“阻尼趴下/StandDown”（常见 2–3 s）会误报，事件文案还会让操作员“使用硬件急停并检查驱动”。再停本身是安全侧，坐下最终完成，所以是 P3（Q5-06，与 R4c-04 同根：settle/阈值按 family 或清单参数标定）。

### 2.6 R4c-01 / Q5-03：`adapter.reset()` 永不返回

`attack_a.py a5`（HTTP，真实网关）：

| 步骤 | 结果 |
|---|---|
| `/v2/stop` → `/v2/reset`（卡住） | 第一次复位挂起 |
| 1 s 后第二次 `/v2/reset` | 409：“适配器上一次复位（adapter.reset()）尚未返回（已 1.0 s）；在它返回之前拒绝新的复位，急停保持锁存” |
| `/v1/reset` | 409 |
| 卡住期间 `/v2/stop` | 200，**5 ms** |
| `/v1/status` | `reset_in_progress: true`，`estop_latched: true` |
| 再试 40 次复位 | 全部 409，线程数增量 0，之后 `/v2/stop` 仍 200 |
| 关闭运行时（0.11 s）→ 同一状态目录重启 | 重启后 `estop_latched=true`、`reset_in_progress=false`，复位成功 |

运行时这边正确：永不解锁、停止不受影响、重启是可靠的出路（锁存持久化）。问题在出路没人告诉操作员：

1. `runtime/README.md` 只写“`reset()` 须在合理时间内返回”“在途时 409”，没有写“`adapter.reset()` 卡住时如何恢复：确认现场安全后重启运行时服务（锁存会保留），再复位”。
2. 桌面 `brainos/connector.request()` 对 HTTPError 只保留状态码。`r5/desk_reset.py` 实测桌面得到的文字：第一次（8 s 超时）“无法连接接入服务；请检查服务是否启动及网络是否可达”；第二次“接入服务返回 HTTP 409；请检查地址、凭据与协议”。界面 toast 为“解除急停结果待核对：……”——没有变成“成功”（安全侧），但真实原因 `reset_in_progress` 和出路都丢了，还把用户引向“检查地址/凭据”。

建议：连接器把设备返回的 `error`/`code` 带上来；桌面对 `reset_in_progress` 给出白话说明与“重启机器人上的运行时服务”（仿真机器人可直接“停止/启动仿真”）；README 补一段操作员恢复流程。

### 2.7 R4c-02 / Q5-09：`keep_reason` 比较交换

`attack_a.py a7`：`sys.setswitchinterval(1e-6)`，每轮先停止（旧原因）→ 占位停止 → 并发“较新停止” + `set_reason_if(旧原因)`，3000 轮，较新原因丢失 **0** 次。代码审读：`emergency_stop()` 先写 `latch_reason` 再写 `_stop_record`；若较新停止恰在这两句之间、而 `set_reason_if` 恰好在其间写入并复查，复查读到旧 `_stop_record` 会放弃恢复，留下旧原因。窗口是两条相邻语句，后果只是原因文本（仍锁存），记 P3。修法：`_stop_record` 与 `latch_reason` 同一赋值序列中先写记录，或复查时比较 `latch_reason` 本身。

### 3.2 参数绕过表单直接发给 API

| 参数（patrol） | 结果 |
|---|---|
| `loops: 1.5` | 设备拒绝：“技能参数 loops 需要 int” |
| 多余字段 `evil` | 设备拒绝：“技能不接受参数：['evil']” |
| JSON 字符串里 `NaN` / `1e400` | 桌面 400（非有限数值不出本机） |
| `loops: -5`、`loops: 10^9` | **接受并运行**（patrol 未声明范围；`10^9` 圈会一直走，靠运行超时/停止结束） |

运动安全仍由设备端监督器兜底（限速、工作区、急停），这里没有物理越界。但见 Q5-05：恶意技能包的 `loops` 声明 `min:1, max:3`，表单显示“范围 1 – 3”并会拒绝 4；而打开“高级：直接编辑 JSON”填 `"loops": 99`，请求体就是 `{"loops":99}`，设备 `accepted`（`r5/raw.cjs`）。运行时 `skills.check_parameters()` 只检查类型和有限性，不读 `min`/`max`。技能作者若把安全相关的上限（速度、力、次数）写在 skill.json 里，会以为它生效。建议运行时按声明检查 `min`/`max`（以及 `choices`，已有）并在拒绝时说明哪一项。

### 3.7 白话错误包装（Q5-04，P2）

`r5/explain.cjs` 把 `web/ux02.js` 的 `explainError` 喂真实的运行时/桌面错误文本：

## 4. C：首次用户走查（`r5/walk.cjs`，截图 `r5/shots-walk/`）

从空工作空间：添加仿真四足 → 工作台“下一步” → 示例库安装“巡逻” → 运行表单 → 不勾授权提交 → 授权运行 → 实时状态 → 停止 → 解除急停 → 浏览各页。整条主路径无 JS 错误、无死胡同，主线顺畅。从用户角度仍然困惑的地方（Q5-12，均 P3）：

1. **安装预检里的参数还是“技术名”**：`waypoints · object · 必填`、`loops · int`、`tolerance · float`，而下一步的运行表单已显示“航点 / 圈数 / 到达容差”和单位。同一个技能两种叫法。
2. **技能说明里有能力 ID**：预检描述“任何提供 base.navigate_to 的本体都能运行；若本体有 legged.posture，会先站立”。新用户不知道这是什么。
3. **机器人详情偏工程**：“标准能力清单（/v2/manifest）”“hardware_estop 否”“rate_hz 100.0 Hz · frame base_link”直接出现在第一屏能力列表里，可收进“技术细节”。
4. **进度条说“01 明确任务 · 已有记录”**：用户只点了“添加仿真机器人”，并没有描述任务；自动建的“试用仿真机器人”项目被算成已明确任务，容易误解进度。
5. **未勾授权就点“授权并运行”** 只有浏览器原生的“请勾选此框”气泡，没有中文说明为什么必须勾（复位表单同）。

7. **实时状态里的运行编号** `run-c452cedf3da8` 显眼放在步骤列表下，用户不需要。
8. 停止后“运行技能”按钮变灰但旁边没写原因（上方红框有说明，按钮本身无提示）。

## 5. 其他观察

- Q5-10：`uxParamBuiltin` 在技能未声明 `unit` 时按参数名套单位（`speed→m/s`、`timeout→s`、`tolerance→m`……）。恶意包的枚举参数 `tolerance` 被显示“m”。第三方技能用 `timeout`（毫秒）或 `speed`（rad/s）会被标错单位。建议只在示例技能或技能明确声明时显示单位，否则显示“单位未声明”。
- Q5-11：`brainos/server.py` `/api/health`、`brainos/service.py` system、`brainos/agent_runtime.py` clientInfo 仍为 `0.11.0`。
- R4c-06（保留 P3）：`run_skill` 仍只凭存储里的 `sim` 标记；本轮确认没有接口能设置它（§3.4），继续作为纵深防御项。
