### issue #3 · 跳板机与真机实时状态
- **连接**：接入表单增加"连接方式：直连 / 经跳板机"。跳板机有自己的地址、端口、用户名和认证方式（密码、私钥、本机 SSH Agent）。两跳主机指纹都要确认并固定，先确认指纹再发送认证信息。只支持一跳，不读本机 `~/.ssh/config`，不做 Agent 转发。
- **粘贴 ssh 命令自动填表**（用户在 issue 讨论中提出）：粘贴一条 `ssh [-J 跳板机] [-p 端口] [-i 私钥] user@host` 命令即可填好表单；命令只被解析，从不执行，也不读取本机文件（`web/ssh_command.js`，纯函数）。
- **真机只读实时状态**：后端执行一条固定的只读命令（不经过模型，不接受用户输入的命令文本），显示是否可达、往返延迟、主机名、开机时长、负载、内存、根分区、最高温度、失败的 systemd 服务，以及用户指定关注的服务；失败时区分跳板机不通、目标机不通、认证失败、指纹变了。页面标明"真机 · 只读"，不产生运动、不修改设备（`brainos/device_status.py`）。
- **改动文件**：`brainos/device_access.py`、`device_status.py`（新）、`engineering.py`、`server.py`；`web/ssh_command.js`（新）、`ssh_jump.js`（新）、`engineering.js`、`app.js`、`index.html`、`style.css`；`docs/ENGINEERING_ENGINE.md`「跳板机与真机实时状态」。
- **会话自测**：`test_ssh_jump.py` 33 项、`ssh_command_logic.cjs` 40 项、浏览器验收 `ssh_jump_browser.cjs` 通过；打包后的后端跑通跳板机流程。
- **验证级别**：界面流程（粘贴命令、两步确认指纹）为替身级——两端都是本机 SSH 协议替身（`tests/ssh_fixture.py`），覆盖密码、私钥、真实 ssh-agent 进程。**后端只读状态已在真机上验证**（用户同意后）：本机 → 公网跳板机 → 四足机器人机载电脑，两跳都用本机 SSH Agent，两跳指纹都与本机 known_hosts 一致；只执行固定状态命令 3 次，首次新建两跳会话 13.4 s，复用会话 0.7–1.0 s，读数与人工排查一致；会话已关闭，没有保存凭据。
- **真机暴露的问题（已修，待提交）**：每个阶段 8 s 的超时对公网跳板机太紧（握手约 3 s，Agent 里两把密钥依次尝试约 6 s），稍有波动就超时并被误报为"连不上跳板机"。改为 TCP 10 s、握手 20 s、认证 20 s、开通道 15 s，新增失败原因 `timeout`（"应答超时：可能是地址不通，也可能只是网络慢"）；替身加了 `banner_delay`/`auth_delay` 模拟慢链路，新增 2 项测试。
- **暂不包含**：机器人 HTTP 适配服务经跳板机转发；多跳；ROS 层数据（电量、位姿）。
- **会话提出的既有行为（未改）**：取消接入对话框后，密码仍留在页面内存中；指纹确认记录 10 分钟内可重复使用。

### issue #4 · TokenFans 模型与算力
- **连接方式**：粘贴 API Key（`sk-tkf-…`，用模型列表校验），或用 TokenFans 账号的邮箱和密码登录：应用登录一次、读取账户的 API Key 与余额，然后立即退出。登录用的是 TokenFans 网页控制台的接口（不在公开 API 文档里，可能变化），失败时请改用粘贴 Key。密码和控制台令牌只用于那一次交换，不保存。
- **Key 的保存**：只存在 `<工作空间>/credentials/tokenfans.json`（目录 700、文件 600），绑定校验时的 TokenFans 地址；不进入注册表、状态快照、审计事件和接口返回；工程引擎运行时通过环境变量拿到。
- **默认模型**：每个项目自动有一个跟随 TokenFans 默认模型的工程模型档案。本体调查、工程任务、协作流程阶段、本体适配在没有单独选择模型时都使用它；界面上所有模型下拉框默认选中 TokenFans。已在项目里单独配置的模型不受影响。
- **给其他模块的入口**：直接调大模型用 `platform.model_compute.default_llm()`（返回 OpenAI 兼容的 `base_url` 与 key，key 只用于当次请求）；走工程引擎时不传 `model_id`，由 `Engineering.resolve_model(project_id, None)` 解析。前端只拿到 `model_compute` 摘要（connected、default_model、models、key_hint）。
- **改动文件**：`brainos/model_compute.py`（新）、`engineering.py`、`service.py`、`workflows.py`、`server.py`；`web/model_compute.js`（新）、`app.js`、`engineering.js`、`ux02.js`、`workflows.js`、`index.html`、`style.css`；`docs/ENGINEERING_ENGINE.md`「TokenFans：工作空间默认模型」。
- **验证级别**：替身级——`tests/tokenfans_fixture.py` 是本机 TokenFans 替身，按控制台与 API 文档的接口形状实现，替身里的凭据每次运行随机生成。**真实 TokenFans 服务未验证。**
- **已知风险**：默认模型取自 `/codex/v1/models`，这些模型在 `/v1` 路由上是否可用，要用真实 Key 才能确认。

### issue #2 · 初始化硬件扫描与修复
- **扫描**：SSH 连接成功后先做一次只读硬件扫描（产品自带的一条命令，不经过模型、不修改设备，通常几秒），用表格列出处理器、GPU、相机、串口、网卡、USB、PCI 设备及驱动状态，并按类别筛选；下方列出需要处理的问题和提示。扫描后可"让 Agent 深入调查本体"（原来的下一步），也可随时"重新扫描"。
- **修复**：勾选问题后"让助手修复所选问题"，工程引擎加载内置 Skill `hardware-init`（随应用发布，项目里不可修改，可在界面查看）。每条会修改设备的命令都单独显示目的、风险、回滚方式，由用户逐条批准（审批与执行的命令严格绑定）。产品另有一份禁止列表，会拒绝常见的危险命令（重启、关机、改 SSH 配置或密码、锁用户、清防火墙、刷机等）；它是尽力而为的第二道防线，不能替代逐条审批（见下方独立审查 #2 的 P1）。修复后重新扫描验证，保存修复记录。
- **模型**：修复会话不指定模型时用工作空间默认模型（#4 的 TokenFans，经 `Engineering.resolve_model(project_id, None)`）；本功能不保存任何 key。
- **改动文件**：`brainos/hardware_scan.py`、`hardware_init.py`（新）、`brainos/skills/hardware-init/`（新）、`engineering.py`（`_tool`/`_run` 中的单行挂钩）、`agent_runtime.py`、`server.py`、`service.py`；`web/hardware.js`、`hardware.css`（新）、`app.js`、`engineering.js`、`index.html`；`scripts/build_macos.py`（打包 `brainos/skills`）；模块文档 `docs/HARDWARE_INIT.md`。
- **会话自测**：硬件测试 34 项（含一次用内置 Codex、脚本模型和 SSH 替身走完的修复会话：批准、产品拒绝 reboot、重新扫描、保存报告）；桌面全套仅 test_adaptation 那项失败（main 上同样失败）；内置浏览器里走过扫描、修复表单、命令审批、会话面板、修复记录和手机宽度（替身数据）。
- **验证级别**：**只读扫描已在一台 Jetson Orin NX 真机上验证**（经跳板机、私钥认证，7 s、约 9 KB 输出，据此修正了 4 处误报规则）。真机上没有执行过任何修复命令；真实模型（TokenFans）下的修复会话未验证。
