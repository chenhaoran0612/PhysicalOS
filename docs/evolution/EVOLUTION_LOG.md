## 第 08 轮 · 2026-11-11～12 · issue 驱动：跳板机与真机状态、TokenFans 默认模型、硬件初始化（0.14.0 → 0.17.0）
- 目标：GitHub issue #3（SSH 经跳板机接入、真机只读实时状态）、#4（TokenFans 作为默认大模型）、#2（连接后硬件扫描与修复）；修复部分 Mac 上启动卡约 35 s；云平台在本地 Docker 运行。
- 关键决策：需求改由 issue 下达，每个 issue 一个会话、一个分支、一个工作区，总指挥合并到 `integration`（AGENT_COLLABORATION「Issue 驱动的并行开发」）；提交必须由用户在该会话里亲自确认，会话之间的转述不算；合并前扫描真实环境信息；硬件修复以逐条审批为闸门，禁止列表只是第二道防线。
- 分工：三个 issue 会话并行 → 总指挥用只读快照提前试合并和打测试包 → 三份独立审查（#3、#2 各 1 个 P1，#4 2 个 P2，均在提交前修复）→ 按 commit 合并 → 全量测试、打包、部署到本机。
- 验证：spec 17 / cloud 218 / 桌面 390（1 个 main 上原有的失败）/ sdk 84 / runtime 486（4 个 main 上原有的失败，Docker Desktop 容器）；三个 issue 的浏览器验收通过；安装包校验与打包后冒烟通过。真机只做了两项只读验证（#3 状态命令经公网跳板机；#2 硬件扫描在一台 Jetson Orin NX）；真实 TokenFans 服务、真机上的修复会话未验证。
- 用户测试 0.15.0 后的跟进（0.15.1）：嵌套 ssh 命令经跳板机解析目标名称（#3）；工程模型只对接 TokenFans、在“云平台账户”页配置（#4）；修复表单的模型指引（#2）。统一回归又查出并修掉：两个浏览器验收脚本因 #4 的改动过时、首次加载在“云平台账户”页时自动刷新不启动（main 上就有）、密码框关闭后仍留着 Key、SSH 执行请求没有时限。main 上原有的两处测试失败也在这一版修复。当时未提交的改动经用户授权以只读快照合入，之后各分支都已原样提交。验证：桌面 415 项零失败，21 个浏览器验收脚本全部通过，Linux runtime 487 项中 1 项计时类用例对负载敏感。
- 用户验证 0.15.1 的结论：基础功能可用，细节另提 issue。随后并入 main 上其他成员提交的账号管理与邮箱验证（212da95）：4 个共用文件 7 处冲突，两边都保留；本轮新增的两个验收脚本改走登录页，并修了 main 自带的 `browser_smoke` 等待条件；用旧版本建的账号和项目在新版本上实测可用。0.16.0（build 26）：桌面 427 项零失败，22 个浏览器验收脚本全部通过，安装包校验通过；用户确认后部署到本机。
- 0.16.0 收尾：`integration` 在用户确认后快进合并到 main 并推送；#2、#3、#4 关闭，细节调整另提 issue。
- 验证后的新 issue（0.17.0 build 27）：调查不设 Token 和时间上限（#5）；调研入口按状态打开、重新调研走完整流程、报告上逐条审批的对话修复（#6）；控制台自己的下拉框、同色系悬停、运行中不显示代码和 JSON（#7）。集成时定了一条例外：审批里要批准的命令保持可见。桌面 480 项零失败，23 个浏览器验收脚本通过，样式和调研在 WebKit 上通过；已部署到本机；用户最终检查后确认，合并到 main 并推送。
- 遗留：用真实 TokenFans Key、真机和真实邮件服务走完整流程；内置测试账号是否默认开启待定；机器人 HTTP 适配服务经跳板机转发、多跳、ROS 层数据；被替换连接的凭据清理；第 07 轮 P3。
