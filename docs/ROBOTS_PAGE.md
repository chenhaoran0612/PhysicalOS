### 卡片

`rpParts(html, robot)` 把各功能拼好的整张卡片拆开：

- **看得见的**：图片（`rcPicture`）、名称、在线与否、品牌 · 型号（没有填时是「未填写品牌型号」）、最多一个下一步按钮、「实时状态」、「更多功能」。「解除急停」出现时仍然留在卡片上。
- **在线与否**：用 SSH 接入的真机仍是心跳那一行（`heartbeat.js` 原地更新它），样式表只显示其中的在线标记；仿真机器人是「运行中 / 已停止」；只有服务地址的真机按控制通道是否连接显示「在线 / 离线」。
- **看不见但还在卡片里的**（`.rp-details`，带 `hidden`）：各功能加在卡片正文里的其余内容，元素和属性原样保留。保留在卡片里有两个原因：原地更新的脚本（心跳、管理层安装、开机自启）照常找得到自己的元素；其他功能的浏览器验收脚本读这些文字的写法不用改。
- **每张卡片都有「实时状态」**：有 SSH 状态页的用它，其次是仿真/技能的实时状态页；两者都没有的（例如已停止的仿真、只有服务地址且未连接的真机），按钮打开一个只有概览的对话框。
- 概览里有已证实的问题（红色状态、设备自报的本体类型与所选不符）时，「实时状态」按钮上有一个红点；提示性的黄色状态不算（issue #47 的规则：没有证据不报故障）。

### 实时状态里的概览

打开一台机器人的实时状态时，`rpOverviewSync()` 在实时数据上方插入概览（`.rp-overview`）：心跳那一行（含最近心跳时间、离线原因、重试）和卡片收起的全部内容。页面每次刷新状态时重写一次（内容没变就不动，原地更新的脚本画上去的内容保持）。概览和卡片里收起的部分是同一份标记，所以两处内容一致。

### 品牌型号清单和图片

- 清单：`web/robot_catalog.js` 的 `ROBOT_CATALOG`，一行一个品牌，`rcM(型号, 本体类型, 图片文件名, 其他写法)` 一个型号。设备自己上报的写法（例如 `unitree`）通过 `aliases` 认到同一个品牌，比较时不分大小写、不计空格和连字符；保存的仍是原来的两段文字，后端规则（`brainos/robot_model.py`）没有改。
- issue #61 起品牌和型号各是一个「可下拉、可输入」的框，没有「其他」和第二个输入框了，见 [BRAND_MODEL_INPUT.md](BRAND_MODEL_INPUT.md)；下面这一条写的是 #53 当时的做法。
- 表单：`rcInputs()` 替换了 issue #48 的 `rmInputs()`（没有改 `web/robot_model.js`）。发送的字段仍是 `vendor`、`model`；下拉列表选中清单里的值时把它写进这两个输入框，选「其他」时显示输入框。星玑的型号是 CS1。
- 图片：`web/robot_images/`，由 `brainos/robot_pictures.py` 提供（只按文件名提供这个目录里的 `.webp` 和 `.svg`，请求里不能带路径）。清单里有图片的型号显示它自己的图；没有的（包括清单之外的品牌型号）按类型显示一张线条示意图（四足、轮足、机械臂、人形各一张）。30 张型号图片来自开源的 MuJoCo Menagerie 模型渲染图；智身 钢镚 L2U 的图由它的 URDF 模型渲染，星玑 CS1 的图取自它的开发手册。来源逐张写在 `web/robot_images/SOURCES.md`；仓库是公开的：除这两张（项目方提供的资料）以外，没有放厂商的产品图。

### 对浏览器验收脚本的影响

- 品牌型号是下拉列表：`require('./robot_model_helper.cjs').fillBrandAndModel(page)` 照旧可用；要填指定的品牌型号用同一个文件里的 `pickBrandAndModel(表单的 locator, {vendor, model})`（清单里有就选，没有就选「其他」再填）。
- 卡片收起的内容：用了 `throughRobotsPage(page)` 的脚本，读文字照旧；等它「可见」变成等它出现在卡片里且没有被自己的功能隐藏；点里面的按钮（心跳的「重试」、开机自启的「设置」）会先打开「实时状态」，在那里点同一个按钮，再关上。`isVisible()` 和整张卡片的文字不包括收起的内容。想看用户实际看到的，用 `robotStatus(page, card)` 打开实时状态并拿到概览。

### 还没有做的

以下是 issue #41 当时的说明；其中卡片上显示什么、「更多功能」里有什么，以上面为准。

## 改之前

每个功能都往机器人卡片上加自己的按钮、状态行和标签，也往页面上加自己的一段。0.21.4 上一台用 SSH 接入的真机，卡片上有 11 个按钮、6 个标签和 2 条状态行；页面上不管有没有机器人，都是 3 个添加按钮、3 张添加方式的大卡片、接入流程说明、助手模型和本体类型清单。

## 现在

**页面跟着状态走。**

| 状态 | 页面上有什么 |
| --- | --- |
| 还没有机器人 | 三种添加方式（页面的主体），页头不再重复这三个按钮 |
| 已经有机器人 | 机器人卡片，页头只有一个「添加机器人」；三种添加方式在这个按钮打开的对话框里 |

页面上不放说明（issue 里 2026-11-25 的补充：「真机接入流程说明 / 这个页面怎么用 / 助手使用的模型 / 本体类型清单 这些不需要，上面的提示尽量少，且对齐」）。原来页面底部的四个折叠行去掉了：两段说明不再显示（使用指南在页面右上角）；两项不属于某一台机器人的设置收进页头的「设置」列表，「助手模型」打开原来的模型对话框，「本体类型清单」打开一个自己的对话框（在里面添加、删除类型，表单关掉后回到清单）。没有机器人时页面只有标题和三种添加方式，标题上方一行「选择一种方式添加机器人」。

卡片对齐：每张卡片都是 名称 → 一行状态（真机是在线/离线和最近心跳，仿真是运行中/已停止）→ 一行「是什么 · 在哪里」→ 需要处理的事。仿真机器人卡片上只起解释作用的两句（「地址和令牌由应用自动管理」「仿真结果只说明逻辑是否正确，不能作为现场证据」）移到它的「更多功能」列表末尾的「说明」里，一字不少。

**卡片只留现在用得上的。**

- 看得见的：名称、是否在线和最近心跳、本体类型和地址、需要处理的事（硬件故障、调研进行中、安全限值未填、管理层安装进度等）。
- 两个按钮：下一步要做的事（实心按钮），和「实时状态」。
- 其余功能在「更多功能」里，分成 连接 / 设备 / 管理层 / 仿真 几组，「删除」单独放在最后。开机自启的状态和普通的状态标签（例如“控制通道：未连接”“硬件 17 项正常”）也在里面。

下一步按这个顺序选：正在进行的调研或修复（「调研进展」）→ 控制通道已连接的机器人是「能力与技能」→ 各功能自己标成实心的那个按钮（「开始调研」「调研报告」「配置 SSH」「启动仿真」）。「解除急停」出现时永远留在卡片上，不收进列表。

「更多功能」一次只开一个；点别处、按 Esc（焦点回到按钮上）、或选了其中一项都会收起；页面轮询刷新时保持打开。

## 做法

新增 `web/robots_page.js` 和 `web/robots_page.css`，其他功能的脚本没有改：它们照旧通过包装 `engineRobotCard` 往卡片上加内容。`rpCard()` 拿到加完之后的整张卡片，把各部分挪到新的位置，元素本身和它们的属性原样保留，所以心跳、管理层安装、开机自启、验证连接这些“原地更新”的代码照常找得到自己的元素。

- `rpCard(html, robot, open)` 是只处理字符串的纯函数，在 `tests/robots_page_logic.cjs` 里检查：每个按钮只出现一次、不丢不重；不认识的卡片原样返回。
- 以后的功能往卡片上加按钮，不用改这里：不认识的按钮自动进「更多功能」的「其他」组。想让它进某一组，在 `RP_GROUPS` 里加上它的 `data-action`。
- 页面在所有脚本加载完之后（`DOMContentLoaded`）才接管 `views.robots`，所以 `index.html` 里这一行放在哪里都可以。接管之后页面由 `rpPage()` 自己拼：包装 `views.robots` 追加的内容不会显示。页面上不再有放说明和设置的地方；不属于某一台机器人的设置，加在 `rpSettings()` 的列表里，各自开对话框。

## 对浏览器验收脚本的影响

卡片上收进列表的按钮在列表打开之前是看不见的，Playwright 点不到；有机器人之后，三种添加方式要先点「添加机器人」。`tests/robots_page_helper.cjs` 提供和用户操作一致的写法：

```js
const {robotAction, addRobotWay} = require('./robots_page_helper.cjs');
await robotAction(card, 'engine-ssh-edit').click();   // 在卡片上就直接点，在列表里就先打开列表
await addRobotWay(page, 'engine-ssh');                // 没有机器人时在页面上点，有了以后先点「添加机器人」
```

## 机器人的对话框（第二部分）

卡片上的每个按钮后面是一个对话框。它们原来各写各的：标题有三种写法（机器人名当标题、「功能 · 机器人名」、功能当标题而机器人名在下面），操作按钮有的在底栏、有的在内容末尾，长的对话框要滚到底才看得到按钮。现在是一个框架：

- **标题**：标题是这个对话框做什么（和打开它的按钮同名，「真机状态」改叫「实时状态」），下面一行先是机器人名（一个小标签），再是原来的说明。
- **切换行**：从卡片打开实时状态、设备档案、硬件初始化、配置连接、管理层（接入或安装）时，标题下面有一行「实时状态 · 设备档案 · 硬件 · 连接 · 管理层」，点一下换到这台机器人的另一个对话框，不用先关掉。只列卡片上此刻有的功能。验证连接、开机自启、删除这类一次性的操作和确认没有这一行。
- **头和操作固定**：内容滚动时标题和切换行留在上面，底栏留在下面；硬件初始化、验证 SSH 连接原来写在内容末尾的按钮也在同样的底栏里，主要操作在最右边。

做法和页面一样，不改各功能的脚本。`web/robot_dialogs.js` 在所有脚本加载完之后站到 `dialog()` 前面：`rdHead(title, sub, names)` 从标题和副标题里认出机器人名（按 `state.robots` 里的名字），认不出的对话框原样通过。SSH 表单是打开之后自己改标题文字的，由一个 `MutationObserver` 照同样的规则再写一次（只处理纯文字的标题，不动带标记的）。固定的头和底栏是 `web/robot_dialogs.css`，滚动的仍然是 `<dialog>` 本身（各功能重画时保存的 `scrollTop` 照常有效）。

以后新增机器人的对话框：标题按上面三种写法里的任何一种带上机器人名，就会得到同样的头；想进切换行，在 `RD_NAV` 里加上它的 `data-action`；内容末尾的操作行想进底栏，用 `.dialog-footer`。

测试：`node tests/robot_dialogs_logic.cjs`（标题的识别、切换行）；`node tests/robot_dialogs_browser.cjs <fixture-config.json> [截图目录]`（fixture 同上，Chromium 和 WebKit）。
