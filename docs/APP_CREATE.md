# 机器人应用页面：只展示应用，创建时选任务和品牌型号（issue #68）

更新：2026-11-27。对应 GitHub issue #68「机器人应用页面」：

> 机器人应用页面展示已经创建的应用，如果没有就是空
>
> 点击创建，需要绑定给对应任务和机器人的品牌型号，然后编排技能。技能默认不用安装，已经是安装好的状态（对应品牌型号）。

> 状态：代码和测试完成；**没有在任何真机上运行过**，也还没有合并。验证范围见[最后一节](#在哪里验证过哪里没有)。

用户在 issue 会话里定的三件事（2026-11-27）：

1. **页面只留应用和「创建应用」**：去掉「正在为任务…准备应用」的提示条、品牌型号筛选条、右上角「技能」按钮和「先把技能加进来」的引导。没有应用时只写「还没有应用」。
2. **任务必选**：创建表单先选任务，再选品牌型号；任务已经定了品牌型号时，品牌型号跟着任务定、不能改。保存后应用自动绑定到这个任务。
3. **这个品牌型号的全部技能都可以直接选**：它的机器人上已有的技能，加上随应用提供、适用于它的技能库，不用先安装，也不用「加入项目」。机器人上还没有的，在做现场测试（仿真机器人是仿真测试）前由系统自动装上。

### 创建表单

- **任务**：必选。从任务过来的，或者账号里只有一个任务的，已经选好；否则是「请选择任务」，不选不能保存。还没有任务时，「创建应用」先让人去新建任务；还没有机器人时，让人去「我的机器人」。
- **品牌型号**：账号里机器人的每个品牌型号一项（issue #60 的写法）。所选任务已经有品牌型号（任务的机器人，或者它绑定的第一个应用，issue #50、#42 的规则）时，只能是那个品牌型号，字段下面写明「品牌型号跟着任务定」；账号里没有那个品牌型号的机器人时，写明先去添加，保存按钮不可用。
- **技能**：选了品牌型号，表单向服务端要一次这个品牌型号的技能（「正在准备这个品牌型号的技能…」），然后写明「这个品牌型号有 N 个技能可以直接选用，不用先安装」。这个品牌型号的机器人都没有连接时读不到技能，表单写明先连接一台。
- 「修改工作流」（新版本）的表单同样能选这个品牌型号的全部技能；它没有任务这一项（新版本沿用应用已有的绑定）。

## 技能从哪里来，什么时候装到机器人上

`model-skills/ready`（`brainos/model_skills.py` 的 `ModelSkills.ready`），参数是代表这个品牌型号的那台机器人：

1. 找出账号里同品牌型号、已连接的机器人，逐台读它上面已安装的技能（设备的 `GET /v2/skills`）。读不到的机器人记在返回的 `unread` 里，不影响其余的。
2. 随应用提供的技能库（`runtime/examples/skills`，就是「安装技能包」对话框里的示例技能）里，和这个品牌型号的能力清单对得上的，也算。对不上的（例如机械臂的「挥手」之于四足）不算。技能包还要属于这个品牌型号或者是通用的（issue #69，归属表 `runtime/examples/skills/products.json`，见 [SKILL_PRODUCTS.md](SKILL_PRODUCTS.md)）：比如「巡逻」只属于 NeuxMind 示例 通用四足，宇树 Go2 的创建表单里就没有它，现场测试也不会去装它。（合并会话在合并 #68 和 #69 时补的。）
3. 上面两类里还没有技能记录的，各建一条（和原来「加入项目」建的记录一模一样，带这个品牌型号）。同一个技能（标识和版本相同）只建一次，再要一次不会多出来。同名不同版本的技能在步骤里写成「名称 · v版本」。
4. 设备对某一个技能的说明不完整（名称过长、没有写需要的能力等）建不了记录时，跳过这一个，记在返回的 `skipped` 里，表单写明哪几个没有列出；其余的照常。
5. 机器人还没有填写品牌型号时什么都不建（建出来的记录不属于任何品牌型号，会出现在别的机器人的表单里）：表单写明先去填写品牌型号。

这一步只读设备，不向设备发任何会改变它的请求。

**装到机器人上**：现场测试（`onsite_test`）里，应用通过了配置检查、设备的能力清单核对过之后，在请设备做执行前检查之前，先看这台机器人上有没有应用每一步的技能；没有、而技能库里有的，用「安装技能包」同一条路径装上（兼容性检查、操作记录都照旧），再往下走。机器人上已经有这个技能的任何版本时不动它；技能库里没有的（手动登记的），留给设备自己的执行前检查去说。自动安装没成功时，现场测试停下并说明是哪个技能、为什么（错误码 `skill_auto_install_failed`）；安装的回答丢了、但再读设备时技能已经在上面的，算装上了。配置检查没通过的应用什么都不装。真机和仿真机器人一样会被装上（现场测试本来就要人确认现场条件）。

发布不需要再装：发布要求同一台机器人上通过的现场测试，那时已经装过。

## 创建并绑定

`model-skills/create`（`ModelSkills.create`）：参数是原来创建应用的参数加 `task_id`。在一把锁里依次：确认任务存在、确认任务的品牌型号和所选的一致（不一致报 `task_other_model`，什么都不建）、建应用、绑定；绑定这一步出错时把刚建的应用删掉再报错。没有 `task_id` 报 `app_task_required`。

原来的 `applications` 接口没有改（测试和别的调用方照旧可以不带任务创建）；页面在创建表单里把这一次请求换成 `model-skills/create`。

## 对已有浏览器验收脚本的影响

见分支交付说明。原则：

- 创建应用的表单多了必选的 `task_id`：账号里只有一个任务时已经选好，脚本不用改；有多个任务、或者没有任务的脚本，要先选任务（或先建一个任务）。
- 表单打开后要等技能准备好（`.ac-status` 里出现「个技能可以直接选用」）再选技能。
- 「机器人应用」上没有「技能」按钮、筛选条和提示条了；要去技能页面的脚本直接打开 `#app-skills`。

## 在哪里验证过，哪里没有

见分支交付说明里的测试结果。没有验证的：

- 真机。自动安装走的是「安装技能包」原来的请求（`/v2/skills/install`），只在仿真本体的管理层上跑过。
- 打包后的桌面 app（WKWebView）：只在 Playwright 的浏览器上跑过。
- 小黄鸭（Microduck AD-P102）的技能：这个工作区里没有它的模型包（按设计不进仓库），没有跑到。它的技能是装在仿真机器人上的，走的是「读机器人上已有的技能」这一条。

## 这一版没有做的

- 任务和应用的品牌型号规则没有改（issue #50、#42）。
- 技能页面、手动登记技能没有删，也没有新的入口。
- 云端技能版本（issue #43 的「技能加载」）不算在“这个品牌型号的全部技能”里：只算机器人上已有的和随应用提供的。
- 一个品牌型号的机器人都没有连接时，读不到它的技能，也判断不了技能库里哪些适用：这时只能选以前已经有记录的技能。
