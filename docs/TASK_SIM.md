# 仿真试运行按任务来做（issue #66）

更新：2026-11-27。对应 GitHub issue #66「仿真机器人」：

> 仿真机器人页面是针对任务进行仿真演示。在这个场景，直接选择任务就可以，他需要自己构建仿真环境和场景。构建一次保存，可以永久使用。节点主页面实际上是选择任务，然后进入仿真机器人和环境，进行展示
>
> 并且在仿真环境中运行对应技能

> 状态：代码和测试完成，在本机用真实的宇树 Go2 模型在浏览器里走通（Chromium）。**没有和任何真机对比过；仿真里的行走不是物理的**（见 [MUJOCO_SIM.md](MUJOCO_SIM.md)）。验证范围见[最后一节](#在哪里验证过哪里没有)。

## 我对这段话的理解

issue 没有逐条写规则，下面是我的理解，做成了现在的样子；哪一条不对，改起来都不大。

| issue 里的话 | 做成了什么 |
|---|---|
| 主页面实际上是选择任务 | 「仿真试运行」页面只列出账号的任务，每个任务一张卡片；原来页面上的「添加仿真机器人」「你的仿真机器人」「仿真研发闭环」「场景资产」「仿真任务」都不在这个页面了 |
| 直接选择任务就可以 | 不用再选类型、品牌、型号：任务的品牌型号（issue #50）决定仿真哪一种机器人 |
| 他需要自己构建仿真环境和场景 | 「他」理解为系统：由工程助手按任务的说明和任务绑定的应用的步骤写出环境（地点、障碍、要推要抓的物体）；也可以先用只有地面的空场地 |
| 构建一次保存，可以永久使用 | 构建通过检查后直接保存在任务上，不再要人逐个「确认可用」；以后每次都是直接「进入仿真」。重新构建失败时，已保存的那一个不动 |
| 进入仿真机器人和环境，进行展示 | 任务有一台自己的仿真机器人，进入时在保存的环境里启动；页面上是实时画面、它在做什么、「停止」 |
| 在仿真环境中运行对应技能 | 「对应技能」理解为任务绑定的应用的步骤用到的技能：进入时自动装到仿真机器人上，页面上每个技能有「运行」，参数先填好应用那一步的值 |

## 规则

1. **一个任务一个仿真环境、一台仿真机器人。** 环境记在任务上（记录 `task_sims`），仿真机器人和其他机器人一样属于账号，出现在「我的机器人」里，名字是「任务名 仿真」，记着它是哪个任务的（`sim.task_id`）。
2. **仿真什么由任务的品牌型号决定**（任务选的机器人的，否则是它最早绑定的应用的，见 [TASK_APPS.md](TASK_APPS.md)）。还没有品牌型号的任务不能仿真，页面写明要先绑定应用或选择机器人。
3. **机器人模型从哪里来**，按顺序找：

   | 这个品牌型号是 | 怎么仿真 | 要不要构建环境 |
   |---|---|---|
   | 内置档案里的型号，安装包里有它的模型（issue #54） | MuJoCo，用档案的模型和站立姿态 | 要 |
   | 不在档案里，或安装包里没有它的模型，但资料库里有确认「可用」的机器人模型（issue #51） | MuJoCo，用资料库的模型 | 要 |
   | NeuxMind 示例的两款 | 应用原有的示例仿真，没有三维画面，页面显示俯视图或关节 | 不要，直接进入 |
   | Microduck AD-P102（issue #63） | 小鸭自己的仿真和技能模型 | 不要，直接进入 |
   | 都不是 | 不能仿真，页面写明缺什么，并给出「去资料库」 | — |

   同一个品牌型号的不同写法算同一个（`zs / L2U` 就是「智身科技 钢镚 L2-U」，和 issue #54 一致）。
4. **构建**：「让工程助手构建」要勾选同意（和其他工程会话一样），要有可用的模型算力；它是一次普通的工程会话，页面上可以「查看过程」，可以「取消这次构建」。「先用空场地」不用助手。两种都要在子进程里用 MuJoCo 建一次、画出预览，通过了才保存。一个任务同时只有一次构建。
5. **保存的环境一直用**，直到重新构建成功（旧的被替换）或「删除环境」。重新构建失败、被取消、应用中途退出：已保存的不变，页面写明这一次为什么没成。
6. **重新构建成功后**，任务的仿真机器人换到新环境里（正在运行就重启一次），装在它上面的技能保留。
7. **任务换了品牌型号**（解除了全部应用又绑了别的）：已保存的环境标为「品牌型号变了，需要重新构建」，不能进入；重新构建后，旧的那台仿真机器人删除，进入时按新的品牌型号新建。
8. **进入仿真**：第一次新建并启动仿真机器人（MuJoCo 要先建模型，可能一两分钟），以后是启动已有的那一台；被关闭的会重新启动，在「我的机器人」里被删除的会重新建一台。
9. **技能**：任务绑定的应用的每一步用到的技能，按步骤的顺序列出。进入时，这台电脑上有技能包的（随应用带的示例技能，或以前安装时用过、现在还在的技能文件夹）自动安装；没有技能包的写明，并给出「从文件夹安装」。运行走原有的路径（勾选授权 → `robots/run-skill`），参数先填好应用那一步的值，可以改；一个技能在应用里用了几次，就有几个「按第 n 步运行」。任务的应用没用到、但装在这台仿真机器人上的技能也列出来，可以运行。
10. **小鸭**：没有运行时技能，列出的是它的技能模型（issue #63 的规则：节目不走运行时的技能通道），「运行」就是让它表演。
11. **停止**立即发出并锁存急停（和「实时状态」里的一样）；页面写明急停已锁存，给出「解除急停」，锁存期间不能运行技能。「关闭仿真」只停掉进程，环境和技能都留着。
12. **删除任务**时，它的仿真环境、预览图和仿真机器人一起删除。
13. 仿真结果只说明逻辑是否正确，**不是现场证据**，这一点没有变。

## 没有改的

- issue #51 的「应用的仿真环境」（交付清单里的入口，人确认后启动）照旧。
- 「添加仿真机器人」（按类型、品牌、型号，issue #54）照旧，在「我的机器人」里。
- 「实时状态」对话框照旧；任务页面上的「详细状态」打开的就是它。
- 接外部仿真引擎的「仿真任务」（执行服务、场景登记）的代码没有动，只是**不再从这个页面进入**；「自有服务」页面在 issue #49 已经隐藏。`web/app.js` 的 `simulation()` 和 `web/ux02.js` 的 `simWorkbench()` 现在没有页面使用，要不要删留给以后。

## 接口

桌面端后台（`brainos/task_sim.py`；都是 POST、JSON，`project_id` 是任务）：

| 路径 | 作用 |
|---|---|
| `task-sim/list` `{}` | 每个任务：品牌型号、绑定的应用、怎么仿真（`model`）或为什么不能（`problem`）、保存的环境、正在进行或失败的构建、仿真机器人 |
| `task-sim/view` `{project_id}` | 一个任务，另有可以运行的技能（`skills`）或技能模型（`shows`） |
| `task-sim/build` `{project_id, mode: agent \| empty, note?, data_authorized?, model_id?}` | 构建；不用构建的型号直接保存为「自带场地」 |
| `task-sim/cancel` `{project_id}` | 放弃正在进行的构建 |
| `task-sim/remove` `{project_id}` | 删除环境和仿真机器人（构建进行中拒绝） |
| `task-sim/enter` `{project_id}` | 启动仿真机器人，安装任务的技能；返回 `view` 加 `installed_now` |
| `task-sim/install` `{project_id, skill_id}` | 把一个技能装到任务的仿真机器人上 |

预览图：`GET /api/sim/mujoco/preview?id=<环境编号>`（和 issue #51 同一个地址；只给自己工作区里记录着的编号）。实时画面、状态、运行、停止用的是仿真机器人原有的接口。

新的错误码（说明在 `web/ux04_errors.js`）：`task_sim_no_product`、`task_sim_not_built`、`task_sim_no_package`。

## 在哪里验证过，哪里没有

见提交说明和交付记录里的测试结果；这里只写范围。

验证过（2026-11-27，这台 Mac，MuJoCo 4.0.1）：

- 浏览器里（Chromium）：任务列表 → 选任务 → 没同意时助手构建被拒绝 → 空场地构建并保存、预览图出来 → 进入仿真、出现实时画面（真实的宇树 Go2 模型）→ 技能已自动安装 → 运行「巡逻」并在页面上看到进度和完成 → 停止后显示急停已锁存 → 刷新页面后不用再构建 → 窄屏不溢出 → 回到列表显示已保存 → 关闭仿真 → 删除环境。
- 单元测试里：工程助手（替身）写的环境被保存、机器人认得环境里的地点；不合格式的环境构建失败；取消；重新构建后机器人保留技能；失败的构建不影响已保存的；品牌型号变了标为需要重建；示例四足和小鸭直接进入；删除任务带走仿真机器人。

没有验证的：

- **真的大模型写的环境**：格式和建模的检查都在，但写得合不合用只有人看。原来有「确认可用」这一步，现在构建通过检查就保存；觉得不对就「重新构建」。
- 资料库里的机器人模型这条路径在这个页面上没有单独跑过浏览器（规则和 issue #51 共用，单元测试只覆盖了内置档案的模型）。
- 打包后的应用、DMG 安装后的应用；Intel Mac、Linux。
- 和真机的对比。

已知的限制：

- 任务的仿真机器人和其他仿真机器人一样，应用关闭时在运行的，下次打开会自动恢复；任务多的时候会同时起多个仿真进程。
- 环境保存后不能改，只能重新构建。
- 技能包只认示例技能和以前安装过的文件夹；从云端「技能加载」装过的技能，进入时不会自动装到仿真机器人上，要在页面上点「安装技能」。
- 随应用带的示例技能包按品牌型号归属（issue #69，[SKILL_PRODUCTS.md](SKILL_PRODUCTS.md)）：任务的仿真机器人和同品牌型号的真机一样，只能装属于这个品牌型号的包和通用包。任务的应用用到别的品牌型号的示例技能（比如宇树 Go2 的任务用了「巡逻」）时，进入仿真照样进入，这个技能显示没有装上，并写明它属于哪个品牌型号。（合并会话在合并 #66 和 #69 时补的。）
- 运行的是单个技能，不是按应用的步骤整条跑；整条应用的仿真测试仍在应用的交付清单里。
