两件事：**收集什么数据**（下面第一节，是这次的规划），和**怎么展示**（第二节）。

## 一、数据规划：一个任务从接入到部署，每一步记什么

以「巡检」为例，一个任务走五步。每一步现在记了什么、这次新收集什么、还没有收集什么：

| 步骤 | 已经在记的（这次之前） | 这次新收集的 | 还没有收集（没有做） |
|---|---|---|---|
| 1 接入机器人 | 机器人记录（接入时间、连接状态、品牌型号、能力清单）；SSH 连接；最近一次心跳；硬件扫描和修复记录；设备档案 | — | 连接和心跳的**历史**（现在只有最近一次）；「验证连接」的结果只在事件里 |
| 2 安装技能 | 管理层安装的**最近一次**结果；每次安装技能包是一条操作记录（技能、版本、摘要、结果） | — | 管理层安装的历史；安装用了多久（记录里只有发出时间） |
| 3 仿真试运行 | 仿真机器人；仿真环境；在仿真机器人上「运行技能」的请求；仿真测试报告 | **每次运行的过程和结果**（见下） | 仿真画面的录像 |
| 4 真机测试 | 静态检查报告；现场测试的请求和报告（每一步通过与否）；在真机上「运行技能」的请求 | **每次运行的过程和结果**（见下） | 现场的视频、传感器原始数据 |
| 5 部署运行 | 发布记录；启动、停止、解除急停的请求 | **每次启动之后这次工作的过程和结果**（见下） | 长期运行的统计（每天几次、平均用时）要等记录积累后再做 |

这次之前最大的缺口在 3、4、5：平台只记到“设备已受理”。**这次运行后来怎样了、用了多久、哪一步失败、机器人走到了哪里，都只留在设备上**，页面上看不到，设备重启或换机器后也就没有了。

### 这次新收集的：一次运行的记录

三种请求会让机器人运行：直接运行技能、现场测试（含仿真测试）、启动已发布的应用。每一个请求（操作记录）对应一条运行记录，由 `brainos/run_records.py` 从设备读回来存在这台电脑上（完整的一份是 `run_record_data`，给列表用的不带采样和事件的小记录是 `run_records`）：

| 内容 | 说明 |
|---|---|
| 怎么结束的 | 设备给的状态（完成、失败、被停止、超时）、停止原因、错误信息 |
| 时间 | 开始、结束、用时 |
| 步骤 | 应用的每一步用的技能和结果；现场测试的每一项 |
| 技能返回的结果 | 技能自己返回的内容（例如巡检到了哪些地点） |
| 事件 | 设备记下的这次运行的事件：开始、步骤开始/结束、进度、日志、收到停止请求、出错、结束（最多 300 条） |
| **采样** | 运行过程中大约每秒一次：位置（x、y）、朝向、速度、电量、进度。这是产品里唯一的时间序列 |
| 走过的距离 | 按采样到的位置算出来的 |

几条规则：

- **只读**。跟随一次运行只读设备的 `/v2/state` 和 `/v2/runs/<id>`，不发任何会让机器人动或改变它的请求。
- **什么时候开始收集**：请求被设备受理的那一刻（运行技能、现场测试、启动工作各自的审计记录）；三个页面打开时也会检查有没有正在进行、还没人跟的运行。
- **长时间运行**：最多 600 个采样点。超过后每隔一个丢一个、采样间隔加倍，所以整次运行始终都有覆盖，只是变稀。最多跟两小时。
- **读不到设备**：连续 30 次读不到就停止，记录写明“后面的数据没有收集到”，列表里这一行写「结果没有收集到」（不会一直停在「运行中」）。应用退出时正在跟的运行同样写明。之后打开这条记录时会向设备补读一次结果，已有的采样保留。
- **结果的大小**：技能返回的结果超过两万个字符时只保留开头并标明被截断；不是有限数字的值记为空。列表一次最多给最新的 500 条。
- **这次之前的运行、应用关着时结束的运行**：打开它的记录时向设备读回一次，有结果和事件，**没有采样**，记录里写明。设备上也没有了的，页面写“这次运行的数据没有收集到”和原因，不显示任何推测的数字。
- **不进 `/api/state`**。跟随时记录每秒都在变，而界面在 `/api/state` 变化时会重画整页；页面用 `runs/records`（列表，不带采样和事件）和 `runs/record`（一条的全部）另外取。
- **开关**：只有应用的入口（`brainos.server` 的 `main()`）打开收集；环境变量 `NEUXMIND_RUN_FOLLOW=0` 可以关掉。测试里直接建的 `Platform` 默认不收集，所以数设备收到了几个请求的测试不受影响。
- 删除机器人时，它的操作记录原来就留着，运行记录也一样留着。

## 二、展示

三个页面都改成“上面一块数字板，下面一张记录列表，点一行打开这条记录的页面”，样子跟工作台首页一致。只显示记录下来的数据，没有示例数据；没有记录时写明以后这里会列出什么。

### 数字板

左边是总数（大字），中间是结果分布（完成/通过、失败/缺项、被停止、进行中、待核对，一条按比例分段的色条加图例），右边三个数：通过率、累计运行时间（和走过的距离）、最近一次的时间（和涉及几台机器人）。

### 记录列表

每条记录一行：记录是什么（运行技能、现场测试、静态工程检查…；仿真的带「仿真」标记）、对象（技能或应用）、机器人和所属任务、结果、运行数据（用时 · 距离 · 步骤通过数）、时间。整行可以点，行尾有「查看」按钮（键盘用它）。列表上方可以按任务筛选（只列出有记录的任务；选择记在浏览器会话里）。

记录属于哪个任务：记录的应用被哪些任务绑定了（任一版本），就属于哪些任务；直接运行技能的记录，属于选了这台机器人的任务。

| 页面 | 列出什么 |
|---|---|
| 仿真试运行 `#simulation` | 在仿真机器人上的运行和仿真测试。**这一页原来的内容不动**：数字板插在页头下面，记录列表接在页面最下面（见下面“和 issue #66 的关系”） |
| 验证与测试 `#harness` | 静态检查、现场测试、仿真测试（标「仿真」，写明不能作为现场证据）、在真机上直接运行技能。页头保留三个操作：外部测试任务、发起现场测试、运行应用检查。有外部测试任务时，它们的表格在最下面 |
| 部署与运行 `#deployment` | 上面是发布版本的列表（应用、状态、发布时间、启动过几次和最近一次的结果；行内保留「启动工作」「请求停止」，急停锁存时的提示也在行内）；下面是发给机器人的**每一个**请求（安装技能包、运行技能、现场测试、启动、停止、解除急停），新的在前 |

仿真机器人的说明块（“你现在只有仿真机器人…”）在验证与测试、部署与运行两页照旧，位置从页头下面挪到了数字板下面。

### 一条记录的页面 `#record`

从上到下，没有数据的部分不画：

0. 读取失败时有「再读一次」。
1. 「← 回到来的那个列表」；记录的名称（例如“运行技能 · patrol_places”）、结果、仿真标记。
2. 一排数字：机器人（和任务）、发出时间、用时（和停止原因）、走过的距离、步骤通过数。
3. 出错信息；没有收集到数据时的说明；正在运行时写“正在运行，数据每两秒更新一次”。
4. **这台机器人走到了哪一步**：接入机器人 → 安装技能 → 仿真试运行 → 真机测试 → 部署运行，每一步写做了几次、几次成功和最近一次的时间。仿真那一步把同一个应用、同一个品牌型号的仿真记录也算上，所以在真机的记录里能看到它之前在仿真里跑过几次。
5. **运行过程**：左边是路线图（按采样的位置画，上北右东的平面图，带起点、终点和比例尺），右边是速度、电量、进度随时间的曲线，各带最小值和最大值。
6. 步骤（应用的每一步，或测试的每一项）和结果。
7. 运行参数；技能返回的结果。
8. 设备记下的事件，带相对开始时间的秒数。
9. 折叠着的原始记录（操作记录、测试报告、收集到的运行数据）。

静态检查打开是检查的每一项；发布版本打开是它的数字、「启动工作」「请求停止」「发布所依据的测试」和这个版本的全部运行。

侧边栏亮着来的那个页面，页头路径写“验证与测试 / 记录”。刷新留在这条记录上。

### issue #75：「2 次运行 0 次成功」和「技能返回的结果」

用户在一条小鸭仿真的记录上看到「这台机器人走到了哪一步 → 仿真试运行：2 次，0 次完成」，而两次 `status_report` 其实都成功了；下面「技能返回的结果」里 `health` 画成了框中框，其他几行是英文名和 `true`。这台 Mac 上的数据（只读查过）是这样的：

| 那两次运行 | 当时的样子 |
|---|---|
| 11-27 13:10 那次 | 操作记录还是「已受理」，从来没有运行记录：它在应用关着时结束，之后也没人打开过它的页面，所以一直没读回来 |
| 11-27 13:18 那次 | 用户打开它的页面时才读回来（「这次运行结束之后才读回来」），运行记录是「已完成」；但页面上的标记、「走到了哪一步」用的是打开之前的列表，读回来以后列表变了，这一页却没有重画，于是还写「已受理」「0 次完成」 |

改了三处：

1. **列表也会读回没人跟着的运行**（`brainos/run_records.py`）：列表每次来要记录时，后台一个线程把「平台还以为在进行」的运行问一次设备（`GET /v2/runs/<id>`，只读）——跟丢了的（`lost`），和太旧、不会再被跟着的（超过 6 小时、没有记录的）。读到结束就和打开它的页面时一样存下（「这次运行结束之后才读回来」）；设备答不上的，5 分钟后（`SETTLE_RETRY_S`）再问。6 小时以内的照旧由跟着它的线程处理。
2. **记录页在列表变了时重画**（`web/run_boards.js` 的 `rbPoll`）：标记和「走到了哪一步」跟着最新的列表；打开的折叠、事件列表的滚动位置照旧保留。
3. **「走到了哪一步」把每一类都说出来**：「2 次：1 次完成，1 次待核对」「2 次：0 次通过，2 次失败」，完成（真机是「通过」）的次数总写，失败、被停止、进行中、待核对有才写。结果还没读回来的不再被算成「没完成」。用时不到 0.05 秒的写「不到 0.1 秒」，不写「0 秒」。

「技能返回的结果」和「运行参数」改成和上面事实一样的排法（`web/run_record_view.js` 的 `rrRows`）：一行一项，名称用中文（`health` → 系统健康、`ok` → 正常、`mode` → 模式、`family` → 本体类型、`available` → 读到的状态 ……，表里没有的用 `web/readable.js` 的名称，再没有就照设备写的），嵌套的值拆成「系统健康 · 正常」这样的行，列表里的对象写「第 1 项 · …」，`true/false` 写「是/否」，空的写「无」，`sim:stand` 写「仿真里站着待命」，本体类型用页面上的类型名。最多 80 行，多的写明还有几项、去「收集到的运行数据」里看。

没有改的：设备报告的内容本身。小鸭的仿真身体仍然报告 `family: humanoid`（issue #65 只改了应用里的类型「其他」），所以 `status_report` 在小鸭上会显示「本体类型 人形机器人」。

在合并后的代码（两个 issue 都在）上跑过 #66 的 `task_sim_browser`、`ux02`、`ux03`、`planner` 和本 issue 的浏览器脚本（Chromium、WebKit），都通过；任务页顶上不再有数字板（看过截图）。**任务页最下面那张列表没有断言覆盖，也没有截到图。**

## 怎么实现的

- 新增 `brainos/run_records.py`：`RunRecords`（`platform.run_records`）。包了一层 `platform.audit`，在 `skill.run`、`onsite.requested`、`robot.start` 三种审计记录之后检查有没有要跟的运行；每个运行一个后台线程。接口 `runs/records`、`runs/record`。
- `brainos/service.py` 两行（建立、关闭），`brainos/server.py` 四行（导入、静态文件、两个接口、入口处打开收集）。没有改任何已有的函数。
- 新增 `web/run_boards.js`（三个页面的数字板和列表）、`web/run_record_view.js`（一条记录的页面和图）、`web/run_boards.css`。接管 `views.harness`、`views.deployment`，新增 `views.record`；`#simulation` 只在画完之后接上一块。图是页面自己画的 SVG，没有引入图表库。
- 原来这三页的操作（`harness-pick`、`onsite-pick`、`deploy-pick`、`operate-start`、`operate-stop`、`job-evaluation`）和它们打开的对话框都没有改。原来的「报告」「记录」「详情」按钮换成了「查看」（打开记录页面）；`detail-evaluations` 等动作本身还在，别处仍可用。

## 测试

- `tests/test_run_records.py`（25 个）：采样、稀疏化、距离、步骤和事件的整理；默认不收集；一次运行跟到结束并保存；受理请求即开始；应用运行的步骤；现场测试跟到操作结束；设备不再回答；旧的和已结束的不跟；读回一次且只读一次；没有数据时说明原因；退出时的标记；页面文件有被提供和加载；开始跟之前就已结束的运行只读回结果、不记当前的采样；结果里的非有限数字和过长的结果；稀疏化不让距离变短；中断过的记录在打开时补上结果；没有设备地址的机器人不反复重试；收集出错不影响已经发出的请求。
- `tests/run_boards_logic.cjs`（63 项）：记录列表怎么从已有数据拼出来、各页列什么、属于哪个任务、数字板、五个步骤、路线和曲线的坐标。
- `tests/run_boards_browser.cjs` + `tests/run_boards_browser_fixture.py`：浏览器里真的加一台仿真四足机器人、装「巡检」技能并运行，看到这一行从「运行中」变成「已完成」并带上用时和距离；打开记录页面看到五个步骤、路线、曲线、事件；刷新、返回；部署与运行里两条请求；375 / 768 / 1440 三个宽度都没有横向溢出。

## 在哪里验证过，哪里没有

- 验证过：仿真四足机器人上的「巡检」（真实的管理层进程 + 仿真本体），Chromium 和 WebKit（桌面应用用的引擎）各跑通一遍。
- 经过这三个页面的 12 个原有浏览器脚本在改完后的代码上全部通过（Chromium）：`browser_smoke`、`delivery`、`desktop02`、`sim_reset`、`ux02`、`ux03`、`ux04`、`planner`、`hidden_pages`、`page_titles`、`style`、`journey`。`engineering`、`extensions` 两个第一次在机器负载很高时超时，重跑通过。
- 最接近的 11 个单元测试文件（171 个测试）通过。**整套桌面单元测试和其余浏览器脚本没有跑**（当时机器上其他会话在跑测试，负载过高），留给合并时统一跑。
- **没有验证**：任何真机；现场测试和「启动工作」的整条链路只在单元测试里用替身设备走过，没有在浏览器里带着真实管理层走过（需要一台能通过现场测试的非仿真机器人）。
- 真机经 SSH 转发访问管理层时，每秒两次读取的开销没有在真机上量过。
