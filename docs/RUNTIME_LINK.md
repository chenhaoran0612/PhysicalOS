# 经 SSH 通道访问管理层（issue #17，需求 R1-09）

机器人上的管理层（端侧运行时的网关，`runtime/`）只监听机器人本机的回环地址。以前桌面端要访问它，得有人在开发机上手工开 `ssh -L` 隧道，再把隧道的地址和令牌填进“配置连接”。现在桌面端自己经这台机器人已有的 SSH 连接（直连，或经多级跳板机）把请求送过去：不开隧道、不填地址，断了自己重连。

代码：`brainos/runtime_link.py`（接入、移除、状态、重试，和连接检查之间的锁）、`brainos/runtime_link_sessions.py`（每台机器人一条 SSH 会话、登录、重连、通道）、`brainos/runtime_forward.py`（HTTP 请求怎样走 SSH 通道）、`brainos/connector.py`（按地址的写法选择走法）。界面：`web/runtime_link.js`、`web/runtime_link.css`。

## 怎么用

1. 用“通过 SSH 调查真机”接入机器人（和以前一样）。
2. 在机器人卡片上点“接入管理层”。表单里只有两项：管理层端口（默认 8790，标准安装就是它）和令牌（可以留空）。点“接入并检查”。
3. 令牌留空时，平台登录机器人后读标准安装的令牌文件 `~/neuxmind/edge-token`（SSH 登录的账号要能读它）。管理层装在别的账号或目录时，在表单里手工填写令牌。
4. 保存后立即做一次连接检查（读清单和状态），通过后卡片显示“控制通道：已连接”和设备能力。卡片上多一行“管理层”，说明这条通道现在的状态。

接入以后，桌面端对这台机器人管理层的所有请求（连接检查、能力与技能、安装技能、安全限值、停止与解除急停、部署与运行……）都走这条通道，调用的地方没有改：机器人记录里的服务地址变成 `ssh-forward:<机器人 id>`，`connector.call` 认出这种写法后改走 SSH。

“管理层设置”里可以改端口、重新读或重新填令牌，也可以“移除接入”：SSH 连接保留，保存的令牌和经通道读到的清单删除，之后可以再接入。

## 通道只通到哪里

- **只通到机器人本机的一个端口。** 通道是 SSH 的 `direct-tcpip`，目标固定是机器人上的 `127.0.0.1:<端口>`。端口只能是 1024–65535 之间的整数（普通用户运行的管理层只能用这个范围），由人在表单里填写并保存在机器人记录里。接口不接受任何地址字段（`host`、`endpoint`、`address`、`target`、`url`，带上就拒绝）；服务地址 `ssh-forward:` 后面只认本工作空间里一台已接入的机器人的 id，其他任何内容都不会被当作主机、端口或路径。
- **这种服务地址不能手工填。** “添加机器人”、“配置连接”和“接入自己的服务”的服务地址仍然只接受 `http(s)://`，`ssh-forward:` 会被拒绝；记录被改过（端口不合法、记录里的服务地址指向别的机器人、机器人不再有 SSH 连接）时请求不会发出，报 `device_link_not_configured`。
- **本机什么都不监听。** 请求直接写进 SSH 通道，从通道读回应答，桌面端不为它打开任何本机端口：两台机器人的管理层都在 8790 也不会冲突，本机别的程序也连不进来。
- **令牌只发给接入时那台机器。** 接入时记下 SSH 连接的主机指纹；之后这台机器人的 SSH 连接被改到另一台机器（主机指纹不同）时，请求不再发出，卡片显示“需要重新接入”，重新接入时从新机器读令牌。打开通道之前还核对请求带的令牌仍是这台机器人现在保存的那个：按旧记录拼好的请求（期间重新接入过）不会把旧令牌带出去。令牌不出现在任何接口的返回、`/api/state`、操作记录和日志里，读令牌失败时设备输出的内容也不显示。
- **接入以后不能再手工填地址。** 对已接入的机器人，“配置连接”（`connections/configure`）拒绝改服务地址：令牌是从这台机器人读来的，不能跟着一个手填的地址发出去。要改成手工填地址，先“移除接入”。
- **管理层仍然只监听机器人的回环地址。** 不需要、也不应该把它改成 `--host 0.0.0.0`。

## 一条独立的 SSH 会话

每台接入的机器人有一条自己的 SSH 会话（`device_access.SSHDevice`，和其他功能一样逐级固定主机指纹），不和心跳（issue #24）共用：

- 一个大的请求（安装技能包、上传）不会让同一条 TCP 连接上的心跳排队等着；心跳放弃自己的会话时也不会切断正在进行的请求。测试里管理层故意不应答时，心跳照常在时限内完成。
- 机器人在不在线仍然只由心跳说了算；这条通道的状态单独显示在卡片的“管理层”一行。
- 每台机器人多一个 SSH 登录、一条长连接。会话空闲时每 15 秒发一次保活（防火墙不断开它，断了也能被发现）；10 分钟没有请求就关闭，下一个请求来时再连。

## 断开后自动重连

| 状态 | 什么时候 | 卡片上 |
| --- | --- | --- |
| 待连接（`idle`） | 刚接入还没用过，或者 10 分钟没用被关闭 | 灰色，“用到时自动连接” |
| 连接中（`connecting`） | 第一次登录进行中 | “正在建立 SSH 通道…” |
| 已连通（`up`） | 会话正常 | 绿色 |
| 已断开（`down`） | 会话断了或登录没成功，正在自动重连 | 红色，断开了多久、哪一跳什么原因、请求会怎样、“立即重试” |
| 登录被拒绝（`refused`） | 密码、私钥或主机指纹被拒绝 | 红色，已停止自动重连，“立即重试” |
| 需要重新接入（`moved`） | SSH 连接改到了另一台机器 | 红色，去“管理层设置”重新接入 |

- **谁来重连。** 会话断了以后，下一个请求会立刻重新登录一次（请求还有时间就等它连上再发）；没有请求时，定时器每秒看一眼，只要这条通道在 10 分钟内被用过（`KEEP_SECONDS`），就按间隔重新登录，网络恢复后不用任何人操作就回到“已连通”。
- **两次尝试之间的间隔** 从 2 秒开始逐次加倍，最长 30 秒（`retry_seconds`）。断开期间不管来多少请求，都不会每个请求各登录一次：它们等同一次登录，或者在时间不够等下一次时直接失败。登录成功、但会话不到 30 秒就断了（`STABLE_SECONDS`，例如设备的 sshd 每次登录后马上断开），也算一次失败，间隔照样加长：不会每秒登录一次。会话正常用了 30 秒以上再断，下一次立即重连。
- **TCP 连接卡死时。** 对端不再应答（网线断了、中间设备丢了状态）时，paramiko 往这条 TCP 连接里写数据会一直重试到内核放弃（约 15 分钟），任何时限都管不到它。所以每次写都有一个看门狗：卡住超过请求的时限（至少 30 秒，`STALL_SECONDS`）就关掉整条 SSH 会话，这个请求按“结果未知”结束，会话随后重新建立。一次请求和它的应答合计也有上限（请求时限 + 120 秒 + 按每秒 4 KB 算的上传时间）：机器人上监听那个端口的程序一字一字地回、或者没完没了地回 `100 Continue`，都占不住桌面端的线程。
- **不再需要的通道。** 已断开、10 分钟没有请求的通道不再自动重连，状态回到“待连接”，下一个请求来时再连。
- **连不上的请求怎样失败。** 在请求自己的时限内（大多是 8 秒）失败，错误码说明原因，并且都明确“这次请求没有发出”（`sent=False`）——机器人上什么都没有发生，不需要到现场核对：

  | 错误码 | 意思 |
  | --- | --- |
  | `device_link_down` | SSH 会话断了，正在自动重连 |
  | `device_link_slow` | 会话还在，但机器人没有在时限内应答通道请求或读令牌（网络很慢），或者它的 SSH 服务暂时打不开新通道，或者请求的时限在发出之前就用完了 |
  | `device_link_refused` | 登录被拒绝，已停止自动重连 |
  | `device_service_down` | SSH 正常，但机器人本机这个端口没有程序在监听（管理层没装或没启动） |
  | `device_forward_forbidden` | 机器人的 sshd 不允许转发（`AllowTcpForwarding no`） |
  | `device_link_not_configured` | 没有接入、接入已移除、记录不对，或者 SSH 连接改到了另一台机器 |
  | `runtime_token_not_found` | 接入时没有在机器人上读到令牌 |

  已经发出、半路断开的请求和直连时一样按“结果未知”报（`device_unreachable` / `device_timeout`，`sent=None`），不会自动重试；应答残缺或不是 HTTP（`http.client` 的异常）也按“结果未知”报，直连时同样（以前这种情况会变成桌面端的内部错误）。这些错误码在 `web/ux04_errors.js` 里都有白话说明。
- **被拒绝的登录不反复试。** 设备或跳板机拒绝登录（`auth`、`key`、`fingerprint`）以后不再自动登录，免得错误的密码把账号锁住，或让这台电脑被跳板机封禁。之后三种情况会再试：连接在“配置连接”里改过；心跳此后又登录成功了（说明问题已经解决）；有人点了“立即重试”（只试一次）。心跳刚被拒绝过的登录，通道也不会再去试；一台跳板机拒绝了某台机器人的登录，5 分钟内经过它的其他机器人的通道也先不去试。
- **和连接检查不会互相覆盖。** “连接检查”（`connect_robot`）读机器人记录、等设备应答、再整条写回；接入、改端口和移除接入跟同一台机器人的连接检查一次只做一个（每台机器人一把锁，`_wrap_record_writers`），检查写回的旧记录不会把刚移除的令牌带回来，也不会把刚改的端口改回去。别的“读记录 → 等设备 → 写回”的地方（能力与技能页读 v2 清单等）没有这把锁：那是这个项目原有的写法，这次没有改。
- **连接被改过或删掉。** 改过的连接（另一条路线、另一个登录）立即关闭旧会话，下一个请求按新的保存重新登录；删除机器人时会话一起关闭。这些通知来自 `StatusSessions.on_forget`，排在心跳的通知之后，不读写存储、不等设备（删除机器人时它在引擎的锁里被调用）。
- **应用退出** 时（`Platform.close`）关闭所有会话；还卡在登录里的线程是守护线程，登录结束后自己关闭会话，不保存任何东西。

## 接口

- `POST /api/robots/runtime-link`：`{project_id, robot_id, port?, token?}`。接入（或修改端口、令牌）并做一次连接检查，返回机器人（不含令牌）。检查没通过时接入仍然保存，错误照常返回；管理层启动以后点“连接检查”即可。
- `POST /api/robots/runtime-link/remove`：`{project_id, robot_id}`。
- `POST /api/robots/runtime-link/state`：`{}`。`{links: {机器人 id: {state, label, since, down_since, error, port, retry_in}}}`，只列已接入的机器人。这些内容随时间变化，所以不在 `/api/state` 快照里：页面每 5 秒单独问一次，只在原地改那一行，不重画页面（展开的说明不会合上，键盘焦点不会丢）。
- `POST /api/robots/runtime-link/retry`：`{project_id, robot_id}`。立刻登录一次（被拒绝后也试），最多等 45 秒，返回 `{robot_id, link}`。

机器人记录里新增 `runtime_link`：`{port, token_source（device / typed）, attached_at, fingerprint}`。`endpoint`、`token` 两个字段沿用原来的：其他代码不需要知道通道的存在。

**给 issue #19（在控制台里安装管理层）。** 安装步骤完成后调用 `platform.runtime_link.attach({'project_id', 'robot_id', 'port', 'token'})`：安装时生成了令牌就传进来；不传则按标准安装的令牌文件去读。安装改了端口（`NX_PORT`）时把端口一起传。`attach` 只依赖机器人已有的 SSH 连接，不要求设备上有别的东西。

## 弱网

需求的验收线：带宽 1 Mbit/s 以内、丢包 30%、时延 300 ms 以上时最终完成；丢包 60% 时不要求完成，只要求网络恢复后能继续。

在 Linux 容器里用 `tc netem` 只给桌面端到机器人的 SSH 连接加限制（双向，每个方向 300 ms，往返 600 ms；机器人本机回环上 SSH 服务到管理层那一段不受影响），两端都是本机替身（`tests/runtime_link_support.py` 的 `LoopbackDevice` 和 `tests/management_fixture.py`），心跳同时在运行。脚本是 `tests/runtime_link_weak_network.py`（不在任何套件里，只能在 Linux 上以 NET_ADMIN 运行，怎么跑写在文件开头）。2026-11-21 的结果：

- **1 Mbit/s、丢包 30%：** 移除接入后从头接入（登录、读令牌、连接检查）第一次就成功，用了 19 秒。小请求（读状态）2–14 秒完成；按控制台自己的 8 秒时限，4 次里 3 次成功，没成功的那次按“结果未知”报。中途把机器人上的 SSH 会话全部断掉，56 秒后自己连回来，这期间的请求都报“没有发出”（`device_link_down`）。一次 200 KB 的请求完成不了：这样的链路上 TCP 每秒只能送出几 KB，它在 286–322 秒时按“结果未知”结束（`device_timeout`），不再像修改前那样卡住十几分钟；大文件应走 issue #18 的可续传通道。
- **再跑一次，32 KB 的请求在单独的线程里连续发，读状态的请求同时进行（丢包 30%，7 分钟）：** 这次从头接入试了 10 次、174 秒才成功（读令牌的那条命令在这样的链路上屡次超时，会话被换掉后成功）；同样的条件第一次跑时一次就成功，差别在丢包落在哪里。32 KB 的请求 9 个里 7 个完成，每个 16–61 秒，另外 2 个按“结果未知”结束（其中一个正赶上把会话断掉）。大请求进行时，同一条通道上的小请求排在它后面：按 8 秒时限的读状态 9 次只成功 1 次，不限时的都在 6–55 秒内完成。心跳有自己的会话，不受这条通道上排队的影响（单元测试里验证，这次没有单独计时）。会话断掉后 27 秒自己连回来；60% 丢包 2 分钟后网络恢复，30 秒后请求重新通过。
- **丢包 60%（5 分钟）：** 51 个请求全部失败，都是“没有发出”（`device_link_down`），状态在“已断开（超时 / 连不上）”之间，不要求完成。
- **恢复：** 网络恢复后没有任何人操作，28 秒后请求重新通过（最长等一次 30 秒的重连间隔）。
- 全程没有一个请求以“已发出”失败，也没有一个请求以意外的异常结束。

- `tests/test_runtime_link_reconnect.py`：会话断了下一个请求重新登录；断开期间请求很快失败并说明没有发出；网络恢复后没有请求也自己回到“已连通”；会话死掉时定时器自己换一条；断开期间多个请求不各自登录；间隔逐次加倍且有上限；半路断开的请求报结果未知；空闲关闭后按需再连；被拒绝的登录不重复、点“立即重试”再试一次、心跳刚被拒绝的不再试、心跳再次成功后恢复；主机指纹不对时不登录、不发令牌；管理层慢的时候心跳不受影响、两边各有会话、心跳失败不关通道；改连接、连接改到另一台机器、删除机器人、关闭工作空间。

- `tests/test_runtime_link_http.py`：四个接口经 HTTP 的往返、错误码、未登录不能用、页面引入了脚本和样式；`node tests/runtime_link_logic.cjs`（页面逻辑，含转义）。
- 浏览器验收：`tests/runtime_link_browser.cjs` 配 `tests/runtime_link_browser_fixture.py`（夹具自己建临时目录，要 `NEUXMIND_MAIL_DEV_ECHO=1`）。从 SSH 接入开始，表单里没有地址；一次提交读到令牌、连接检查通过；断网后卡片原地变成“已断开”并说明原因，请求报“没有发出”；恢复后不点任何东西回到“已连通”；登录被拒绝后不再自动重连，点“立即重试”恢复；只有管理层没启动时报 `device_service_down`；移除接入后 SSH 连接还在。Chromium 和 WebKit 都跑过，含 390 px 宽度。

机器都是本机的 SSH 协议替身和 HTTP 替身，没有连真机。

## 还没有做的、没有验证的

- 没有在真机上验证。真机上现在仍是 2026-11-15 那次手工隧道的用法（见 `runtime/README.md` §0.4）。
- 令牌由人填写或从标准安装的令牌文件读取；由安装步骤生成并直接交给 `attach` 要等 issue #19。
- 心跳仍然来自 SSH 连接本身（issue #24），不是管理层的心跳；管理层没启动时卡片上心跳仍是“在线”，“管理层”一行和连接检查会说明管理层的问题。
- 定时器只照看 10 分钟内用过的通道；更久没用的在下一个请求时才重新连接（第一个请求要多等一次登录的时间）。
