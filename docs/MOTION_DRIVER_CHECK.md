# 运控驱动检查（issue #28，需求 R1-10 的检查部分）

更新：2026-11-21。代码在 `brainos/motion_drivers.py`、`spec/neuxmind_spec/ros2_interfaces.py`、`web/motion_drivers.js`、`web/motion_drivers.css`。

设备通过 SSH 接入、读过设备档案之后，平台按它的本体类型核对：这类本体的运控驱动应该提供的 ROS 2 话题和动作，在设备上在不在。缺少时平台指出缺的是哪一个接口、应有的话题（或动作）和消息类型，并可以把它交给修复助手。驱动齐全的设备不显示任何入口。

整个检查只读：不发布话题、不调用服务、不发送动作目标，也不改变机器人或平台上任何状态。**安装驱动不在这里**：放开修复助手安装和启动运控驱动的规则是 issue #29，让修复会话能查资料库是 #30，把安装包送到设备是 #31。

## 对照的是哪三样

三样都是已有的东西，检查本身没有新的读取。

| 是什么 | 从哪来 |
| --- | --- |
| 这类本体应有哪些运控接口 | 本体类型清单里该类型的 `required_capabilities`（issue #32，[BODY_TYPES.md](BODY_TYPES.md)）。内置四足：停止、底盘速度、足式姿态、里程计；内置机械臂：停止、关节状态、机械臂关节位置 |
| 每个标准接口对应哪个 ROS 2 话题或动作、什么消息类型 | 标准里的 ROS 2 接口表 `neuxmind_spec.ros2_interfaces`（本次新增，见 [specs/CAPABILITIES_V1.md](specs/CAPABILITIES_V1.md#ros-2-接口表issue-28)） |
| 设备上实际有什么 | 设备档案的 ROS 2 部分（issue #27，[DEVICE_PROFILE.md](DEVICE_PROFILE.md)）：话题和动作的名称与消息类型，由那条固定的只读命令读取 |

## 怎么判定

每个应有的接口得到一个状态：

| 状态 | 含义 |
| --- | --- |
| 在（`present`） | 清单里有消息类型对得上的话题（或动作）。**按类型认，名称可以不同**：真机常带命名空间或改过名，某台设备到底用哪个话题是设备接口表（issue #23）的事 |
| 清单里没有（`missing`） | 清单里没有这个类型的话题（或动作）。可能是运控驱动没有安装或没有在运行，也可能是本体不通过 ROS 2 标准接口运动，或者这一次根本没读到节点：见下面“不是故障” |
| 类型不对（`wrong_type`） | 惯用名称上有话题，但消息类型不是标准要求的（例如 `/cmd_vel` 上是 `TwistStamped`） |
| 核对不了（`unverified`） | 标准没有给这个接口规定 ROS 2 话题或动作。停止（`safety.stop`）靠运动接口实现（发零速度、取消动作）；足式姿态（`legged.posture`）各厂商做法不同。**核对不了的接口从不报成缺少**，界面上写明原因 |

整体结论（`status`）：

| 结论 | 什么时候 | 报不报问题 |
| --- | --- | --- |
| `ok` | 能核对的接口都在 | 不报，卡片上没有入口 |
| `missing` | 有接口缺少或类型不对 | 报 |
| `unlisted_type` | 设备的类型不在本体类型清单里（清单出现之前登记的旧取值）。平台不知道它该有什么，**不猜**：提示先把设备改成清单里的类型。改完后保存的档案立刻按新类型判定，不用重新读取 | 不报 |
| `nothing_to_check` | 类型应有的接口在标准里都没有 ROS 2 绑定（例如只要求“停止”的自定义类型）。这是对类型的结论，和读到什么无关 | 不报；别的类型留下的这类问题也随之消失 |
| `not_read` | 还没有读过设备档案，或连接被修改过（旧档案不再算这台设备的） | 不报新的；最近一次扫描里已有的保留（见“重新核对用 ROS 2 读取”） |
| `unknown` | 档案下不了结论：ROS 发行版不是 Humble（含 ROS 1）；话题清单没读全（命令超时、输出被截断、某次 `ros2` 调用失败）；ROS 2 这一部分从未读到 | 不报新的；最近一次扫描里已有的保留 |

几种“缺少”会写明档案里看到的原因：

- 设备上没有读到 ROS 2（`/opt/ros` 下没有安装，也没有带 ROS 环境的进程）：能核对的接口全部记为缺少。只有命令完整执行到结束才这样判定；输出不完整时是 `unknown`。
- 有 ROS 2 Humble，但没有读到任何运行中的节点。这一次如果是按默认设置读的（没有从运行中的进程取到 `ROS_DOMAIN_ID` 等），问题说明里会提醒：节点由别的账号运行或设了别的域时，这里看不到。

这一次 ROS 2 没读到、档案里显示的是上一次的清单时，检查按上一次的清单判定，并写明最近一次读取没有成功。

### 不是故障（issue #47）

清单只说明**平台看得到哪些 ROS 2 标准接口**，说明不了本体能不能运动：本体可以用厂家自己的程序运动。一台能走的四足曾被这项检查报成“运控驱动缺 2 项”（红色），那次读取按默认设置进行，一个运行中的节点都没读到。所以：

- 这类问题**从不是故障**（`error`），卡片上没有红色标签。
- 清单**可信**（`credible`：读到了运行中的节点，或设备上根本没有 ROS 2）时是“待确认”（`warning`）：卡片上一个普通标签“运控接口 N 项待确认”（在「更多功能」里），说明写“这只说明平台的 ROS 2 标准接口在这台设备上接不上，不说明本体不能运动”。
- 这一次**没有读到任何运行中的节点**时是“提示”（`info`），卡片上没有标签，只留“运控驱动”入口：读不到节点时接口自然也读不到，节点可能由别的账号运行，或用了别的 `ROS_DOMAIN_ID`、RMW。说明里写明这样一份清单不说明问题。
- 仍然可以勾选并交给修复助手（`fixable: auto`）；助手先确认运控程序是不是已经在以别的方式运行，再决定装不装（Skill 1.4.0）。
- 以前保存的扫描记录里，这类问题按“提示”显示。

## 界面

- **机器人卡片**：结论是 `missing` 时多一个按钮“运控驱动”；清单可信时再多一个普通标签“运控接口 N 项待确认”（不是红色，见上面“不是故障”）。其余情况卡片不变（类型不在清单里的设备，卡片上已有 issue #32 的“旧类型，不在清单里”标签）。
- **运控驱动检查对话框**（卡片按钮，或设备档案里的“查看并处理”）：一句结论、ROS 2 清单的读取时间、一张表（接口、应有的话题或动作与消息类型、这台设备上的状态和找到的话题名），以及：
  - “交给修复助手”：见下一节。全部问题都在等现场处理、或这台机器人已有修复会话在进行时不可点。
  - “重新核对”：重新读取设备档案（issue #27 的读取，二三十秒）。
  - 类型不在清单里时只有“修改本体类型”；没读过档案时只有“读取设备档案”。
  - 按钮上方写明这一轮助手会做什么（见“这一轮修复助手拿到问题会做什么”）。
- **设备档案对话框**：页签上方多一行“运控驱动”：缺什么（带“查看并处理”）、都在、类型不在清单里（带“修改本体类型”）或为什么没有核对。读完档案后这一行立刻更新。
- **硬件初始化页**：缺少的接口作为问题出现在问题列表里，可以勾选、标注。和别的问题不同的两点：不默认勾选；标签写“助手可安装，启动时要人在现场”，而不是“可远程处理”（issue #29 起助手可以安装并启动驱动，启动那一步要人在现场确认；#28 时写的是“助手只排查，安装要人处理”）。
- 窄屏（700 px 以下）表格改成每个接口一块，状态紧跟在名称下面，不需要横向滚动。
- 前端通过包装 `engineRobotCard`、`engineAction`、`engineRefresh`、`dialog` 和设备档案的 `profileBody`、`profileRead` 接入，不改这些函数本身。

## 进入修复流程：一种新的问题

缺少（或类型不对）的接口是一种新的问题，id 为 `motion-driver:<标准能力编号>`，例如 `motion-driver:base.velocity`。id 在多次扫描之间稳定。

它**写在硬件扫描记录的问题列表里**，所以现有的硬件问题和修复流程原样适用：可以勾选、交给助手、在 `HARDWARE_SCAN.json` 里、受报告规则和“等待现场处理”的标注管理。形状和扫描问题相同，多三个字段：

```json
{"id": "motion-driver:base.velocity", "severity": "warning", "blocks": "", "category": "motion", "fixable": "auto",
 "source": "ros2_profile", "device_id": null,
 "title": "ROS 2 清单里没有运控接口：底盘速度（base.velocity）",
 "detail": "按本体类型“四足机器人”，运控驱动应提供话题 /cmd_vel，消息类型 geometry_msgs/msg/Twist（名称可以不同，类型要对）。读到的 ROS 2 话题清单里没有这个类型的话题。这只说明平台的 ROS 2 标准接口在这台设备上接不上，不说明本体不能运动：本体可能用厂家自己的方式运动，也可能是运控驱动没有安装或没有在运行。",
 "hint": "…",
 "capability": "base.velocity", "state": "missing",
 "expected": {"kind": "topic", "role": "subscribes", "name": "/cmd_vel", "types": ["geometry_msgs/msg/Twist"]}}
```

- `fixable` 是 `auto`：这样才能勾选并交给助手（需求要求“能交给修复助手”）。扫描判定“需要现场处理”的问题是不能勾选的。`hint` 写明可以交给助手安装并启动驱动、启动时要有人在现场（issue #29；#28 时写的是助手只排查）。
- 每条保存下来的扫描记录多一个 `motion_drivers` 字段：`status`、`reason`、`body_type`、`checked_at`（所依据的 ROS 2 清单的读取时间）、`reverified`（这次扫描有没有重新读取 ROS 2）、`problem`、`missing`（问题 id）。这个版本之前的扫描记录没有这个字段。
- 扫描记录的 `summary.warnings` 包含其中“待确认”的；`summary.errors` 从不包含这类问题（issue #47）。`motion_drivers` 字段多一个 `credible`。
- **扫描命令没有改**：`hardware_scan.SCAN_COMMAND` 里仍然没有 `ros2`，也不加载任何文件。问题来自设备档案的 ROS 2 部分，不是扫描命令读出来的。连接后的第一次扫描发生在读档案之前，所以不会有这类问题；读过档案后，下一次扫描才会带上。
- 从检查对话框点“交给修复助手”时：最近一次扫描记录里列的运控问题和当前检查结果不一致，就先扫描一次（走硬件页自己的扫描），然后直接打开“让助手修复硬件问题”表单，只勾选运控驱动的问题。

## 重新核对用 ROS 2 读取

以前修复后的核对只重扫硬件，而硬件扫描看不到 ROS 2。现在的规则：**运控驱动的问题是否消失，从不由硬件扫描决定**；已知有这类问题时，在扫描之后再执行一次设备档案的那条固定 ROS 2 只读命令（`ros2_profile.ROS2_EXEC`），按读到的清单判定。

| 什么时候 | 在哪个 SSH 会话上 | 条件 |
| --- | --- | --- |
| 修复会话的 `hardware_rescan` | 重新扫描自己新登录的那个会话，扫描之后 | 会话的基线扫描里有运控驱动的问题 |
| 硬件页的“重新扫描”、连接后的扫描 | 扫描之后另开一个会话 | 保存的档案此刻显示有运控驱动的问题；或者档案此刻下不了结论（`unknown`、`not_read`），而这台机器人最近一次扫描记录里有这类问题 |
| 设备档案的“重新读取”、检查对话框的“重新核对” | 档案自己的读取 | 总是读 |

- 读到的清单同时存进设备档案的 `ros2` 部分（只换这一部分，它有自己的 `checked_at`），所以卡片、档案和之后的扫描看到的是同一份。档案里已有一份更晚读到的（同时进行的档案读取先完成了），就不覆盖它。连接在这期间被改过时，读到的结果只用于这次扫描，不写进旧连接的档案。
- **没读到不等于没有了**：ROS 2 命令超时、会话中断、输出不完整，或读到的内容下不了结论时，原来的问题原样保留在这次扫描里，扫描的说明（`notes`）写明原因，`motion_drivers.reverified` 为 `false`；档案的 `ros2` 部分保留之前的内容并记下这次的原因。助手不能据此把问题标为已修复或未复现，问题的“等待现场处理”标注也不会因此被清掉。
- 同样的规则也用在不读 ROS 2 的保存上（重新调研时的扫描）：档案此刻下不了结论时，沿用最近一次扫描记录里的运控驱动问题，并在说明里写“按上一次扫描的结果保留”。
- 硬件页上人在等的那次扫描，整个请求控制在约 55 秒内（`SCAN_REQUEST_SECONDS`，桌面端网页视图一次请求等一分钟左右）：扫描命令之后、或登录设备之后剩下的时间不到 8 秒就不再读 ROS 2，读到一半到点就停，都按“没读到”处理，问题保留；没有读的那次不记进档案。登录本身不受这个时限约束（`device_access` 每一跳有自己的超时），登录卡住时请求仍可能超过一分钟。修复会话里的重新扫描不受这个限制。
- 设备换成了别的发行版（不是 Humble）时，已有的问题一直保留，每次扫描都会重读 ROS 2，直到读到 Humble 的清单为止。
- `hardware_rescan` 返回给助手的结果多一个 `motion_drivers` 字段，助手据此知道这次有没有读到 ROS 2。
- 每次这样的核对写一条审计 `device.motion_drivers_reverified`（机器人、会话、结论、仍缺的问题 id）。
- 没有运控驱动问题的机器人，扫描和以前完全一样：到达设备的只有扫描命令。

## 这一轮修复助手拿到问题会做什么

> issue #29 起规则放开了：助手可以从资料库取安装包装上并启动运控驱动，启动那一步要有人在现场确认，全程不发运动指令。见 [运控驱动的安装](REPAIR_DRIVER_INSTALL.md)。下面是 #28 时的情况。

修复助手的规则在这个 issue 里**没有放开**（那是 #29）：

- 产品规则照旧拒绝发布运动或控制指令（命令里出现 `cmd_vel`、`ros2 topic pub` 即拒绝）、`source`、内联脚本、重启等。
- 内置 Skill `hardware-init`（升到 1.2.0）多了一节 `motion-driver:<能力编号>` 的处理办法：只读排查（装了哪个 ROS 发行版、有没有驱动包、有没有驱动或启动服务、为什么没运行），**不自己安装、启动或重启运控驱动**（会带起底盘或电机），不用发布话题、调用服务的办法试接口；会话里加载不了 ROS 环境，要知道接口在不在就调用 `hardware_rescan`；结论标为 `needs_user`，写明需要用户提供什么、在现场做什么。
- 所以现在把问题交给助手，结果多半是一份“需要人处理”的报告。报告保存后，这些问题被标注为“等待现场处理”（issue #13 的规则），检查对话框里写明并不再提供“交给修复助手”。人在现场装好并启动驱动后，“重新扫描”或“重新核对”读到接口，问题和标注一起消失。

要说清的一点：“不启动会驱动电机的程序”是写给模型的规则（Skill 和会话指令），不是产品在命令文字上强制的。`systemctl start <某个服务>` 这样的命令，产品规则本身不拦（对已有的 `unit:<服务>` 问题也是这样）；逐条批准时由人把关，“默认允许执行”时只靠模型遵守。这是原有的情况，这个 issue 没有改变它；#29 要重新定这部分规则。

## 状态快照

`/api/state` 多一项 `motion_driver_checks`：每台通过 SSH 接入的真机一条（仿真机器人和没有 SSH 连接的不在里面）。

| 键 | 内容 |
| --- | --- |
| `robot_id` / `project_id` / `family` | 哪台设备，它现在的类型 |
| `status` / `reason` | 结论，和给人看的原因（`ok`、`missing` 时为空） |
| `body_type` | `{id, name}`；类型不在清单里时为 `null` |
| `cause` | 缺少时档案里看到的原因（没有 ROS 2、没有节点在运行），没有时为空 |
| `credible` | 这份清单能不能当依据（issue #47）：`missing` 而一个运行中的节点都没读到时为 `false` |
| `checked_at` / `problem` | 所依据的 ROS 2 清单的读取时间；最近一次读取没成功时的原因 |
| `items` | 每个应有的接口：`capability`、`title`、`kind`（`topic` / `action` / `null`）、`role`、`name`、`types`、`note`、`state`、`found`（找到的话题，最多 5 个）、`found_total`、`issue_id`（缺少或类型不对时） |

里面没有会定时变化的内容：只在读档案、重新核对或修改类型时变，不会让页面无故重画。检查结果不单独保存，每次由保存的档案、设备的类型和类型清单现算，所以不会和它们不一致，也没有新增“按机器人保存的记录”。没有新增 HTTP 接口，也没有新增错误码。

## 验证情况

- `spec/tests/test_ros2_interfaces.py`（9 项）：表里每一项绑定的是标准能力、有类型和惯用名；动作只绑在动作类能力上；类型写法的归一；没有绑定的能力返回空。
- `tests/test_motion_drivers.py`（63 项，SSH 协议替身）：
  - 对照本身：四足缺底盘驱动、机械臂缺轨迹控制器（动作）、只缺一项、驱动齐全、话题改了名、惯用名上类型不对、一个话题多种类型、核对不了的接口不报缺少、没有 ROS 2、有 ROS 2 但没有节点、其他发行版和 ROS 1、清单没读全、类型不在清单里、没有档案、自己添加的类型。
  - 验收：缺运控驱动的四足和机械臂读过档案后，状态里指出缺的是什么（接口、话题或动作、消息类型）；驱动齐全的两类设备没有问题、没有入口；旧类型的设备提示先改类型、不报问题，改成清单里的类型后立刻按保存的档案判定；连接改过之后不沿用旧档案；机器人删除后检查随之消失。

  - 档案下不了结论时不丢问题（两轮独立审查发现的缺陷，都补了测试）：档案重新读取时清单不完整、连接被改过、重新调研的扫描不读 ROS 2 这三种情况，下一次扫描沿用或重新核对问题，标注不被清掉；改成一个没有可核对接口的类型后，旧问题随之消失，不会一直挂着；扫描或登录用完请求时间时不再读 ROS 2、也不记进档案，读到一半到点按没读到处理；较早的读取不覆盖档案里较晚的。

## 已知限制

- **只看接口在不在，不看是谁提供的。** 档案的清单说明一个话题存在，不说明谁在发布或订阅：`ros2 topic list` 也列出只有订阅方、或只有发布方的话题。驱动没有运行时，导航栈发布的 `/cmd_vel`、定位节点订阅的 `/odom`、`robot_state_publisher` 订阅的 `/joint_states` 都会让对应接口算“在”，重新核对时问题也会因此被当作已消失。要分清需要读每个话题的发布方和订阅方（例如驱动订阅的接口要有订阅方、驱动发布的接口要有发布方），设备档案现在不读；这要改 issue #27 的固定命令，没有在这里做。
- **分不清“没装”和“没运行”。** 两者在 ROS 2 清单里看起来一样，问题说明里两种可能都写着。
- 四足的足式姿态、所有本体的停止没有标准的 ROS 2 接口，平台核对不了；一台只缺这两项的设备会被判为齐全。
- 按类型认接口比较宽：设备上任何一个 `geometry_msgs/msg/Twist` 话题都算底盘速度在。哪一个才是这台设备真正用的，要等设备接口表（issue #23）。有了接口表以后，这里应该改成优先按表里确认过的话题核对。
- 只支持 ROS 2 Humble；其他发行版不核对。
- 检查依据的是保存的档案，不会自己定时刷新：驱动在读档案之后才挂掉，要到下一次读档案才看得出来。
- 档案显示驱动齐全时，硬件页的“重新扫描”不会重新读取 ROS 2；要重新核对请重新读取设备档案。
- 有运控驱动问题的机器人，硬件页的“重新扫描”多一次 ROS 2 读取，真机上大约多十几秒（issue #27 在一台真机上测到三次 `ros2` 调用各约 4 秒）。
- 读过档案、驱动出现之后，硬件页显示的仍是之前那次扫描（它写着自己的扫描时间），重新扫描后才一致。
