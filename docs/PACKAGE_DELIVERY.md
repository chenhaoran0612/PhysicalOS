# 把驱动安装包送到设备并核对（issue #31，R1-10）

资料库里的驱动安装包存在云平台（issue #33，见 [MATERIAL_LIBRARY.md](MATERIAL_LIBRARY.md)）；向设备传文件的通道只接受本机文件（issue #18，见 [DEVICE_TRANSFER.md](DEVICE_TRANSFER.md)）。这里是中间的一段，和它留下的结果：

1. 向云平台要这份资料的记录并检查：必须是驱动安装包，已经标为「可用」（R1-13），而且不属于另一台机器人（issue #34）。
2. 把安装包取到本机，按资料库记录的 SHA-256 核对。取到一半断了，下一次从断开的地方接着取。
3. 经 #18 的通道送到设备的 `~/neuxmind-pkg/library/<SHA-256 的前 32 位>/<合规的文件名>`。通道自己分块、压缩、续传，设备上算出同一个 SHA-256 之后文件才出现在这个位置。
4. 记下送到了什么：哪份资料、设备上叫什么、放在哪里、大小和校验值。这条记录就是交给修复流程的结果。

**不解压、不执行、不安装。** 云端只认出了文件的类型，没有打开它，内容是不可信的；这里从头到尾只把它当作带校验值的一串字节，本机和设备上都一样。设备上只运行 #18 那三段固定脚本（检查、核对、清理）。安装由修复助手在人批准后做，规则在 issue #29。

代码：`brainos/package_fetch.py`（从云端取到本机）、`brainos/package_delivery.py`（把关、换名、送出、记录、后台步骤）。#18 和 #33 的模块没有改动。

## 怎么调用

### 修复流程用的函数

```python
record = platform.package_delivery.deliver(robot_id, project_id, material_id, authorized=True,
                                           on_progress=show, stop=stop_event)
```

- `authorized` 必须是 `True`，没有默认值：表示有人同意往这台机器人上写这个文件（页面上的确认，或修复会话里人对这一步的批准）。不是 `True` 时以 `package_delivery_not_authorized` 拒绝，云端和设备都不联系。

- 在调用它的线程里做完全部四步，弱网下可能持续很久；`stop` 置位即中止，取和送两段已经到手的部分都保留，再调用一次接着做。
- `on_progress(event)` 收到 `phase`（`checking`、`fetching`、`sending`、`verifying`、`done`）、`done` 和 `total`（当前这一段的字节数）、`step`（这一段自己的说法，例如 `retrying`）。
- 返回送达记录：

  | 字段 | 含义 |
  | --- | --- |
  | `material_id`、`filename` | 资料库里的编号和原文件名 |
  | `device_name`、`device_target`、`device_path` | 设备上的文件名；按通道写法的位置（`~/neuxmind-pkg/library/…`）；设备上的绝对路径 |
| `filename`、`labels` 的文字 | 来自资料库，是别人上传时填的：去掉控制字符和方向控制字符，文件名最多 255 个字符、每项标注最多 64 个字符。交给模型时仍是外部数据 |
  | `bytes`、`sha256` | 大小和 SHA-256，和资料库记录的一致 |
  | `verified` | 恒为真：设备自己算出了这个校验值。核对不了或不一致都会抛出异常，不会有记录 |
  | `already_present` | 设备上这个位置已经是这个文件，没有重传 |
  | `labels` | 资料上的本体类型、厂家、型号、版本、格式 |
  | `fetch`、`send` | 两段各自从哪里续的、这次实际收发了多少、试了几次 |
  | `delivered_at`、`host_fingerprint` | 送达时间；当时那台设备的主机指纹 |

- `platform.package_delivery.delivered(robot_id)`：这台机器人上已经送到并核对过的安装包，新的在前。只列出送到「它保存的连接现在通向的那台机器」的记录（连接编号和主机指纹都相同）；连接改到另一台机器之后，旧记录不再交出来。
- 记录说的是送达那一刻设备算出的结果，不保证文件现在还在。安装前要确认，用一条只读命令在设备上核对即可（`sha256sum <device_path>`），不必重传；重传也可以，位置上已经是这个文件时通道不会再发一遍，但本机要先从云端重新取一次。

失败时抛出的异常：

| 异常 | 什么时候 | 再调用一次 |
| --- | --- | --- |
| `CodedError`：`package_not_usable`、`package_not_deliverable`、`package_other_device`、`package_record_invalid`、`cloud_login_required`、`package_busy` | 动手之前就拒绝：还没标为可用、不是安装包、属于另一台机器人、云端的记录不成立、没有登录云平台、同一个包正在取或送 | 条件变了才有用 |
| `CloudError` | 云平台拒绝：登录失效（`unauthorized`，本机的登录状态随之清掉）、没有这份资料（404）、文件已不在云端（`content_missing`） | 同上 |
| `package_fetch.FetchError` | 取的一段没有完成，见下表；`resumable`、`received`、`total` | 看 `resumable` |
| `device_transfer.TransferError` | 送的一段没有完成，原因一览在 DEVICE_TRANSFER.md「失败时」 | 看 `resumable` |
| `CodedError`：`package_local_copy_changed` | 本机核对过的副本在送出之前被改动或替换了（见「核对」）；什么都没写到设备上，副本已删除 | 重新从云端取 |
| `CodedError`：`package_delivery_unverified` | 通道报告核对过的校验值不是资料库记录的那个（见「核对」） | 重新送 |
| `device_transfer.TransferError`（`cancelled`） | 文件已送到并核对过，但应用正在退出，没有记下 | 再送一次会发现它已经在设备上，不重传 |

### 平台侧的步骤（给页面用）

同一件事做成人可以发起的后台步骤，桌面端接口（POST，JSON）：

| 路径 | 作用 |
| --- | --- |
| `/api/library/deliver/start` | `project_id`、`robot_id`、`material_id`、`modify_authorized: true`。能当场判断的拒绝当场回答（没确认、不是这个项目的机器人、没有 SSH 连接、不是安装包、没标为可用、正在送）；否则返回一条正在进行的传送 |
| `/api/library/deliver/status` | `project_id`、`job_id` → `status`（`running`、`delivered`、`failed`、`stopped`）、`phase`、`done`、`total`、`error`、`code`、`reason`（送的一段失败时通道自己的原因）、`resumable`、`delivery`（送达记录） |
| `/api/library/deliver/stop` | `project_id`、`job_id`：请它停下，两段已到手的部分保留 |
| `/api/library/deliver/list` | `project_id`、`robot_id` → `deliveries`（同 `delivered`）和 `jobs`（应用打开以来为它发起的传送） |

- `modify_authorized` 必须是 `true`：往设备上写文件要人明确同意。
- 一个工作空间同时最多 4 个传送在进行，再开始的以 `package_busy` 拒绝；同一台机器人的同一个包同时只有一个。
- `status`、`stop` 要带上传送所属的项目，别的项目的传送查不到也停不了。
- 送的一段失败时，只有连接中断（通道的 `interrupted`）算 `package_send_interrupted`；登录被拒、主机指纹变了、没有 SFTP、设备磁盘满、没有校验工具、位置被占等都是 `package_send_failed`，`reason` 是通道给的原因，`resumable` 也照通道的说法。
- 进行中的传送只在内存里。应用重启后它不在了，重新发起即可，两段都会接着做；所以没有「恢复上次任务」这种状态要维护。进度不进 `/api/state` 快照（它随时间变化，放进去会让整页反复重画）。
- 关闭应用（`Platform.close`）会先让进行中的传送停下，最多等 30 秒，再关存储。之后才结束的传送不再碰存储：文件已经核对过的，不记下（下次再送会发现它已经在设备上）。
- **这一轮没有做页面上的入口。** 接口和后台步骤已经可用并有测试，但「资料库」页和机器人页上还没有「送到设备」的按钮。

## 只送「可用」的资料（R1-13）

修复助手只能用「可用」状态的资料。把关的地方只有一处：`package_delivery.usable(material)`，取值在 `USABLE_STATUSES`。

- 资料怎样变成「可用」由 issue #34 做：解析完是 `parsed`（待确认），有人核对并确认后才是 `usable`（可用）；`parsing`（解析中）、`failed`（没解析出来）都不送。`USABLE_STATUSES` 是 `('usable',)`，取的是 #34 定下的值（2026-11-21，当时 #34 还没有提交）。
- **#34 合并之前，上传完的资料都停在「解析中」，所以没有任何安装包能被送出去**，`deliver` 和 `start` 都会以 `package_not_usable` 拒绝，不联系设备。这是有意的。
- 拒绝的说明里用页面上的叫法：解析中、待确认、没解析出来。
- 测试里用替身把资料置为可用：假云端直接给出状态；真云端的测试在云端数据库里改这一个字段，测试的说明里写了它代替的是 #34 的哪一步。

### 资料属于哪台设备（issue #34）

- #34 里每份资料属于上传它的那台机器人：`device_id` 是桌面端机器人的编号。属于另一台机器人的安装包不送（`package_other_device`），也不从云端取。
- `device_id` 为空的资料（#34 之前上传的）不受限制，可以送到这个项目里的任何一台机器人。
- `device_id` 是从云端答复里原样读的；不是普通文字的值（数字、列表等）不会被当成「没有归属」，一律拒绝。
- #34 合并之前，云端的答复里没有这个字段，所以不受限制。
- 状态是送之前向云端现查的，不用页面或调用方传来的值。

## 文件名

资料库里的文件名可以有空格、括号、中文、`~` 等；通道只写字母、数字和 `. _ + -` 组成的名字。`package_delivery.device_name(filename, format)` 负责换名：

- 后缀用云端认出的格式对应的后缀（`.deb`、`.zip`、`.tar.gz`、`.tar.xz`、`.tar.bz2`、`.tar`），不看文件名自己以什么结尾；`.tgz` 这样的写成 `.tar.gz`。
- 其余字符每一串换成一个下划线；开头和结尾不留 `. - + _`（没有隐藏文件，也没有会被命令当成选项的名字，例如 `-rf.deb` 变成 `rf.deb`）；主干最多 80 个字符。
- 什么都没剩下（纯中文的名字），或者换出来的名字被通道拒绝（`id_rsa`、`credentials…` 这类存放凭据的名字，或通道留给临时文件的名字），就叫 `package` 加后缀。
- 目录是校验值的前 32 位（128 位），所以两个内容不同、换名后同名的包不会放到一起，故意造两个前缀相同的文件也做不到；同一个包再送一次落在同一个位置。

| 资料库里的名字 | 设备上的名字 |
| --- | --- |
| `driver_1.0_arm64.deb` | `driver_1.0_arm64.deb` |
| `驱动 安装包 (v1.0).deb` | `v1.0.deb` |
| `运控驱动.tar.gz` | `package.tar.gz` |
| `ros-humble-driver_2.1.0~rc1-1_arm64.deb` | `ros-humble-driver_2.1.0_rc1-1_arm64.deb` |
| `Motor Driver (ARM64).TAR.GZ` | `Motor_Driver_ARM64.tar.gz` |

对应关系记在送达记录里（`filename` 和 `device_name`），审计日志里也有（`library.package_delivered`）。

只写进通道默认允许的 `~/neuxmind-pkg`，没有放宽目录；文件权限 `644`，不带可执行位。

## 从云端取到本机

`package_fetch.fetch(source, material, cache_dir, on_progress=…, stop=…)`，`source` 是这个工作空间登录的云平台（地址和会话令牌），`material` 是资料的记录。

- `GET /library/materials/{id}/content` 一块一块读进 `<工作空间>/package-cache/<sha256>.part`，到一个字节记一个字节。连接断开、长时间没有数据（默认 60 秒没有任何字节就放弃这条连接）或者被停止，已经到手的都留着；下一条连接或下一次调用用 `Range: bytes=<已有的字节数>-` 只要剩下的。
- 每个答复先看再收：响应头里的 `X-Checksum-SHA256` 和长度必须和资料记录一致，续传的答复必须正好从本机已有的位置开始。云端不理会 `Range`（回了整个文件）就从头收；回的位置不对，丢掉已有的部分从头取；校验值或长度变了，说明云端的内容已经不是记录里的那一份，不收，拒绝。
- 全部到齐后算整个文件的 SHA-256，和资料库记录的一致才改名为 `<sha256>.pkg`（只读）。**不一致就删除并拒绝，不会送往设备**，也不自动重试；下一次调用从零开始取。
- 自动重连：连续没有进展的失败之间依次等 1、2、5、10、20、30 秒，只要这条连接收到过新的字节就重新计数；连续 7 次没有进展才停下来报告，已取到的部分保留。云端答 5xx、408、425、429 算暂时不可用，会重试；401、403、404 和跳转是最终答复，不重试（跳转从不跟随）。
- 取之前先看本机磁盘够不够（还差的字节数加 32 MB 余量）。本机写不进去不会被当成网络问题去重试。
- 和其它访问云平台的地方同一套规则：不走代理、不跟随跳转、对实际连接的地址应用地址策略、只有本机地址可以用 http。地址策略拒绝的地址不重试（只有一时解析不了的名字会重试）。会话令牌只出现在请求头里，不进记录、进度、错误信息和缓存文件。
- 云端答复里的错误文字去掉控制字符和方向控制字符、最多 300 个字符，答复的其它字段不往下传。
- 没有声明长度的答复（分块传输，或以关闭连接为结束），收满安装包的大小后最多再等 1 秒看后面还有没有字节，有就拒绝。
- 不设总时限：只要每条连接都有新的字节到，取就一直进行，人可以随时停止。一台故意每次只给一点点的云端能让它拖很久，但不会让它出错地收下内容。

| `FetchError.code` | 含义 | `resumable` | 本机留下什么 |
| --- | --- | --- | --- |
| `package_fetch_interrupted` | 连续多次连接都没有新的进展 | 是 | 已取到的部分 |
| `package_fetch_cancelled` | 按停止请求结束 | 是 | 已取到的部分 |
| `package_no_local_space` | 本机磁盘放不下 | 是 | 已取到的部分 |
| `package_cache_unusable` | 本机存放的位置写不进去，或被别的东西（链接、目录）占着 | 是 | 没有动 |
| `package_checksum_mismatch` | 取到的文件和资料库记录的校验值不一致 | 否 | 已删除 |
| `package_content_changed` | 云端现在给出的校验值或长度和资料记录不一致 | 否 | 已删除 |
| `package_record_invalid` | 资料记录里的编号、大小或校验值不成立，或超过 4 GB | 否 | 没有取 |

### 本机的副本

- 放在 `<工作空间>/package-cache/`，目录 700；未完成的文件 600，核对过的 400。文件名只有校验值，没有登录信息。
- 设备核对通过后立刻删除。送的一段没完成时保留，下次不用再从云端取（再用之前会重新算一遍校验值，被改动过就丢掉重取）。
- 一周没人动的（放弃了的取，或一直没送出去的包）在下次启动或下次传送时清掉；正在用的包不清，再次用到的副本会刷新修改时间。
- 本机磁盘够不够，在每一条连接之前都看一次。
- 同一个包同一时间只允许一次取或送（按校验值，进程内有效），第二个会得到 `package_busy`。

## 核对

校验值在三处被比对，任何一处不一致都不会留下「已送达」的记录：

1. 本机：取到的文件的 SHA-256 等于资料库记录的。不一致 → 删除本机文件，不联系设备。
2. 设备：通道在设备上算出的 SHA-256 等于它发出的文件的。不一致 → 通道清掉设备上这次传送的内容，目标位置不出现新文件，原有的文件不动（`TransferError`，`verify` / `checksum`）。
3. 送出之前：通道算完本机文件的校验值、在设备上写任何东西之前会报告一次「检查中」。这时比对本机文件的身份（设备号、inode、大小、修改时间）和第 1 步核对完时记下的是否相同；不同就停下（`package_local_copy_changed`），设备上什么都没写，本机副本删除。之后文件再被改动，通道自己会停下。
4. 交接：通道报告的校验值和大小等于资料库记录的。前两步之后这里正常不会不一致；真发生时抛出 `package_delivery_unverified`，写明设备上那个不能用的文件在哪里，不记为已送达。

剩下的缺口：能以同一个账号改动工作空间目录、又把修改时间改回原值的程序，可以在第 3 步之前换掉文件内容而不被发现；它也就能改这台电脑上的任何东西，这里不再设防。

「已核对」和 #18 的含义相同：防的是传输途中和磁盘上的损坏，防不了一台对自己说谎的设备，也不说明包的内容是安全的。

## 弱网

需求的验收线：带宽 1 Mbps 以内、时延 300 ms 以上、丢包率 30% 时最终传完且校验一致；丢包率 60% 时不要求传完，只要求不留下损坏的文件、网络恢复后续传。送的一段由 #18 保证并实测过。取的一段：

- 断线后续传靠的是上面的 `Range` 和逐字节落盘，自动化测试里用「每条连接传够若干字节就切断」的假云端和真云端前面的中继覆盖。
- 不留下损坏的文件：未完成的内容只在 `.part` 里，只有整个文件校验一致才改名；`.part` 只追加，内容始终是安装包的一段前缀。
- 实测见下面「测试」里的弱网一节。

## #29、#30 从哪里接

修复会话现在不能加载外部资料，也没有「安装包」这类工具，所以这一轮修复助手自己还发起不了传送。接入点：

- **#30（修复会话能查资料库）**：候选的安装包按 #34 的做法取（`GET /library/materials?device_id=<机器人编号>&status=usable&kind=package`），再用 `package_delivery.usable()` 过滤；把 `platform.package_delivery.delivered(s['robot_id'])` 写进会话的工作目录（和 `HARDWARE_SCAN.json` 一样由 `HardwareInit.prepare_workspace` 写），助手就知道哪些包已经在设备上、在哪里、校验值是多少。
- **#29（装运控驱动的规则）**：给修复会话加一个工具（`hardware_init.tools_spec()` 和 `HardwareInit.tool()` 里各加一处），处理函数里在人批准这一步之后调用 `platform.package_delivery.deliver(s['robot_id'], s['project_id'], material_id, authorized=True, stop=device.stop_event)`，把返回的记录存成一条证据（`HardwareInit._evidence`），再把 `device_path`、`sha256` 交给助手。之后的安装命令（`dpkg -i <device_path>` 等）照常走 `device_fix` 和人的批准。
- 这个工具要不要每次都由人批准，由 #29 定；`deliver` 本身要求调用方传 `authorized=True`，不传就拒绝。它只往 `~/neuxmind-pkg/library` 写一个不可执行的文件，资料又必须是人确认过的「可用」状态；但它确实改动了设备。平台侧的步骤要求 `modify_authorized`。
- 交给模型和用在命令里时：`filename`、`labels`、`device_name` 是别人填的文字，只当数据；`device_path` 放进命令时要加引号（`~` 会被 shell 展开）；安装前在设备上再算一次校验值。校验值只说明文件和云端记录的一致，没有签名：云端本身被攻破时它可以换上别的包和与之相符的校验值，所以人对安装的批准才是关键的一步。
- 会话里的传送用的是保存的连接（`ssh_edit.saved_login`），和会话自己的 SSH 连接不是同一条。连接在会话运行期间被改到另一台机器时，会话不会跟过去（issue #12），而传送会连到新保存的那台。#29 接入时要在处理函数里比一下主机指纹（记录里有 `host_fingerprint`）。
- 厂家驱动包「先查资料库，没有才记为由用户提供」是 #29 的事；这里只负责已经选定的那一个包。

## 删除机器人

送达记录是按机器人存的（存储种类 `package_deliveries`），已经加进 `robot_remove.ROBOT_RECORDS`，随机器人一起删除。删除不联系设备，设备上的文件留着。传送进行到一半时机器人被删掉，文件可能已经在设备上，但不会留下记录。

### 弱网实测（取的一段）

容器里用 `tc netem` 在回环口上限速 1 Mbit/s、双向各加 300 ms 时延，丢包对数据和应答都生效；假云端和取的一方在同一个容器里。全部用产品默认的重试间隔和时限（2026-11-21，两次运行，第二次是审查修改之后的代码；数字随运行有出入）：

- 30% 丢包，256 KiB：一次调用里断开重连 3 次（第二次 2 次）后取完，校验一致，339 秒（340 秒）。
- 512 KiB，先无丢包取到 200 KiB，再切到 60% 丢包：8 分钟里又取到一些，之后按停止结束，本机只有一个 309872 字节（354760 字节）的 `.part`，内容是安装包的前缀，没有 `.pkg`。恢复无丢包后再调用一次，从那个字节接着取，5 秒（4 秒）取完，校验一致。
- 每条被放弃的连接里，云端已经发出、还在网络缓冲里的字节会丢掉，所以云端实际发出的比文件大；本机已有的字节没有被要第二次。
