# 应用编排用上「技能发布」里发布给品牌型号的技能（issue #73）

更新：2026-11-28。对应 GitHub issue #73「应用编排」：

> 应用编排现在无法正确关联到已经发布的能力。需要关联上，能力是发布给品牌型号的

> 状态：代码和测试完成；**没有在任何真机上运行过**，也还没有合并。验证范围见[最后一节](#在哪里验证过哪里没有)。

## 原来的问题

issue 截图里的情形：任务「办公室每日巡检」用的是「智身科技 钢镚 L2-U」，账号里那台 L2-U 没有连接；云端「技能发布」里已经给「智身科技 钢镚 L2-U」发布了 6 个技能（无图自由走、去指定地点、巡逻、巡检、状态报告、挥手）。「创建机器人应用」的技能步骤里却写着「这个品牌型号还没有技能」，上面写「这个品牌型号的机器人现在都没有连接，读不到它的技能」。

原因：创建表单（issue #68 的 `model-skills/ready`）只从两处找技能——这个品牌型号**已连接**的机器人上装好的，和随应用提供、适用于它的技能库——云端发布的版本根本不在里面（[APP_CREATE.md](APP_CREATE.md) 当时写明了「云端技能版本不算」）。机器人没连接时两处都是空的。

## 现在

| | 原来 | 现在 |
|---|---|---|
| 创建表单能选的技能 | 已连接机器人上的 + 技能库里适用的 | 再加上**云端「技能发布」里发布给这个品牌型号的全部版本** |
| 这个品牌型号的机器人都没连接 | 什么都选不了 | 发布给它的技能照样能选 |
| 表单上的说明 | 「有 N 个技能可以直接选用，不用先安装」 | 「有 N 个技能可以直接选用（M 个来自「技能发布」），不用先安装」；机器人都没连接时补一句「机器人上自己装的技能连接后才列得出」 |
| 没登录云平台 | — | 写明「没有登录云平台，「技能发布」里的技能没有列出」，其余照常 |
| 云平台读不到（网络、地址、回答不完整） | — | 写明没有读到和原因，其余照常；所有读取加起来最多等 8 秒 |
| 现场测试前机器人上缺这个技能 | 技能库里有的自动装，其余交给设备检查 | 先用技能库里**同一版本**的；没有就从云端装发布给这个品牌型号的那个版本 |

「修改工作流」（新版本）的表单走同一个请求，同样能选这些技能。

### 什么算「发布给这个品牌型号」

- 云端每个版本（release）都写着它属于哪个品牌型号（issue #48 的 `product`）。和机器人的品牌型号按 `robot_model.key` 比较：同一个品牌型号的别的写法（例如 `zsibot / L2U`）算同一个。
- 一个技能的**每个**版本分别看：0.1.0 发布给 L2-U、0.2.0 发布给别的型号时，L2-U 只看到 0.1.0；两个版本都发布给 L2-U 时，两个都列出，步骤里写成「名称 · v版本」（#68 原有的写法）。
- 还没有写明品牌型号的旧版本（issue #48 之前发布的）不算：在「技能发布」里给它指定品牌型号后就会出现。
- 云端返回的某一条读不懂（编号、版本不合规则）时只跳过那一条，其余照常列出。
- 不按机器人的能力清单筛：发布给这个品牌型号就是人的判断。装到某台机器人上时仍然核对兼容性，不兼容的现场测试会停下并说明缺什么（见下）。

### 列出来以后

和 #68 一样，每个技能（标识 + 版本）建一条技能记录（带这个品牌型号、需要的能力、参数说明），步骤里的参数表单照技能的参数说明生成（截图里「去指定地点」的「去哪里」）。同一个技能既在机器人上、又在云端时只有一条。再打开表单不会多建。

没有设备能力说明（`requires` 为空）的版本建不了记录，记在 `skipped` 里，表单写明哪几个没有列出（#68 原有的规则）。

## 现场测试前自动装上

现场测试通过配置检查、核对过设备能力清单之后（#68 的位置），对应用里每个机器人上还没有的技能：

1. 技能库里有**同一版本**的，按原来的路径装（「安装技能包」）。
2. 否则，云端有发布给这个品牌型号、**同一版本**的，按「技能加载」的路径装：下载、核对云端记录的摘要、核对品牌型号、对照机器人当前的能力清单检查兼容性，再 `POST /v2/skills/install`，操作记录和手动「技能加载」一样（`source: cloud`）。现场测试本身就要人确认现场条件，所以这里不再单独问一次。
3. 两边都没有这个版本、但技能库里有别的版本的，照原来装技能库里的（#68 的行为不变）。
4. 都没有的，交给设备自己的执行前检查去说。
   - 云平台登录着、但这次读不到（网络、地址）时，现场测试停下并说明（`skill_auto_install_failed`）：这时不知道它是不是在云端。
   - 没有登录云平台时，按原来交给设备。

装不上（不兼容、云端拒绝、设备拒绝）时，现场测试停下并说明是哪个技能、为什么（`skill_auto_install_failed`，#68 已有的错误码）。

云端的版本和创建应用时不一样了也停下、不装：在「技能发布」里删掉一个版本再用同一个版本号发布不同内容是可能的。

- 核对一：云端现在列出的这个版本需要的设备能力，要和应用步骤里那条技能记录的一样（`install_missing`）。
- 核对二：下载到的包，摘要和需要的设备能力要和刚列出的一样（`published_skills.install`）。

不一样时说明请在应用里重新选这个技能（修改工作流）。机器人上已有这个技能的任何版本时不动它（#68 的规则）。

只有需要从云端装的时候才去问云平台：应用里的技能都在机器人上、或都在技能库里时，现场测试不碰云平台。

## 怎么实现的

- 新增 `brainos/published_skills.py`：
  - `releases_for(platform, product)` 读出这个品牌型号的全部版本。云端的技能列表每个技能只带最新版本；有多个版本的技能再读它自己的版本列表（最多 8 个同时读，全部共用一个 8 秒的期限）。回答不完整、连接断开（`http.client` 的异常、`OSError`）算读不到，不会让表单出错。
  - `install(platform, robot, item)` 走 `CloudSkills.install_preview` → `install`，不另写一套；两步之间核对下载到的包就是列出的那个版本。
- `brainos/model_skills.py`（#68 的模块）：
  - `ready` 在机器人和技能库之后加上云端的，返回多一个 `cloud: {status, count, error}`（`status` 是 `ok` / `signed_out` / `failed`）。
  - `install_missing` 按步骤技能记录的版本找来源。
  - 两个新的替换点 `published_for`、`install_published`（测试用）。
- `brainos/cloud_skills.py`：`_call` 多一个可选的 `timeout`，默认值不变。表单读云端用 8 秒（`published_skills.READ_TIMEOUT_S`），「技能发布」「技能加载」页面仍是 30 秒：表单是人在等着的地方。
- `web/app_create.js`：只改了表单上那句说明（`acStatus`，新增 `acCloudNote`）。

没有新的错误码，没有新的路由，`brainos/server.py`、`web/index.html` 都没有改。

## 测试

- `python -m unittest tests.test_published_skills`，分五组：
  - `Ready`：没连接也能选；别的品牌型号、没写品牌型号的不算；每个版本分别看；别的写法算同一个；不重复；没登录不问云端；读不到、回答不完整时说明且其余照常；云端不回答时在期限内放弃；一条读不懂的不连累其余；多个技能的版本列表同时读。

## 这一版没有做的

- **仿真试运行（issue #66）不从云端装**：任务的仿真机器人进入仿真时只装这台电脑上有技能包的技能（`brainos/task_sim.py`）。issue #74 正在改这个文件，这次没有动它；应用里用了只在云端的技能时，仿真里那一步会缺技能。
- 「技能」页面（`#app-skills`，「机器人应用」上已经没有入口）和训练与改进页的技能选择（issue #71）没有加云端的。
- 云端技能版本被删除后，已经建出来的技能记录不会跟着删（和机器人上的技能被卸载时一样）。
