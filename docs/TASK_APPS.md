# 任务绑定应用：任务工作台不再直接开发（issue #50）

更新：2026-11-26。对应 GitHub issue #50「任务工作台」：

> 任务工作台应该是绑定应用或者跳转到应用页面中创建应用。而不是直接开发。应用是绑定给机器人品牌 型号的，不同型号之间不通用。

> 状态：代码和测试完成；**没有在任何真机上运行过**，也还没有合并。本文所在的分支建立在 issue #48（品牌型号，[ROBOT_MODEL](ROBOT_MODEL.md)）之上。验证范围见[最后一节](#在哪里验证过哪里没有)。

用户在 issue 会话里定的四件事（2026-11-26）：

1. **应用属于账号**，和机器人一样从任务里独立出来：在「机器人应用」里创建和修改，每个任务都看得到。
2. 任务和应用之间是**多对多**的绑定：一个任务可以绑定多个应用，一个应用可以绑定到多个任务；解除绑定只去掉关系。
3. 任务页面**只留绑定的应用**：去掉「现在做这一步」开发引导、五步进度和「需要时，再使用这些能力」四个开发入口。
4. **一个任务限定一个品牌型号**：绑定第一个应用后，这个任务只能再绑定同一品牌型号的应用。

## 现在的规则

| | 原来 | 现在 |
|---|---|---|
| 应用保存在哪里 | 创建它时打开的那个任务里 | 账号里；打开哪个任务都一样，不打开任务也能创建 |
| 「机器人应用」页列出谁 | 当前任务的应用 | 账号的全部应用（按品牌型号筛选是 issue #48 的功能） |
| 任务怎样得到应用 | 在任务页面里一步步开发 | 绑定账号里已有的应用；没有合适的，去「机器人应用」创建后再绑定 |
| 技能、测试报告、发布记录、启动和停止记录 | 跟着任务 | 跟着应用，也属于账号 |
| 删除任务 | 应用和它的测试、发布记录一起删除 | 只删除绑定关系；应用和记录都留下 |
| 任务的品牌型号 | 没有这个概念 | 第一个绑定的应用决定；之后只能绑定同一品牌型号的 |

细则：

- **绑定的是“这个应用”，不是某一个版本。** 一个应用“修改为新版本”后还是同一个应用；任务用的是它最新的版本，页面上写明版本号和一共几个版本。
- **任务的品牌型号不单独保存**，就是它最早绑定的那个应用的品牌型号。所以把全部应用都解除后，任务可以改绑另一个品牌型号；应用后来才有了品牌型号（issue #48：旧机器人补填之后），任务也跟着有。
- **没有品牌型号的应用**（为没填品牌型号的旧机器人建的）按 issue #48 的说法自成一类：它只能和“为同一台机器人建的、同样没有品牌型号的应用”绑在同一个任务里。
- 品牌和型号的比较不分大小写，和 issue #48 一致。
- 创建应用不会自动绑定到任何任务。
- 解除绑定不影响已经发布到机器人上的版本，也不影响正在进行的测试。
- 任务用得到哪些机器人：账号里和它同品牌型号的机器人（没有品牌型号时，就是应用所针对的那一台）。任务页面的「技能与配置」只列这些机器人。

## 页面

### 任务页面（`#task`）

从上到下：

1. 「← 全部任务」；任务名称和目标；右上角「绑定应用」和「去创建应用」。
2. **品牌型号**：任务限定的品牌型号，以及账号里有几台这样的机器人、几台已连接。还没有绑定应用时写“还没有确定”，并说明绑定第一个应用后就固定。
3. **已绑定的应用**，每个应用一行：名称、版本、品牌型号、工作步骤（技能名称）、可用的机器人、进度（配置检查 → 现场测试 → 发布，按当前版本的记录算）、「交付清单」、「解除绑定」。检查、测试、发布仍然在交付清单里做，没有变。
4. 没有绑定应用时：说明“任务工作台不开发应用”，给出「绑定应用」和「去创建应用」。
5. **技能与配置**（issue #46 的那一节）：只在任务绑定了应用之后出现，内容是“这个品牌型号的机器人装了哪些技能、绑定的应用用到哪些、各自怎样配置”。

不再出现的：「现在做这一步」、五步进度条、「查看哪个应用的进度」、「需要时，再使用这些能力」（选用现成模型、用自己的数据训练、在仿真中试运行、让助手帮忙开发）。这些功能本身的页面都还在侧边栏里，只是不再从任务页面进入。

### 绑定应用

- 任务页面的「绑定应用」：列出账号的全部应用，按品牌型号分组，任务自己的品牌型号排在最前；已经绑定的标“已绑定”；其他品牌型号的应用按钮不可用，并写明原因。
- 「去创建应用」：打开「机器人应用」，页面顶部提示“正在为任务「…」准备应用”。创建后在应用卡片上点「绑定到这个任务」，绑定并回到任务。「返回任务」「不绑定了」可以结束这次提示。提示记在浏览器的会话存储里，关掉应用就没有了。
- 「机器人应用」里每张应用卡片多了一行：已绑定到哪些任务，以及「绑定到任务」（列出账号的任务，可以绑定，也可以解除）。
- 解除绑定先确认，说明只解除关系。

### 任务工作台首页

- 任务卡片：原来的五步进度改成“绑定了 N 个应用 · M 个已发布”（每个应用一个标记，已发布的填满，最多画 5 个）；三行内容改成 品牌型号、机器人应用、机器人（这个品牌型号的台数、已连接数、名字）。卡片大小一致的规则（issue #46）没有变。
- 看板上的“机器人应用”改成“绑定的应用”：几个任务绑定了同一个应用只算一次。任务名称旁边的 `n/5` 改成“n 个应用”。
- 删除任务的确认框：写明会解除和几个应用的绑定，并说明“绑定的应用本身不会删除”。

### 不打开任务也能用的页面

「机器人应用」「验证与测试」「部署与运行」不再提示“先描述任务”。没有任何任务时，也可以登记技能、创建应用和检查应用。

## 怎么实现的

- `brainos/task_apps.py`：规则都在这里。
  - 绑定是一种新的记录 `task_applications`：`{id, project_id（任务）, application_id（应用第一个版本的 id）, created_at}`。
  - `TaskApps.bind / unbind / applications / product / keep_models`，以及 `migrate`、`as_made`、`kind_of`。
- 应用以及跟着应用的记录保存在账号的“家”里（`project-robot-home`，issue #42 给机器人用的那条记录，见 [ROBOT_SCOPE](ROBOT_SCOPE.md)）。关于应用的请求（`skills`、`applications`、`applications/…`、`harness`、`onsite`、`onsite/…`、`deployments`）由服务端一律按“家”处理，页面当前打开哪个任务不影响结果；这几个路由登记在 `brainos/robot_scope.py` 里，和机器人的路由在一起。
- 页面读到的状态里多了 `task_applications`。页面上按任务筛选的列表本来就包含“家”里的记录，所以应用、技能、测试报告在每个任务里都能看到。
- 接口：`POST /api/task-apps/bind`、`POST /api/task-apps/unbind`，参数都是 `{project_id, application_id}`（应用的任何一个版本的 id 都可以）。新的错误码：`task_other_model`（品牌型号不同）、`task_app_missing`（应用不在了）。
- 页面：新增 `web/task_apps.js`、`web/task_apps.css`（任务页面、两个绑定对话框、「机器人应用」上的绑定入口）。`web/task_workbench.js` 的卡片、看板、删除确认按绑定的应用改写；`web/task_skills.js` 改为只看绑定的应用和它们的机器人。
- 改到共用文件的地方：`brainos/service.py` 三处插入（创建模块、状态、项目检查）、`brainos/server.py` 两处插入（静态文件、路由）、`brainos/robot_caps.py` 一行、`brainos/task_remove.py` 一行、`brainos/robot_scope.py` 两行、`web/index.html` 一行、`web/ux04_errors.js` 两条；改写的有：`web/app.js` 一行和 `web/delivery.js` 两处（去掉“必须先有任务”的限制），`web/delivery.js`、`web/revisions.js`、`brainos/evaluations.py` 各一处（查看测试报告、修改为新版本、查询进行中的现场测试时，不再要求记录属于当前打开的任务）。
- `web/journey.js` 没有改：它画的任务步骤页不再显示，文件里的 `journeyOverview`、`journeyNext` 等函数现在没有页面使用（其他页面的标题和说明仍然来自这个文件）。要不要删掉这些代码，留给以后决定。

### 模型

没有改动模型的归属：模型仍然是在某个任务里选用的。账号的技能可以引用任务里的模型；删除这个任务时，被账号的技能引用的模型不删除，改为留给账号（`TaskApps.keep_models`），其余模型照旧随任务删除。留给账号的模型之后在每个任务的模型列表里都能看到。

## 旧数据

打开工作区时整理一次（`task_apps.migrate`，在 issue #42 和 issue #48 的整理之后），之后不再做：

- 每个应用移到账号里，并**绑定到它原来所在的任务**（每个应用一条绑定，多个版本算一个）。
- 全部技能、带应用的测试报告和发布记录、应用和发布的操作记录（现场测试、启动、停止）一起移到账号里。
- 任务自己的东西不动：训练和仿真任务、模型、数据、场景、服务、助手会话、协作流程。
- 原地改写、一次提交：列表顺序不变；中途被打断等于没有做，下次打开再做。不联系任何设备。出错时工作区照原样打开，记一条 `task_apps.migration_failed`。

两点说明：

- **应用的摘要不变，已有的测试证据照旧有效。** 应用的摘要是连同它所在任务的 id 一起算的，设备收到应用后会重新核对摘要。所以移走的应用记下原来的任务 id（`made_in_project_id`），发给设备时仍按创建时的样子发送（`task_apps.as_made`）。
- **一个旧任务里有两种品牌型号的应用时**，两个都保留绑定；任务的品牌型号按最早的那个应用算，另一个在任务页面上标出“品牌型号和这个任务的不一样”，可以继续用，也可以解除；之后不能再绑定第三种。

回到旧版本的应用时（按 issue #42 的做法推断，没有实际验证过）：应用会显示在名为「我的机器人」的任务里（旧版本把“家”当成一个任务），数据不丢；`task_applications` 旧版本不认识，不受影响。

升级后用户会看到的变化：每个任务页面变成“已绑定的应用”列表，原来在这个任务里的应用都已经绑定好；「机器人应用」里能看到所有任务的应用。

## 对已有浏览器验收脚本的影响

任务页面不再有 `.journey-next`、`.journey-step`、`.journey-options`：

- `task_workbench_browser`、`journey_browser`：新任务的页面改为检查“还没有绑定应用”。
- `task_skills_browser`：新任务没有「技能与配置」；创建应用后先绑定到任务，再检查这一节。
- `ux03_browser`：任务页面不再推荐下一步（也就不会推荐工程助手）；“在仿真机器人上运行技能”改从「仿真试运行」页进入。
- `ux04_browser`：试用任务改为检查任务卡片上的“试用任务”标记。
- `delivery_browser`：原来检查“任务页面选中了新版本”，改为把应用绑定到任务后检查任务用的是新版本（v1.1，共 2 个版本），并从任务打开交付清单。
- `robot_scope_browser`、`task_workbench_browser`：任务卡片不再列出账号的全部机器人；没有绑定应用时写“绑定应用后确定”，绑定后列出这个品牌型号的机器人。
- issue #49（功能简化）新增的 `hidden_pages_browser` 原来检查任务页面上的五步；那个会话已经改成“有步骤视图才检查”（`feat/feature-simplify` @ 9cc0d4b），和本分支合并后不会因此失败。合并后的代码上还没有一起跑过。
- 页面逻辑检查 `task_workbench_logic`、`task_skills_logic`、`robot_scope_logic` 按绑定的应用更新。

## 在哪里验证过，哪里没有

见分支交付说明里的测试结果。没有验证的：

- 真机。检查、现场测试、发布走的仍是原来的请求，设备端没有改动；“移走的应用按原样发给设备”只用摘要的重新计算验证过，没有发给真实的管理层。
- 本机真实工作区上的整理：只在测试建出来的旧数据上验证过。

## 这一版没有做的

- 删除应用（原来也没有）。
- 模型、数据、训练和仿真任务的归属没有改，仍然属于任务。
- 两个任务里各有一份“同一个技能”的登记时，整理后「技能资产」里会有两条相同的技能记录；不影响使用，没有合并。
- 任务页面上没有“这个任务用哪一台机器人”的选择：用哪台仍然在交付清单里选（issue #48）。
