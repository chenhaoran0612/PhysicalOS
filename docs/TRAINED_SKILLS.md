# 仿真里训练出的模型就是机器人的技能（issue #67）

原来（issue #63），小鸭在仿真里训练出的模型只是「训练与改进」页里的「技能模型」：能在仿真小鸭身上演，但不是机器人的技能，在「我的机器人」的技能列表里看不到，也不能编排进机器人应用。原因是管理层不执行它无法限幅的厂商扩展动作，而能力标准里没有「运行一个训练好的模型」这一项。

这一版补上了这一项。现在每个有模型包的训练成果都是 Microduck AD-P102 的一个技能，仿真小鸭自带全部技能。

> 状态：代码和测试完成；**没有在任何真机上运行过**（没有小鸭的真机接入）。验证范围见最后一节。

## 用户定的事（2026-11-27，本 issue 的会话里）

| 问题 | 决定 |
|---|---|
| 做到哪一步 | 真正的技能：能力标准加一项，每个训练模型做成技能包，经管理层授权、运行、停止 |
| 「绑定给仿真环境」指什么 | 仿真机器人：同品牌型号的仿真机器人自动带上这个型号训练出的全部技能 |

## 用起来是什么样

1. 「添加仿真机器人」里添加 Microduck AD-P102（或在「训练与改进」页点「添加仿真小鸭」）。
2. 它启动后，每个有模型包的训练成果已经作为技能装在它身上：「我的机器人 → 它 → 能力与技能」的「已安装技能包」里有 `duck.bow_roll`（鞠躬鞠过头）等，每个旁边有「运行」。运行表单里有一个可选参数「起姿编号」。
3. 同时它们登记成了 Microduck · AD-P102 的技能，在「机器人应用 → 技能」里列出，可以编排进这个品牌型号的机器人应用。
4. 「训练与改进」页的每个模型下面多了一行：它是哪个技能、哪个版本、有没有装在选中的仿真小鸭上。那一页原来的「运行」按钮照旧。

以前添加的仿真小鸭不用重新添加：它下一次启动时（包括应用重新打开时）会装上并登记这些技能。

## 规则

1. **能力标准 1.2 → 1.3，新增 `policy.run`「运行已训练的技能模型」**（动作，运动类）。输入：`name`（模型名）、`seed`（可选的起始编号）。输出：`completed`，以及可选的 `name`、`reason`、`duration_s`、`steps`。本体在清单里用 `policies` 声明它有哪些模型（必填，互不相同的名字），可选 `max_duration_s`。
2. **安全监督器管什么、不管什么。** 它不能给模型内部的动作限幅，这一点没有变。它管的是：只启动本体清单里声明过的模型，别的名字在到达本体之前就被拒绝；运动授权、急停锁存、真机必须先填写安全限值、运行时限、停止，这些和别的运动能力一样生效。也就是说，一个模型能不能安全地在真机上运行，由声明它的本体（接入程序）负责，标准只保证不会运行没声明的东西。厂商扩展 `x.*` 的运动能力仍然一律拒绝。
3. **一个模型一个技能，重新训练就是新版本。** 技能标识是 `duck.<节目>`，版本是「训练轮次.更新次数.0」（鞠躬是第 40 轮第 4 次更新 → `40.4.0`）。技能包里只有一份说明和十几行代码（调用 `policy.run`，带上模型名），不含权重和网格；模型仍在套件里，仍按 issue #63 的规则核对和运行（只在验收时的物理引擎版本上、不用 PyTorch）。
4. **候选也是技能，但说明里写着成绩。** 独立组 8/10 的「醉鸭不倒（绕场两圈）」也会装上，技能说明里有两组成绩和「还没有达到交付要求」；它可能失败，失败时运行结果里有原因。还在训练、没有模型包的两个节目不是技能。
5. **技能按品牌型号登记一次。** 第二个仿真小鸭不会再登记一遍。
6. **一次只演一个。** 仿真小鸭正在演的时候，再经技能通道启动另一个会失败并说明原因（「训练与改进」页的「运行」是直接换节目，和原来一样）。
7. **仿真结果不是现场证据**，和原来一样。

## 测试

```sh
python -m unittest discover -s spec/tests            # 能力标准，含 policy.run 的 8 项
python -m unittest tests.test_duck_skills            # 14 项：技能包、仿真小鸭自带、经管理层运行 / 失败 / 停止、编排进应用、旧的仿真小鸭
python -m unittest tests.test_duck_kit               # issue #63 的 35 项
node tests/duck_logic.cjs                            # 页面逻辑
# 在 Linux 容器里（runtime 的测试套件）：
python -m unittest runtime/tests/test_policy_run.py  # 8 项：授权、未声明的模型、参数、停止与锁存、真机没填限值
```

测试用的模型是编出来的（`tests/duck_support.py`：一个方块、数步数的「节目」），仓库里没有任何权重、网格或录像。

## 在哪里验证过，哪里没有

2026-11-27，这台 Mac（当天小鸭的训练任务占满了处理器，负载 150–340，计时类用例受影响）：

- 能力标准 43 项通过；`tests.test_duck_skills` 18 项、`tests.test_duck_kit` 35 项通过；页面逻辑 53 项检查通过。
- 浏览器验收 `tests/duck_skills_browser.cjs`：编造的模型在 Chromium 和 WebKit 上通过；**真实套件**在 Chromium 上通过，交付的「鞠躬鞠过头」作为技能 `duck.bow_roll@40.4.0` 经管理层从头演完，五个模型都列在 Microduck · AD-P102 的技能里。issue #63 的 `tests/duck_browser.cjs` 照旧通过。
- Linux 容器里的管理层测试 1149 项：13 项失败、1 项出错。出错的一项是容器里没有 `paramiko`（和这次改动无关）。13 项失败单独重跑后 11 项通过；剩下两项（`test_models…install_while_latched_and_beside_motion`、`test_sandbox…fork_bomb_is_contained`）在没有改动的 `integration` 上同样失败，是负载下的计时超限。新加的 `test_policy_run` 9 项通过。
- SDK 85 项通过（云平台镜像的容器里）。云平台 655 项里 1 项失败（`test_material_parse…test_huge_numbers_and_deep_nesting…`），它在没有改动的 `integration` 上用同一环境同样失败。
- 桌面端完整测试 2174 项：16 项失败、11 项跳过。失败的都是等待工程助手会话或停止计时的用例（`test_extensions`、`test_workflows`、`test_stop_bound`、`test_adaptation`、`test_heartbeat_limits`、`test_runtime_link_review`、`test_ssh_multi_hop`），没有一项在这次改到的代码里；单独重跑 16 项仍有 14 项超时，抽 6 项在没有改动的 `integration` 上跑，4 项同样失败。也就是说，这些用例当天在这台电脑上跑不出结论，要在负载正常时由统一测试再跑一遍。
- 独立代码评审一轮：没有严重问题；三个中等问题已改并加了测试（一次运行的结果可能记到下一次运行上；被替换的运行仍可能发给物理进程；说明文字变了的技能包重装时被当成旧请求）。

没有验证的：


- **真机。** 没有小鸭的真机接入；真机上要有一个声明 `policy.run` 的接入程序，并由它保证每个模型的动作在机器人的限值以内。这不在本 issue 里。
- 旧的管理层（能力标准 1.2 及以前）不认识 `policy.run`：依赖它的技能装不到那样的机器人上，安装时会被拒绝。
- 其他品牌型号的训练成果：现在只有小鸭有训练出的模型。别的机器人接入训练后，走同一条路（本体声明 `policy.run`，每个模型一个技能包）。
