# 去指定地点、巡检、无图自由走（issue #38）

一台自带导航程序的四足机器人（下面叫“这台机器狗”）已经会三件事：按顺序去会议室和二楼巡检、去一个指定地点、不用地图在附近自己走。这些能力原来只是机器人电脑上的几个程序，要登录上去手工运行。本文说明它们怎样接进系统：成为三个可安装的技能，经管理层的授权、限速和停止来运行。

> 状态：代码和测试完成；**没有在任何真机上运行过**。机器狗上只做过只读检查（读它的程序和运行记录），没有安装管理层，没有发过任何指令。验证范围见[最后一节](#在哪里验证过哪里没有)。

## 一句话

技能只说“去哪里”“走多久”，怎么走由机器人自己的程序决定。中间加了两项标准能力和一段“把机器人上的程序当作动作来运行”的适配代码：

```
技能包（去指定地点 / 巡检 / 无图自由走）
   │  ctx.call("base.navigate_to_place", place="会议室")
   ▼
能力总线 → 安全监督器（现场授权、急停锁存、认识的地点、速度上限、时长与半径上限）
   ▼
ROS 2 适配器 → programs：启动机器人上的程序，看它的退出码和输出，停止时结束它
   ▼
机器人自带的导航程序（定位、路线、避障、上下楼）
```

## 新增的两项标准能力（能力标准 1.2）

| 能力 | 类型 | 输入 | 输出 | 本体在清单里声明 |
|---|---|---|---|---|
| `base.navigate_to_place` 去指定地点 | 持续动作，运动类 | `place`（地点名）、可选 `max_speed` | `reached`、`place`、可选 `final_pose` | `places`：它认识的地点名列表（必填，不能重名） |
| `base.explore` 无图自由走 | 持续动作，运动类 | `duration_s`、可选 `radius`、`max_distance`、`max_speed` | `completed`、可选 `travelled`、`final_pose` | 可选 `max_duration_s`、`max_radius` |

为什么不用已有的 `base.navigate_to`：它的目标是地图坐标系里的一个位姿。这台机器狗的地点是它自己标记的名字，从一楼到二楼要走楼梯，这不是“走到一个坐标”能表达的；厂商扩展能力（`x.*`）又会被安全监督器一律拒绝。所以按标准的方式加了两项。

安全监督器对这两项做的事（`runtime/neuxmind_runtime/safety.py`）：

- 和所有运动类能力一样：要 `hardware_authorized=true`；急停锁存时拒绝；真机没有填写安全限值时拒绝（`safety_limits_missing`）。
- 地点名不在本体声明的 `places` 里：拒绝，请求到不了适配器。
- `duration_s`、`radius` 超过本体声明的上限：拒绝。
- **每个请求都带着速度上限到达本体**：`max_speed` 取“请求给的值、现场填写的最大线速度、清单声明的最大线速度”里最小的一个；请求没给也会填上。行走由机器人自己的程序完成，这个数是管理层能管住它速度的唯一办法；一个上限都没有时拒绝。

## 三个技能

在 `runtime/examples/skills/` 下，随控制台发布，出现在“安装技能包”的示例里。

| 技能 | 参数 | 做什么 |
|---|---|---|
| `goto_place` 去指定地点 | `place`：会议室 / 二楼（下拉选择）；可选 `max_speed` | 走到选的地点 |
| `patrol_places` 巡检 | `places`（默认“会议室、二楼”）、`return_to`（默认“出发点”，留空则停在最后一处）、`loops`、可选 `max_speed` | 按顺序走到每个地点，最后回去；出发前先核对每个地点本体都认识；有一处没到就停下，不再往下走 |
| `free_walk` 无图自由走 | `duration_s`（默认 60）、可选 `radius`、`max_distance`、`max_speed` | 在附近自己走动并避障，到时间或走够距离为止 |

技能只依赖能力 ID，不知道是哪台机器人。电量是可选读数，读不到（话题一时没有新数据）只记一条日志，不会让行走失败。

## 把机器人上的程序接成动作（`programs`）

写在 ROS 2 适配器的配置文件 `ros2-config.json`（[runtime/README.md §3.3](../runtime/README.md#33-接设备自己的-ros-2-humbleissue-21需求-r1-03)）的 `programs` 一节里。这份配置放在机器人上，不进仓库；仓库里有一份虚构的例子 [runtime/examples/ros2/onbody-programs.example.json](../runtime/examples/ros2/onbody-programs.example.json)。格式和全部规则在 `runtime/neuxmind_runtime/adapters/programs.py` 的文件头。要点：

- **地点 = 一串步骤**，每一步是机器人上的一个程序（`argv`，不经过 shell，每个元素就是一个参数）。按顺序执行，第一步没成功就结束，后面的不再启动。
- **怎样算成功必须写明**：退出码为 0 **并且**输出里出现 `ok` 给的内容；只看退出码的程序要明写 `exit_code_only: true`。这台机器狗的行走程序不管成没成功都以 0 退出，只在最后一行说结果，所以不能只看退出码。
- **重试**（`retry`）只用于程序在发出任何运动指令之前的拒绝，比如“传感器话题没收齐”：按输出里的内容（`when`）或程序为此保留的退出码（`exit_code`）判断。
- **请求里的值只通过占位符进入程序**：`{max_speed}`、`{duration_s}`、`{radius}`、`{max_distance}`（都是数值）和 `{run}`（这里生成的标签）。地点名只用来在配置里选一项，不会传给程序。速度写成三位小数并且只往下取（传给程序的不会高于上限）；小到写出来是 0 的值被拒绝，不会当作 0 传下去（有的程序把 0 当成“不限”）。环境文件（`env_file`）看不到也改不了程序的命令行，它打印的内容不算程序的输出，它换了目录程序也仍在 `workdir` 里启动；它自己把 shell 结束掉（`exit`）时这一步算失败。`argv` 要直接写程序本身，不要写一个再去启动它的包装脚本（管理层被杀时内核的 SIGTERM 只发给被启动的那个进程）。
- **速度**：用了 `{max_speed}` 的步骤要给 `speed_range: [最低, 最高]`，传给程序的是“这次允许的上限”和“最高”里小的那个，上限低于“最低”时拒绝；固定速度的步骤（爬楼梯）写 `speed`，上限低于它时拒绝。整条路线在第一步启动之前就全部核对。
- **区域**：路线取决于机器人在哪一层时，地点写 `region`，并按出发区域各给一条路线；进入另一个区域的步骤写 `enters`。适配器把当前区域记在 `state_file` 里：跨区域的步骤一开始就记为“未知”，成功后记为新区域；只有一种情况保持原来的区域：这一步每次都以 `retry.exit_code`（程序保留给“还没动就拒绝”的退出码）结束。输出里的文字不算数，程序可能走了几步之后才打印同样的话。**区域未知时，去任何地点和自由走都被拒绝**，并说明原因：停在楼梯上的机器人需要人到场，而不是一条按错误楼层规划的路线。人把机器人带回 `start_region` 之后，删除 `state_file` 并重启管理层。
- **停止**：取消动作或按停止时，向程序所在的进程组发 SIGTERM，`stop_grace_s`（最多 8 秒）之后仍在就 SIGKILL；停止路径不等待。**SIGTERM 只发一次**：急停锁存期间管理层会反复调用适配器的停止，程序自己的受控停止（比如在楼梯上稳住）不会被第二个信号打断。程序以成功之外的任何方式结束（失败、超时、被杀）时，适配器自己再向速度话题发零速度。程序结束时它留在同一进程组里的子进程一并结束。
- **管理层自己死掉时**（崩溃、被强杀）：内核会给正在运行的程序发 SIGTERM（Linux 的 `PR_SET_PDEATHSIG`），所以收到 SIGTERM 会停下机器人的程序不会无人看管地继续走。不理会 SIGTERM 的程序这时不会被结束，重启后的管理层也不知道它：**接进来的程序必须在 SIGTERM 时停下机器人**。
- **同一时间只运行一个**：程序在跑时，新的地点或自由走请求被拒绝（作为一次失败的动作返回，不会打断正在跑的那个）；非零的速度指令回答 `accepted: false`、不发布（程序正在同一个话题上驾驶）；零速度和停止始终照发。

另外两处为这类机器人加的小改动：`battery_percentage: "percent"`（电池话题的百分比是 0–100 而不是消息定义里的 0–1）；安装脚本多认一项 ROS 设置 `ZENOH_SESSION_CONFIG_URI`（设备用 `rmw_zenoh_cpp` 时，管理层要用和设备节点相同的会话配置）。

## 怎么用

**仿真（现在就能试）。** 控制台里添加一台仿真四足机器人 → “安装技能包”的示例里装“去指定地点”“巡检”“无图自由走” → 运行。仿真本体认识三个虚构的地点（出发点、会议室、二楼，坐标是编的，没有楼梯），自由走是绕出发位置走星形的替身。它只用来看技能和流程，不说明真机怎么走。

**真机。** 步骤和别的技能一样，没有为这三个技能开捷径：

1. 机器人上装管理层，本体选 `ros2`，安装目录里放带 `programs` 的 `ros2-config.json`（话题名、`battery_percentage`、`programs`）。在控制台里做：卡片上的「本体设置」选真实本体、填 ROS 2 环境和本体配置，再点「安装管理层」；以后改地点点「应用到机器人」（[ROBOT_BODY.md](ROBOT_BODY.md)）。也可以在机器人上用安装脚本手工装（runtime/README.md §3.3）。
2. 控制台里连接这台机器人，填写安全限值（最大线速度要不低于路线里固定速度的步骤，否则路线会被拒绝并说明是哪一步）。
3. 在机器人页面安装三个技能包；“登记技能”，把它们编排进一个应用（步骤的参数表单和运行时一样）。
4. 现场测试（会让机器人真的走，需要现场确认）→ 部署 → 启动。停止按钮随时可用，停止后要现场确认才能解除。

issue #42 之后，第 3 步装好技能包就可以直接运行（要两项现场确认），不必先编排应用：见 [SKILL_RUN.md](SKILL_RUN.md)。

## 在哪里验证过，哪里没有

验证过的（全部是替身，没有真机）：

- `spec/tests/test_spec.py`：两项能力的字段、清单里地点列表的规则、技能能声明依赖它们。
- `runtime/tests/test_places_explore.py`：仿真四足上经能力总线的授权、未知地点、速度上限、时长和半径上限、停止和锁存。
- `runtime/tests/test_programs.py`：程序运行器，用临时目录里的小脚本当程序：成功规则、顺序、重试、超时、取消、SIGTERM 只发一次、不理会 SIGTERM 的程序被杀、遗留子进程和“管理层被强杀后程序收到 SIGTERM”（这两项只在 Linux 上跑）、别的会话里占着输出的辅助进程不拖住动作也盖不掉程序的结果、打开的文件很多时照样读得到输出、参数不经 shell、环境文件碰不到命令行（提前 `exit`、换目录、最后一条命令为假）、速度上限和取整、区域和它的持久化（只凭保留的退出码保持原区域）。
- `runtime/tests/test_ros2_programs.py`：rclpy 测试替身上的 ROS 2 适配器：清单、经总线到程序的速度上限、失败后发零速度、停止结束程序并锁存、第二个请求不打断第一个、被拒绝的请求不会解除速度看门狗、程序接手时先把速度话题清零、反复停止只给程序发一次 SIGTERM、程序运行时不接受非零速度。
- `runtime/tests/test_place_skills.py`：三个技能从安装到结果，仿真四足上一遍（进程内和独立进程各一遍），ROS 2 替身加替身程序上一遍（巡检按“上楼、下楼、去会议室、回出发点”的顺序启动程序）。
- `runtime/tests/test_device_install_ros2.py`（Linux）：安装脚本记录并只使用 `ZENOH_SESSION_CONFIG_URI`。
- `runtime/tests/ros2_humble/`（**真实的 ROS 2 Humble**，容器里，Fast DDS）：替身程序本身是一个真实的 rclpy 节点，经管理层启动后在真实的 `/cmd_vel` 上发指令。没填限值时拒绝、不启动程序；填了之后程序按管理层给的上限（0.3 m/s）行驶并成功结束；长距离行走中按停止，程序在宽限期内结束，话题上最后几条是零速度；一个自己发不出零速度的程序被取消后，适配器发的零速度到达底盘；管理层被 SIGKILL 后程序收到内核的 SIGTERM、停下并退出。46 项通过。
- `sdk/tests`：从带中文地点名的清单生成适配器脚手架（地点名原样带过去；带引号、空格、换行的地点名仍被拒绝）。
- `tests/test_place_skills_desktop.py`：控制台后端对一台仿真四足：示例里有这三个技能和起始参数、安装、运行到结束、运行中停止、机器人页面上两项能力的说明和地点列表。

没有验证的：

- **真机上的任何一步**：管理层没有装到这台机器狗上，适配器没有接过它的 ROS 2（它用 `rmw_zenoh_cpp`，仓库里的真实 ROS 2 测试用的是 Fast DDS），它的程序没有经管理层启动过，停止没有在它身上试过。
- **这台机器狗的程序收到 SIGTERM 时自己能不能发出零速度**：它们先装信号处理、后 `rclpy.init()`。在容器里，这样写的替身程序收到 SIGTERM 时 rclpy 先把自己关掉，程序的零速度发不出去。经管理层停止时适配器会自己发零速度（上面测过）；但管理层自己死掉时没有人替它发，这时机器狗能不能停下取决于厂商运控对速度指令的超时，这一点没有验证。
- 机器人自己的程序的行为（定位、避障、爬楼梯、厂商自动刹车的开关）不在本仓库里，这里既不测试也不保证。配置里某一步如果会关掉厂商的保护功能，那是写配置的人的决定，要在配置旁边写明。
- 区域记录只和上一个程序的报告一样可靠：机器人被人搬到别处，这里不会知道；`state_file` 被删掉就当作在 `start_region`（这正是恢复的办法，所以不要在机器人还在楼上时删它）。
- 程序运行时有人直接发非零速度指令：指令不会发布，但管理层的速度看门狗仍会为它触发一次，往程序正在驾驶的话题上发一条零速度。控制台不会这样做；自己写的技能不要在调用这两项能力的同时发速度指令。
- 界面：没有为这三个技能新增页面，用的是已有的示例、安装、运行和应用编排页面；这次没有做浏览器验收。

## 已知限制

- 控制台里的真实本体设置（[ROBOT_BODY.md](ROBOT_BODY.md)）没有在真机上走过；本体配置在界面里是 JSON 文本，没有逐项的表单编辑器。
- 区域未知之后的恢复要到机器人上删文件、重启管理层，控制台里没有对应的按钮。
- 适配器没有 `legged.posture`（站起、趴下由机器人自己的程序在路线里完成），而内置的“四足机器人”本体类型把它列为应有的运控接口。
- 技能参数里的地点选项（会议室、二楼）写在技能包里；换一个场地要改技能包的选项，或者用“巡检”技能的文字参数。
- 运行时的版本号没有变（仍是 0.4.0），能力标准从 1.1 升到 1.2（`neuxmind_spec` 1.2.0）。旧的管理层不认识这两项能力：装了新技能的机器人要用这一版的管理层。
